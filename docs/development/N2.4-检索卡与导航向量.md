# DocQuery N2.4 检索卡与导航向量

> 状态：设计、实现、自动化验证与用户验收均已完成  
> 设计确认日期：2026-08-06  
> 实施授权：用户已于 2026-08-06 明确说“确认开始 N2.4”  
> 完成验收：用户已于 2026-08-10 明确说“确认 N2.4 完成”  
> 前置阶段：N2.3 已完成并经用户验收，完整回归 73/73 通过

## 1. 阶段目标

N2.4 读取 N2.3 已验证的 `canonical.jsonl`，为当前 `DocumentVersion` 生成一份可复用、可校验、可追踪的语义导航产物：

- 一张整文档 `DocumentProfile`；
- 每个非根真实标题节点一张 `RetrievalNode`；
- 每张检索卡对应的 2,560 维导航 Embedding；
- 一个不可变 `retrieval.jsonl` 派生对象及其 MySQL 清单。

N2.4 解决的是“哪份文档、哪个真实章节可能相关”，不负责在原文中执行关键词定位，也不负责回答问题。

```text
canonical.jsonl
→ DeepSeek 生成受限语义字段
→ Java 绑定真实标题树和原文范围
→ 构造稳定 Embedding 输入
→ 阿里云百炼生成 2,560 维导航向量
→ 校验并保存 retrieval.jsonl
```

## 2. 本阶段不做

- 不写 Elasticsearch，不创建 BM25 或向量索引；
- 不实现 `/retrieve`、`/answer`、RRF、查询 Embedding 或受控 Agent；
- 不引入 Redis；
- 不生成文件中不存在的标题、目录或语义树；
- 不把检索卡摘要作为答案证据；
- 不切换 `Document.activeVersionId`，不把版本改为 `READY`；
- 不把当前 ProcessingJob 标记为完整成功；
- 不启用生产 RabbitMQ Listener；
- 不实现 RAPTOR、GraphRAG、固定窗口 Chunk 向量化、OCR 或复杂版面恢复。

## 3. 已选模型与供应商边界

### 3.1 Chat Model

| 项目 | 选择 |
| --- | --- |
| 供应商 | DeepSeek 官方平台 |
| Base URL | `https://api.deepseek.com` |
| 模型 ID | `deepseek-v4-flash` |
| 凭证 | `DEEPSEEK_API_KEY` |
| 检索卡生成模式 | 非思考，`thinking.type=disabled` |
| 输出方式 | JSON Output + 本地 Schema/业务校验 |

DeepSeek 只生成 `purpose`、`summary`、`topics`、`aliases` 和 `answerableQuestions` 等语义字段。稳定 ID、标题、父子关系、标题路径和原文范围全部由 Java 从 canonical 事实附加，不能由模型决定。

DeepSeek 官方 JSON Output 只作为“返回合法 JSON”的第一层保障。DocQuery 仍需使用固定 Schema、字段白名单、长度、数量和覆盖校验；不能把供应商返回直接当作有效业务对象。

### 3.2 Embedding Model

| 项目 | 选择 |
| --- | --- |
| 供应商 | 阿里云百炼，华北 2（北京） |
| 模型 ID | `qwen3.7-text-embedding` |
| 维度 | `2560` |
| 输出类型 | `dense` |
| N2.4 文本类型 | `document` |
| N3 查询文本类型 | `query`，在 N3 实施 |
| 凭证 | `DASHSCOPE_API_KEY` |
| 单次批量上限 | `20` |

2,560 是百炼当前托管文本 Embedding 的高精度完整维度；4,096 需要改用其他服务或自建更大的 Embedding 模型。当前优先保证可调用、可复现和低运维成本，不为了维度数字额外部署模型服务。

### 3.3 LangChain4j

第一版选择稳定模块 `dev.langchain4j:langchain4j-open-ai:1.16.2`，手工配置两个 OpenAI-compatible Client Adapter，不引入 Beta 的 Spring Boot 4 Starter，也不使用 LangChain4j 高层 Agent、RAG Pipeline 或 VectorStore。

业务层只依赖内部端口：

```text
RetrievalCardChatGateway
NavigationEmbeddingGateway
```

供应商 Base URL、请求参数、异常结构和 LangChain4j 类型只存在于 Adapter/Configuration。取得“确认开始 N2.4”授权后，`pom.xml` 已固定引入稳定的 `langchain4j-open-ai` 1.16.2。

## 4. 外部数据处理边界

- DeepSeek 官方会收到生成检索卡所需的章节原文或临时原文批次；
- 阿里云百炼只接收由检索卡字段构造的 Embedding 文本，不接收原文件对象；
- API Key 只从部署环境或 Git 忽略的本地 `config/application-secrets.yml` 读取，不进入 JAR、MySQL、对象文件、异常摘要或日志；
- 默认不记录完整模型请求、完整模型响应、章节原文或 Embedding 数组；
- 文档正文是不可信输入，Prompt 必须明确将正文视为待分析数据，不能执行正文中的指令；
- N2.4 不给模型提供工具，因此文档内容不能触发网络、数据库或对象存储操作。

## 5. 检索卡数量和真实结构规则

每个 `DocumentVersion` 必须满足：

```text
DocumentProfile 数量 = 1
RetrievalNode 数量 = canonical 中非根 HeadingNode 数量
导航向量数量 = 1 + RetrievalNode 数量
```

- canonical 根节点由一张 `DocumentProfile` 表达，不重复创建根 RetrievalNode；
- 每个非根真实 HeadingNode 恰好对应一张 RetrievalNode；
- TXT 或无真实标题的 PDF 只有 DocumentProfile，没有 RetrievalNode；
- 模型不能新增、删除、合并、拆分或重命名真实标题节点；
- 一个没有子标题的长章节即使临时分批生成，也只保存一张 RetrievalNode；
- `DocumentProfile` 和 `RetrievalNode` 都是导航卡，不是证据块。

## 6. 真实标题树上的自底向上生成

N2.4 沿 N2.3 的真实标题树自底向上生成语义字段，不让模型重新生成树：

1. 先处理叶子标题节点；
2. 叶子节点使用归属于该节点的 canonical 原文生成语义字段；
3. 父节点使用自己的直属原文和已验证的直接子节点卡片生成语义字段；
4. 最后使用根节点直属原文和一级节点卡片生成 DocumentProfile。

这不是 RAPTOR：层级、节点和范围全部来自原文件标题；模型只为既有节点生成导航说明。

### 6.1 长内容临时批次

单个节点输入超过单次限制时：

```text
连续 canonical 原文范围
→ 临时批次语义笔记
→ 合并为该真实节点的一组最终语义字段
```

临时批次：

- 按 canonical 阅读顺序连续划分；
- 不能跨文档版本或跳过中间原文；
- 不写 MySQL、对象存储或 Elasticsearch；
- 不生成独立向量；
- 不成为检索结果；
- 任一批次或最终合并失败时，整个 retrieval artifact 失败。

## 7. 模型输出契约

模型只输出语义字段，不输出可信结构字段。

### 7.1 DocumentProfile 语义字段

| 字段 | 约束 | 含义 |
| --- | --- | --- |
| `purpose` | 必填，1～400 字符 | 文档用途和覆盖范围 |
| `topics` | 1～12 项，每项 1～80 字符 | 主要主题 |
| `aliases` | 0～12 项，每项 1～80 字符 | 常见简称、同义或口语表达 |
| `answerableQuestions` | 1～8 项，每项 1～200 字符 | 文档可能回答的问题，不包含答案 |

### 7.2 RetrievalNode 语义字段

| 字段 | 约束 | 含义 |
| --- | --- | --- |
| `summary` | 必填，1～600 字符 | 当前真实章节讲什么 |
| `topics` | 1～12 项，每项 1～80 字符 | 章节主题 |
| `aliases` | 0～12 项，每项 1～80 字符 | 用户可能使用的其他表达 |
| `answerableQuestions` | RetrievalNode 为 0～8 项，DocumentProfile 为 1～8 项；每项 1～200 字符 | 当前章节或文档可能回答的问题，不包含答案；没有可安全问题的标题节点使用空数组，不能为满足数量而编造 |

所有字符串需要去除首尾空白；数组需要去除空值和完全重复值，但不能通过不透明的同义合并改变模型结果。未知字段、缺失必填字段、超限或错误类型均判为无效输出。

## 8. Java 附加的可信字段

### 8.1 DocumentProfile

- `cardId`：`{documentVersionId}:rp:document`；
- `documentId`、`documentVersionId`；
- `rootHeadingNodeId`；
- 逻辑文档标题和源格式；
- canonical artifact ID、Schema Version 和 SHA-256；
- Chat Provider/Model、Prompt Version、Schema Version、Thinking Mode；
- Embedding Provider/Model、维度和模板版本；
- 生成时间。

### 8.2 RetrievalNode

- `cardId`：`{documentVersionId}:rn:{六位稳定顺序号}`；
- `headingNodeId`、`parentNodeId`、`depth`、同级顺序；
- 文件中的真实标题和完整 `headingPath`；
- `sectionStartBlockOrdinal`、`sectionEndBlockOrdinalExclusive`；
- canonical start/end；
- 可推导的起止页、段落或行范围；
- 与 DocumentProfile 相同的生成和 Embedding 血缘字段。

这些字段只能从 MySQL 可信事实和已验证 canonical 对象生成。模型响应中即使出现同名字段也必须拒绝，不能覆盖服务端值。

## 9. 稳定 Embedding 输入

`retrieval-embedding-v1` 使用固定字段顺序和换行规则：

```text
Document: {documentTitle}
Section: {完整真实标题路径；DocumentProfile 使用 ROOT}
Purpose/Summary: {purpose 或 summary}
Topics: {按卡片顺序连接}
Aliases: {按卡片顺序连接}
Questions: {按卡片顺序连接}
```

- 字段标签固定为英文，字段值保留原语言；
- 不包含时间、数据库 ID 之外的随机值或 API 响应元数据；
- 对构造后的 UTF-8 文本计算 `embeddingInputSha256`；
- N2.5 写索引前必须重新构造并核对摘要；
- 更改字段、顺序、分隔符、模型或维度都必须升级模板/生成配置，不能静默混用向量空间。

Embedding 返回必须满足：

- 数量和请求项一一对应；
- 顺序可验证；
- 每条恰好 2,560 个 float32 值；
- 所有值均为有限数，不含 `NaN` 或正负无穷；
- 向量不能全为零；
- 编码后再次解码逐位一致。

## 10. `retrieval.jsonl` 对象契约

每个 DocumentVersion 只保存一个被 MySQL 引用的不可变 `retrieval.jsonl`。记录顺序固定为：

```text
Header
DocumentProfile
RetrievalNode（按 canonical 标题稳定顺序）
Footer
```

### 10.1 Header 示例

```json
{"recordType":"header","schemaVersion":1,"documentVersionId":201,"canonicalArtifactSha256":"...","chatProvider":"DEEPSEEK","chatModel":"deepseek-v4-flash","promptVersion":"retrieval-card-v1","thinkingMode":"DISABLED","embeddingProvider":"ALIBABA_MODEL_STUDIO","embeddingModel":"qwen3.7-text-embedding","embeddingDimension":2560,"embeddingTemplateVersion":"retrieval-embedding-v1","generatedAt":"2026-08-06T12:00:00Z"}
```

### 10.2 检索卡和向量

语义字段保持普通 JSON 可读。向量使用紧凑、显式的 float32 编码：

```json
{
  "dimension": 2560,
  "encoding": "FLOAT32_LE_BASE64",
  "inputSha256": "...",
  "valueSha256": "...",
  "value": "mZk8Pr0..."
}
```

`FLOAT32_LE_BASE64` 表示先按 IEEE 754 little-endian float32 连续编码，再使用标准 Base64。与把 2,560 个小数直接写成 JSON 数组相比，它显著减少对象体积，并保持精确位模式和单一 JSONL 对象边界。

### 10.3 Footer

Footer 至少保存：

- `profileCount`，固定为 1；
- `nodeCount`；
- `vectorCount`；
- 语义字段摘要；
- 向量字节摘要；
- 生成配置指纹。

整个对象的 size 和 SHA-256 保存到 MySQL 清单，避免在 Footer 中形成自引用摘要。

## 11. MySQL 清单

实施时新增 `document_retrieval_artifact`，但设计确认阶段不创建迁移。清单概念字段包括：

- `id`；
- `document_version_id`，第一版唯一；
- `canonical_artifact_id`；
- `bucket_name`、`object_key`、`object_size`、`object_sha256`；
- `schema_version`；
- `profile_count`、`node_count`、`vector_count`；
- Chat Provider/Model、Prompt Version、Thinking Mode；
- Embedding Provider/Model、Dimension、Template Version；
- `generation_fingerprint`；
- `created_at`、`updated_at`。

MySQL 不保存检索卡正文和向量。N2.5 从已验证 `retrieval.jsonl` 流式读取并建立 ES 投影。

## 12. 生成配置指纹与重复执行

生成配置指纹至少覆盖：

```text
canonical artifact SHA-256
+ retrieval schema version
+ Chat provider/model
+ thinking mode
+ prompt version
+ Embedding provider/model/dimension
+ embedding template version
```

API Key、Base URL 中的 Workspace ID、超时和瞬时重试次数不进入指纹。

幂等规则：

1. 已有清单、对象完整且指纹匹配：直接复用，不调用模型；
2. 已有清单但对象暂时不可读：返回可重试基础设施错误；
3. 已有清单但对象摘要、结构或指纹不匹配：失败关闭，不能静默覆盖；
4. 并发生成时数据库唯一约束只保留一个胜者，失败者删除自己创建的精确对象；
5. 对象成功但数据库插入失败时立即删除本次对象；
6. 删除失败或进程崩溃由只扫描 `retrieval/` 前缀、具有宽限期并逐个检查数据库引用的安全回收任务兜底；
7. 数据库状态未知、对象年龄不足或引用检查失败时不删除。

第一版不实现在线模型升级和同一 DocumentVersion 的多套并行 retrieval artifact。配置变化遇到旧指纹时明确失败，后续通过受控重建设计解决。

## 13. 资源和调用预算

| 配置 | 默认值 | 目的 |
| --- | ---: | --- |
| 单次 DeepSeek 原文输入 | 64,000 UTF-16 code units | 限制单次延迟和输出失控 |
| 单文档累计模型原文 | 4,000,000 UTF-16 code units | 限制外部调用成本 |
| 单文档最大检索卡 | 2,000 | 防止极端标题树造成调用和对象膨胀 |
| 单文档最大 Chat 调用 | 128 | 限制批次、合并和修复总调用数 |
| JSON 修复 | 最多额外 1 次 | 容忍一次偶发格式错误，不无限重试 |
| 单个临时网络请求 | 最多 3 次尝试 | 处理超时、限流和 5xx |
| Chat 请求超时 | 180 秒 | 允许长章节生成但避免无限挂起 |
| Embedding 请求超时 | 60 秒 | 限制批量向量调用 |
| Embedding 每批 | 20 | 遵守百炼模型上限 |

输入批次必须覆盖全部范围。超过预算时返回 `RETRIEVAL_GENERATION_LIMIT_EXCEEDED`，不能静默抽样、截断或省略章节后继续成功。

模型响应 Usage 可用于观测，但不把供应商 Token 计数作为业务正确性的唯一依据。

## 14. 失败与重试契约

### 14.1 可重试失败

| 错误码 | 场景 |
| --- | --- |
| `RETRIEVAL_MODEL_UNAVAILABLE` | DeepSeek 超时、明确限流或 5xx |
| `EMBEDDING_MODEL_UNAVAILABLE` | 百炼超时、明确限流或 5xx |
| `RETRIEVAL_OBJECT_UNAVAILABLE` | retrieval 对象暂时无法写入、读取或校验 |
| `PROCESSING_DATABASE_UNAVAILABLE` | retrieval 清单暂时无法读写 |

单次供应商请求先执行最多 3 次有限尝试；仍失败后将受控异常交给 N2.2 已有的 Consumer 重试策略。不能无限叠加 SDK 与业务重试。

### 14.2 不可重试失败

| 错误码 | 场景 |
| --- | --- |
| `CANONICAL_ARTIFACT_NOT_FOUND` | 前置 canonical 清单不存在 |
| `CANONICAL_ARTIFACT_INTEGRITY_MISMATCH` | canonical 对象与清单不一致 |
| `RETRIEVAL_MODEL_AUTH_FAILED` | DeepSeek Key、余额、权限或模型配置错误 |
| `RETRIEVAL_MODEL_OUTPUT_INVALID` | 初次生成和一次修复后仍不符合契约 |
| `EMBEDDING_MODEL_AUTH_FAILED` | 百炼 Key、余额、地域、权限或模型配置错误 |
| `EMBEDDING_RESPONSE_INVALID` | 数量、顺序、维度、有限值或编码校验失败 |
| `RETRIEVAL_GENERATION_LIMIT_EXCEEDED` | 卡片、输入或调用预算超限 |
| `RETRIEVAL_ARTIFACT_VALIDATION_FAILED` | 最终 JSONL、覆盖、映射、计数或摘要失败 |

供应商错误必须映射为稳定错误码；异常摘要不能包含 API Key、完整正文、完整响应、Bucket 或 Object Key。

## 15. 完整生成流程

```text
按 documentVersionId 加载 MySQL 可信事实
→ 校验版本仍处于可处理状态
→ 加载并复核 canonical 清单与对象完整性
→ 解析 Header、EvidenceBlock、HeadingNode、Footer
→ 校验生成预算和真实标题覆盖数
→ 沿真实标题树自底向上调用 DeepSeek
→ JSON 解析、字段白名单、长度和数量校验
→ Java 附加真实节点、标题路径和原文范围
→ 按 retrieval-embedding-v1 构造稳定文本与 SHA-256
→ 按最多 20 张调用百炼 Embedding
→ 校验 2,560 维向量并编码 FLOAT32_LE_BASE64
→ 完整校验 Header、卡片、覆盖、向量、Footer
→ 写入随机 Key 的 retrieval.jsonl
→ 读回并校验对象大小、SHA-256 和可解码性
→ 插入 document_retrieval_artifact 清单
→ 返回已验证 artifact ID
```

N2.4 Service 只返回已验证 retrieval artifact，不修改 DocumentVersion、ProcessingJob 成功状态或 activeVersion。完整处理器仍要等待 N2.5 能够完成双索引、投影校验和 READY 切换后再接管生产 Listener。

## 16. 最小代码边界

实施时只新增 N2.4 所需边界，概念结构为：

```text
ai/RetrievalCardChatGateway
ai/NavigationEmbeddingGateway
ai.adapter/DeepSeekRetrievalCardChatAdapter
ai.adapter/AlibabaNavigationEmbeddingAdapter
service/DocumentRetrievalArtifactService
service/RetrievalArtifactStore
service.impl/...
entity/DocumentRetrievalArtifactEntity
mapper/DocumentRetrievalArtifactMapper
config/DocumentRetrievalProperties
```

- Gateway 接收项目自有请求/响应，不向业务层泄露 LangChain4j 类型；
- 模型 Adapter 不访问数据库、不改变文档状态；
- Artifact Service 负责可信事实加载、编排、校验、对象持久化和幂等；
- 不为 N2.5/N3 提前创建 Elasticsearch、Redis、Controller 或 Agent 类型。

最终名称允许在实施时根据现有工程包结构做小幅对齐，但职责边界不能改变。

## 17. 验收点

### 17.1 卡片与真实结构

- 有真实标题的 PDF、DOCX、Markdown：每个非根 HeadingNode 恰好一张 RetrievalNode；
- 无标题 TXT/PDF：恰好一张 DocumentProfile、零张 RetrievalNode；
- `headingNodeId`、父子关系、深度、标题路径和 canonical 范围逐项匹配 canonical；
- 模型不能新增、漏掉、重复或重命名标题节点；
- 长章节触发临时批次后仍只保存一张对应 RetrievalNode。

### 17.2 模型输出与向量

- DeepSeek 请求使用官方 Base URL、`deepseek-v4-flash`、JSON Output 和禁用思考；
- 非法 JSON、未知字段、缺失字段、数量或长度超限触发一次修复，仍失败则无产物；
- Embedding 请求使用 `qwen3.7-text-embedding`、`document` 类型和 2,560 维；
- 向量数量、顺序、维度、有限值、非零和 Base64 往返全部通过；
- `embeddingInputSha256` 可以从稳定模板重新计算得到同一结果。

### 17.3 对象、清单和幂等

- 每个 DocumentVersion 只有一个有效 MySQL retrieval 清单和一个被引用对象；
- 顺序重复调用直接返回同一 artifact，Fake Gateway 调用次数不增加；
- 并发生成只保留数据库胜者，败者对象被精确清理；
- 对象写入、读回、数据库插入或完整校验失败不留下有效清单；
- 超过宽限期且无数据库引用的 `retrieval/` 对象可被安全回收，状态不明时不删除。

### 17.4 失败、安全和资源

- 超时、限流、5xx、Key 错误、余额/权限错误、非法输出、维度错误和预算超限分别映射稳定错误码；
- 可重试与不可重试分类进入 N2.2 既有错误骨架；
- 超过预算不抽样、不截断、不伪成功；
- 日志、异常和数据库不泄露 API Key、完整正文或完整模型响应；
- 文档中的 Prompt 指令不能改变输出 Schema、真实节点或服务端字段。

### 17.5 测试边界

- 默认 `mvn verify` 使用 Fake Gateway 或本地 Stub Server，不访问真实供应商、不产生费用；
- 提供显式启用的真实 DeepSeek + 百炼小样本冒烟测试，缺少环境变量时不进入默认回归；
- 冒烟测试只记录模型、维度、计数、延迟和脱敏摘要，不记录 Key 或原文；
- N0、N1、N2.1、N2.2、N2.3 的 73 项既有回归继续通过。

### 17.6 阶段边界

- 不新增 Elasticsearch 或 Redis；
- 不写 BM25/KNN 索引；
- 不切换 activeVersion，不产生 READY；
- 不启用生产 Listener；
- 不实现查询 Agent、Retrieve 或 Answer。

## 18. 已确认的设计结论

1. Chat 使用 DeepSeek 官方 `deepseek-v4-flash`，检索卡生成关闭思考并执行 JSON Output + 本地严格校验。
2. Embedding 使用阿里云百炼华北 2（北京）`qwen3.7-text-embedding`，固定 2,560 维；N2.4 使用 `document` 文本类型。
3. 每个版本一张 DocumentProfile，每个非根真实标题一张 RetrievalNode；根节点不重复建卡。
4. 沿真实标题树自底向上汇总，不生成新树；长章节临时批次只服务于最终真实节点卡。
5. 向量保存在单一 `retrieval.jsonl` 中，采用 `FLOAT32_LE_BASE64`；MySQL 只存清单。
6. 生成配置指纹、稳定 Embedding 模板、向量维度和 canonical 血缘必须可追踪。
7. 任一卡片、向量或对象校验失败时不保存部分成功产物。
8. 资源预算、有限重试和稳定错误码按本文默认值执行。
9. N2.4 完成后仍不 READY；N2.5 完成双索引和投影校验后才能切换版本。
