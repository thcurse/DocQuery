## 1. 阶段结果

P2 不再把 DeepDoc 当作绕过 DocQuery 的独立离线解析器。它使用现有“测试科技”租户，把冻结的 100 份 MMLongBench-Doc 原始 PDF 通过管理面正式上传，完整经过：

```text
租户管理员上传
→ SeaweedFS 原文件
→ Outbox / RabbitMQ 既有主队列
→ DeepDoc HTTP 单解析槽位
→ canonical 原文与页位置
→ DeepSeek 检索卡生成
→ 百炼 Embedding
→ Elasticsearch 双索引投影
→ DocumentVersion READY / activeVersion 切换
```

阶段结束时形成真实可查询的专用知识库，并根据实际入库和证据页可用性冻结 N5.2 的正式文档、问题与失败清单。

## 2. 租户与资源边界

- 复用用户已经创建的“测试科技”租户；执行前先只读核对其实际 `tenantId` 和状态，不创建第二个评测租户。
- 在该租户内创建专用知识库 `MMLongBench-N5`，不与现有人工测试文档混用。
- 为 N5 评测准备专用 Application、READ Grant 和 Credential，后续 N5.2 只通过该应用调用 `/retrieve`、`/answer`，从凭证解析可信租户上下文。
- Credential Secret 只在创建时安全接收，不写入仓库、评测产物或日志。
- 如果同名知识库或应用已经存在，必须先核对内容和用途；不得自动清空、删除或覆盖。

## 3. 固定输入与提交规则

- 输入严格使用 `mmlongbench-docquery-v1` 已冻结的 100 份上游原始 PDF、`manifest.json`、`cases.jsonl` 和校验和；不生成、转换、修补或替换 PDF。
- 每份 PDF 先复核 SHA-256，再通过正常管理面上传接口提交。
- 上传使用由数据集版本和文档 SHA-256 派生的稳定 `Idempotency-Key`，重启执行器或重放请求不能创建重复文档。
- 可以连续提交多个文档任务；RabbitMQ 继续使用既有主队列和 Listener 并发，DeepDoc 服务内部解析并发固定为 1。不得新增专用解析队列或后处理队列。
- 100 份文档各提交一次；只允许系统现有的自动重试和第 6 节规定的受控人工恢复，不反复重跑成功文档。

## 4. 真实供应商与费用边界

完整入库会生成检索卡和导航向量，因此 P2 必然调用当前生产配置的真实 DeepSeek Chat 与百炼 Embedding，不再是“完全免费准入”。

- 用户已决定 100 份文档无需先做预算估算，本阶段不设置额外的预算讨论门。
- 仍须记录实际模型标识、配置指纹、供应商请求数、可获得的 Token/用量信息和文档处理耗时，供最终报告区分一次性入库成本与查询成本。
- P2 不执行 `/retrieve` 或 `/answer` case，不产生检索质量、回答质量或查询端到端延迟结论；这些属于 N5.2。
- 开始授权前不得上传文档、开启真实供应商调用或创建评测资源。

## 5. 正式评测集冻结规则

### 5.1 文档准入

文档只有满足以下条件才进入 N5.2 的可查询语料：

1. 上传字节与冻结 SHA-256 一致；
2. 对应版本在真实完整链路中最终达到 `READY`；
3. canonical 原文非空并保留可用的 1-based PDF 页位置；
4. 双索引投影验收通过并成为知识库当前生效版本。

失败文档默认不使用其他文档替换，也不修改原文件后重新进入，以避免根据结果挑选更容易的语料。唯一例外必须同时满足：尚未开始 N5.2、文档只是无 case 引用的 DISTRACTOR、失败原因是预先声明的资源边界而非检索/回答得分、替代文件来自同一固定上游快照，且经过用户明确确认并完整记录前后校验和。

### 5.2 问题准入

- 可回答题：来源文档必须准入，且官方列出的全部证据页在 canonical 位置映射中存在非空原文块。
- 不可回答题：来源文档必须准入；仍保留官方空证据页和空 Gold Answer 语义。
- 问题是否保留不能参考后续 Retrieve/Answer 的得分，防止按模型表现筛题。
- 干扰文档按真实入库结果保留；除 5.1 所述并经用户明确批准的资源边界例外外，失败时只记录，不从数据集另选替代文档。

P2 输出冻结后的 `documentKey → tenantId / knowledgeBaseId / documentId / activeVersionId` 映射和最终 case 清单，N5.2 不再临时换题或换文档。

## 6. 失败、重复与恢复

- 内容、加密、解析或 canonical 校验的稳定业务失败：记录最终错误码，不人工重试，不修改 PDF。
- RabbitMQ、对象存储、DeepDoc、供应商或 Elasticsearch 的瞬时故障：先等待既有自动重试；若最终失败且已确认依赖恢复，最多执行一次管理面人工重试并保留前后 Job 证据。
- 如果凭证、模型名或环境配置错误导致同类批量失败，立即停止继续提交，修复配置并验证单个失败样本后再恢复；不得让 100 份文档重复消耗供应商调用。
- 执行器重启时按稳定 Idempotency-Key 和现有租户资源对账，只补未提交项，不重复创建 Document。
- P2 不新增队列、不修改业务状态机、不重建租户；若发现产品缺陷，应先形成诊断和影响范围，不静默扩大 P2。

## 7. 最小执行产物

产物保存在 `evaluation/mmlongbench-docquery-v1/reports/`，不复制上游 PDF：

- `n5.1-p2-run.json`：租户、知识库、应用、模型、配置指纹、起止时间和执行环境；敏感凭证脱敏；
- `n5.1-p2-documents.jsonl`：100 份文档的校验和、稳定 ID、状态、失败码、Job/版本映射、页覆盖、处理时长和受控重试；
- `n5.1-p2-cases.jsonl`：80 个候选 case 的保留/排除结论和确定性原因；
- `n5.1-p2-summary.md`：可供项目展示的简明入库结果、失败分类、一次性入库用量和边界声明。

这些是实际运行记录，不重新生成大规模自制数据集，也不把 P2 写成官方 MMLongBench-Doc 榜单结果。

## 8. 验收点

P2 只有同时满足以下条件才可提交用户验收：

1. 实际使用既有“测试科技”租户和隔离的专用知识库，没有创建多余租户或污染已有知识库；
2. 冻结的 100 份 PDF 均有唯一上传记录和可解释的最终状态，没有丢失、无限等待或重复文档；
3. `READY` 文档真实完成 DeepDoc、检索卡、Embedding、双索引和激活，不把“仅解析成功”计为完整入库成功；
4. 每个失败都有稳定阶段、错误码和重试证据，且符合第 6 节上限；
5. 正式 N5.2 case 清单仅按预先冻结的文档状态和证据页规则生成，不依据模型得分挑题；
6. 专用 Application 对知识库具有 READ Grant，后续可从外部 API 真实查询，但 P2 尚未执行质量评测；
7. 报告明确区分入库用量与尚未执行的查询质量、回答质量、查询成本和端到端延迟。

## 9. 非目标与下一道门

P2 不做 Retrieve/Answer 质量评分、正式查询压测、故障矩阵、多轮 Conversation、会话记忆或流式 Answer。P2 完成并经用户验收后，只允许另行冻结 N5.2 的真实查询指标、执行方式、失败处理和报告格式；不得自动开始 N5.2。

### 10.5 标题候选治理决策

- 用户检查真实解析结果后指出 17 页 PDF 不应直接产生 100 个真实标题，并明确确认按标题候选治理方案修复后再继续。

- 修复必须保留全部文本和页位置：被拒绝的 title 只降级为 `PARAGRAPH`，不能删除；不调用 LLM 判断标题，不按“每页最多 N 个”或“全文最多 N 个”硬截断。
- 治理优先使用确定性证据：PDF Outline/Bookmark 可映射项、章节编号模式、候选后续正文范围、跨页相同位置重复页眉/页脚、重复弱标签和空章节。最终输出候选数、接受数、降级数和原因告警。
