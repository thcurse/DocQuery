# DocQuery N2.5 双索引投影与版本激活

> 状态：已按确认设计完成实现与验证，用户已于 2026-08-11 明确确认“N2.5 完成”  
> 前置阶段：N2.4 已完成实现、默认回归、真实供应商冒烟和用户验收  
> 本阶段门禁：已关闭；该完成确认不自动授权实施 N3

## 1. 阶段目标

N2.5 将 N2.3/N2.4 已验证的两个不可变对象投影到 Elasticsearch：

- `canonical.jsonl` 中每个 `EvidenceBlock` 投影为一条原文 BM25 记录；
- `retrieval.jsonl` 中一张 `DocumentProfile` 和每张 `RetrievalNode` 投影为导航向量记录；
- 两个投影都通过完整性校验后，MySQL 单事务将候选版本置为 `READY`、切换 `Document.activeVersionId` 并将 `ProcessingJob` 置为 `SUCCEEDED`；
- 提供完整 `DocumentIngestionProcessor`，使既有 RabbitMQ Listener 能够执行 N2.3 → N2.4 → N2.5 全链路。

N2.5 完成的是“文档可靠变成可检索版本”，不是“业务应用已经能够查询”。

## 2. 本阶段明确不做

- 不新增 `/retrieve`、`/answer` 或其他服务面 HTTP 接口；
- 不实现 Application Credential/Grant 的服务面过滤器；
- 不生成查询 Embedding，不执行 BM25/KNN 并行召回；
- 不实现 RRF、Top-K、字段权重和效果调参；
- 不引入 Redis、查询幂等、Agent、Reranker 或多轮对话；
- 不实现文档删除、旧版本 ES 清理、手动重建或在线 Mapping 升级接口；
- 不增加 Kibana、独立 Worker、独立向量数据库、固定 Token Chunk 或语义切分。

## 3. 为什么是两个 Elasticsearch 索引

这里的 Elasticsearch Index 更接近 MySQL 表，不是两台 Elasticsearch，也不是两个新对象文件。

| 索引 | 一条记录 | 主要查询方式 | 是否最终证据 |
| --- | --- | --- | --- |
| Evidence | canonical 中一个 `EvidenceBlock` | BM25 原文关键词定位 | 是 |
| Navigation | 一个 `DocumentProfile` 或 `RetrievalNode` | 2,560 维 KNN 语义导航 | 否 |

两类记录的字段和查询方式不同。拆分后原文索引不承担向量字段，导航索引不伪装成原文证据，也便于分别校验数量、Mapping 和重建范围。

第一版使用共享的多租户索引，不为 Tenant、KnowledgeBase、Document 或 DocumentVersion 创建独立索引，避免小索引和分片数量失控。可信范围字段随每条记录写入，并在 N3 查询阶段前置过滤。

## 4. Elasticsearch 与 Java Client

固定版本：

| 项目 | N2.5 值 |
| --- | --- |
| Elasticsearch Server | `9.4.4` |
| Java Client | `co.elastic.clients:elasticsearch-java:9.4.4` |
| Java | 17 |
| 本地拓扑 | 单节点、一个命名数据卷、`restart: "no"` |
| 本地管理工具 | 不部署 Kibana |

Java 业务层依赖内部 `SearchProjectionStore`，Elasticsearch Java Client 类型只存在于配置和 Adapter。

本地 Compose 关闭 Elasticsearch Security 并只绑定开发端口；该设置只用于本机可复现环境。应用配置保留 Endpoint/API Key 边界，生产环境应使用 TLS 和认证。

## 5. 索引名称与 Mapping 版本

第一版物理索引与稳定别名：

```text
docquery-evidence-v1      <- alias: docquery-evidence
docquery-navigation-v1    <- alias: docquery-navigation
```

索引前缀可配置，用于测试或多环境隔离。写入和后续查询只使用稳定别名；清单同时记录实际物理索引和 Index UUID。Mapping 变化必须创建新版本索引并受控重建，不能静默改变 `v1`。

两个 Mapping 均使用 `dynamic: strict`。索引不存在时可以幂等创建；索引或别名已经存在但 Mapping 版本、分析器或向量维度不兼容时 fail-closed，禁止自动删除或重建已有索引。

## 6. Evidence 原文索引契约

### 6.1 记录粒度与 ID

```text
一条 canonical EvidenceBlock = 一条 ES Evidence 记录
ES _id = blockId
```

`blockId` 已包含稳定 DocumentVersion 身份和顺序。N2.5 不重新执行固定 Token Chunk、Overlap 或模型切分。

### 6.2 主要字段

- 可信范围：`tenant_id`、`knowledge_base_id`、`document_id`、`document_version_id`；
- 血缘：canonical artifact ID/SHA-256、Evidence Mapping 版本、projection fingerprint；
- 结构：`block_id`、`ordinal`、`kind`、`heading_node_id`、`continuation_group_id`；
- 文本：文档标题、真实标题路径、原始 `text`；
- canonical 位置：`canonical_start`、`canonical_end`；
- 原位置：PDF 页内位置、DOCX 正文/表格位置、Markdown/TXT 行列范围。

### 6.3 文本分析

中文/中英混合正文主字段使用 Elasticsearch 内置 `cjk` analyzer，同时保留 `standard` multi-field 处理英文、错误码、接口名和配置项。N2.5 只冻结 Mapping，不冻结 N3 的字段 Boost、候选数量或查询 DSL。

## 7. Navigation 导航索引契约

### 7.1 记录粒度与 ID

```text
一张 DocumentProfile = 一条 PROFILE 记录
一张 RetrievalNode   = 一条 NODE 记录
ES _id = cardId
```

### 7.2 主要字段

- 与 Evidence 相同的可信 Tenant/KnowledgeBase/Document/Version 范围；
- retrieval artifact ID/SHA-256、canonical artifact SHA-256、Mapping 版本和 projection fingerprint；
- `card_id`、`card_type`、`heading_node_id`、`parent_heading_node_id`、`depth`、`sibling_order`；
- 文档标题、真实标题、完整标题路径；
- canonical、Block ordinal 和源位置范围；
- `purpose/summary`、`topics`、`aliases`、`answerable_questions`；
- Embedding Provider/Model/Template、输入摘要、向量摘要；
- `embedding`：`dense_vector`、`dims=2560`、`similarity=cosine`。

Base64 向量在写入前必须重新解码并复核维度、有限值、非零、输入摘要和值摘要。ES 只保存可重建投影，完整精确向量仍以 `retrieval.jsonl` 为来源。

## 8. MySQL 投影验收单

V8 新增 `document_search_projection`。每个 DocumentVersion 最多一条，保存：

- Tenant、KnowledgeBase、Document、DocumentVersion；
- canonical/retrieval artifact ID 和 SHA-256；
- ES cluster UUID；
- 两个物理索引名称、Index UUID 和 Mapping 版本；
- Evidence/Navigation 预期数量和实际数量；
- projection fingerprint；
- 完成时间和更新时间。

该表不保存原文或向量，不决定权限，也不替代 ES。它是 MySQL 中的投影验收单：没有完整验收单不能进入 READY；已有验收单也必须重新检查目标 Cluster/Index UUID、数量和指纹后才能复用。

投影验收单是可重建的持久清单，允许在受控重建后更新 Cluster/Index UUID 和完成时间；canonical/retrieval 对象本身仍保持不可变。

## 9. 投影指纹

projection fingerprint 至少覆盖：

```text
documentVersionId
canonical artifact ID/SHA-256
retrieval artifact ID/SHA-256
Evidence Mapping 版本
Navigation Mapping 版本
Embedding Provider/Model/Dimension/Template
索引前缀
```

Endpoint、API Key、超时、ES Cluster UUID 和本地批大小不进入业务指纹。

## 10. 幂等写入与校验顺序

`ensureProjection(documentVersionId)` 使用以下顺序：

```text
加载 MySQL 可信 Document/Version 与两个 artifact 清单
→ 复核 Version 仍为 PROCESSING
→ 读回并完整校验 canonical/retrieval JSONL
→ 校验或创建两个索引与别名
→ 计算 projection fingerprint
→ 若已有清单，复核 Cluster/Index UUID、指纹和 ES 数量后复用
→ 若无有效清单，清理该候选 Version 的旧未验收投影
→ 流式批量写 Evidence
→ 流式批量写 Navigation
→ 最终 refresh
→ 按可信范围、artifact SHA 和 projection fingerprint 校验精确数量
→ 插入或更新 document_search_projection
```

Bulk 使用确定性 `_id` 和 `index` 操作。重复消息、Confirm 不确定和进程重启可以覆盖相同记录，不能增加数量。

当前默认批量边界：单批最多 500 条且编码后最多 5 MiB；任一上限先到即发送。批间不 refresh，只在完整写入后执行一次 refresh 和验证。

## 11. 版本可见性与原子切换

ES 记录不保存可变 `active=true`。MySQL 是版本可见性的唯一事实源。

N3 查询开始时必须读取一份 KnowledgeBase 当前 `activeVersionId` 快照，并让 BM25 与 KNN 使用同一组 Version ID。这样一个查询要么完整使用切换前版本，要么完整使用切换后版本，不会两路混用。

投影完成后，MySQL 在一个事务内：

1. 锁定并复核 Document、DocumentVersion、ProcessingJob 和投影清单；
2. 要求候选 Version 仍为 `PROCESSING` 且等于 `latestVersionId`；
3. 将 Version 置为 `READY`、清空失败信息、写 `readyAt`；
4. 将 `Document.activeVersionId` 原子指向候选 Version；
5. 将当前 Lease Owner 持有的 Job 从 `RUNNING` 置为 `SUCCEEDED`；
6. 任一条件更新失败则整个事务回滚。

旧 Version 可以继续保留 `READY` 历史状态，但不再是 `activeVersionId`。第一版不增加 `SUPERSEDED` 状态。

## 12. 完整 Processor 与 Listener

N2.5 提供 `DocumentIngestionProcessor` 生产实现：

```text
ensureCanonical(versionId)
→ ensureRetrieval(versionId)
→ ensureProjection(versionId)
→ activate(versionId, jobId, leaseOwner)
```

Processor 返回后 Listener 才 ACK。激活事务提交后、ACK 前崩溃时，重复消息会看到 `ProcessingJob=SUCCEEDED` 并直接 ACK。

公共配置继续将真实模型和生产 Listener 默认关闭，避免克隆仓库后意外产生外部费用。完整部署必须显式开启 Provider、Elasticsearch 和 Listener；自动化 E2E 使用 Fake Gateway 和真实 MySQL/SeaweedFS/RabbitMQ/Elasticsearch。

## 13. 失败分类

| 错误码 | 可自动重试 | 含义 |
| --- | --- | --- |
| `SEARCH_INDEX_UNAVAILABLE` | 是 | 连接、超时、5xx 等暂时不可用 |
| `SEARCH_BULK_REJECTED` | 是 | 429 或可恢复 Bulk 项失败 |
| `SEARCH_AUTH_FAILED` | 否 | ES 凭证或权限配置错误 |
| `SEARCH_INDEX_SCHEMA_MISMATCH` | 否 | 索引、别名或 Mapping 与冻结契约不一致 |
| `SEARCH_VECTOR_DIMENSION_MISMATCH` | 否 | 导航向量不是 2,560 维 |
| `SEARCH_PROJECTION_VALIDATION_FAILED` | 否 | 数量、ID、来源摘要或指纹不完整 |
| `SEARCH_ACTIVATION_CONFLICT` | 否 | 候选 Version/Job/latestVersion 状态已变化 |

日志、异常和数据库不保存 API Key、Authorization Header、完整原文、完整向量、完整 Bulk 请求或 ES 完整响应。

## 14. 部分失败与恢复

- Evidence 成功而 Navigation 失败：不写有效清单、不 READY，旧 activeVersion 不变；
- Bulk 部分成功：整次投影失败，重试前按可信 Tenant/KnowledgeBase/Version 范围清理未验收记录；
- 写完 ES、清单前崩溃：重试清理或覆盖相同 `_id` 后重新校验；
- 清单成功、激活前崩溃：重试验证清单和 ES 后执行激活；
- 激活成功、ACK 前崩溃：重复消息读取成功 Job 并 ACK；
- ES 清理失败：不能 READY；残留候选 Version 因不在 MySQL activeVersion 快照中而对 DocQuery 查询不可见；
- 新版本最终失败：既有 activeVersion 继续服务。

## 15. 配置边界

N2.5 新增配置概念：

- `enabled`、`endpoint`、可选 API Key；
- Index prefix、两个物理索引版本和稳定别名；
- Evidence analyzer、Embedding dimension/similarity；
- Bulk actions/bytes、连接和请求超时；
- 本地 shard/replica 仅用于创建新索引。

Mapping 业务值在代码中固定并进入 Mapping 校验，不能通过部署变量把 2,560 维静默改成其他维度。

## 16. 验收点

1. Elasticsearch 9.4.4 与 Java Client 9.4.4 可以在 Java 17 下连接；
2. 两个索引和别名可以幂等创建，Mapping/别名不兼容时 fail-closed；
3. Evidence 数量等于 canonical Block 数量，Navigation 数量等于 Profile + Node 数量；
4. ES `_id`、可信范围、标题、位置、artifact SHA、向量血缘与两个 JSONL 一致；
5. 2,560 维向量可以写入并通过真实 KNN 最小查询；
6. 重复投影、重复消息和并发执行不增加记录数量；
7. 一个索引成功、另一个失败时 Version 不 READY，旧版本继续 active；
8. v2 处理/失败时 v1 继续 active，v2 成功后原子切换；
9. 投影后崩溃、清单后崩溃和激活后 ACK 前崩溃均可幂等恢复；
10. 错误 Mapping、错误维度、错误数量和错误摘要全部拒绝 READY；
11. 完整 Listener E2E 能从 RabbitMQ 消息完成两个 artifact、两个 ES 投影、清单、READY、activeVersion 和 Job 成功；
12. N0—N2.4 既有回归继续通过，默认回归不访问真实模型；
13. 可选执行一次真实模型 + 真实 ES 的小文档完整链路冒烟，单独记录且不进入免费默认回归。

## 17. 实施与验证记录

截至 2026-08-11，已完成：

- Elasticsearch Server/Java Client 固定为 9.4.4；Compose 新增单节点 Elasticsearch，业务层通过内部 `SearchProjectionStore` 隔离客户端类型；
- 创建 `docquery-evidence-v1`/`docquery-navigation-v1` 物理索引及稳定别名，两个 Mapping 均为 `dynamic: strict`；
- V8 新增 `document_search_projection`，投影指纹覆盖版本、两份 artifact、Embedding 配置、Mapping 版本和索引前缀；
- Evidence 保存原文、标题路径、位置和 canonical 血缘；Navigation 保存卡片、2,560 维向量及输入/向量摘要血缘；
- 实现按版本范围清理、确定性 ID Bulk、精确数量复核、验收单复用以及 MySQL 原子激活；
- 完整 `DocumentIngestionProcessor` 已接通既有 RabbitMQ Listener，公共配置仍默认关闭真实模型、ES 投影和生产 Listener。

验证证据：

- `./mvnw.cmd -q "-Dit.test=DatabaseStartupIT" verify`：7/7 通过，真实 MySQL 8.4 从空库执行 V1—V8；
- `./mvnw.cmd -q "-Dit.test=DocumentSearchProjectionIT" verify`：3/3 通过，真实 MySQL、SeaweedFS、RabbitMQ、Elasticsearch + Fake Gateway；
- 上述专项覆盖 BM25、真实 2,560 维 KNN、artifact/Embedding 血缘、重复投影修复、Lease 冲突、Rabbit 消息全链路和 READY 原子切换；
- `./mvnw.cmd -q verify`：单元测试 23 项（22 通过、1 项真实供应商测试按设计跳过），集成测试 69/69 通过，0 failure、0 error；
- `docker compose config --quiet`：通过。

Elasticsearch 9 默认不把 `dense_vector` 放入 `_source`，因此验收通过真实 KNN 查询证明向量可用，而不是读取 `_source` 假装验证向量。默认回归没有调用 DeepSeek 或百炼，不产生模型费用。
