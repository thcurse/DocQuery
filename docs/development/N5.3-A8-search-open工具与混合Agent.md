# N5.3-A8 `search/open` 工具与混合 Agent

> 状态：`COMPLETED_FAILED_REVALIDATION / PENDING_USER_DECISION`
> 冻结日期：2026-08-24

## 1. 目标

只重构现有非流式、单轮 `/answer` 的内部 Agent：

- 使用 LangChain4j `AiServices` 管理本次请求内的 Tool Calling 循环；
- DocQuery 继续控制授权、activeVersion 快照、Redis 幂等与续租、预算、审计、
  canonical Evidence 登记、最终引用校验和失败映射；
- 将现有 `searchDocuments`、`getDocumentOutline`、`searchWithinDocument`、
  `readSection` 收敛为模型可理解的 `search` 与 `open`；
- Java 在进入 Agent 前用原问题执行一次同契约的初始 `search`，不再要求模型用第一次
  Tool Call 重复原问题检索。

## 2. 非目标

- 不实现 Conversation、跨请求消息历史、会话记忆或摘要；
- 不实现流式输出；
- 不新增索引、Embedding 类型、Reranker、数据库迁移或外部 HTTP 接口；
- 不引入搜索候选池、搜索分页或模型可调 `topK`；
- 不新增计算工具；
- 不重建现有文档，不执行付费模型调用，不扩大到 20/80 题 Answer。

## 3. 工具契约

### 3.1 `search`

输入：

```json
{"query":"...","documentRef":"D1"}
```

- `query` 必填，最大长度沿用 Answer 工具查询上限；
- `documentRef` 可选，只能使用本次 Answer 会话由 DocQuery 返回的 `D#`；
- 不允许模型提交 Tenant、KnowledgeBase、Document/Version ID、模式、`topK` 或 ES 条件；
- 无 `documentRef` 时检索本次 KnowledgeBase 固定 activeVersion 快照；有值时只检索对应
  固定文档版本；
- 底层复用 N3.2 BM25、Navigation KNN、RRF 与 canonical 读取，不增加第二套检索算法；
- 返回固定上限的结构化候选、`documentRef`、`sectionRef`、标题路径、位置、通道和已登记
  canonical Evidence；检索卡仅提供地址，不能成为引用；
- 完全相同的规范化参数在本次会话内复用结果，不重复执行 Embedding。

### 3.2 `open`

输入：

```json
{"ref":"D1"}
```

或：

```json
{"ref":"S1"}
```

- `D#`：打开该文档的真实 canonical 目录，返回唯一 `sectionRef`、完整标题路径、父子关系
  和是否有子标题；不返回整篇正文；
- `S#`：沿用 A4 最小章节读取语义：导航分区读取精确范围；真实叶子标题读取完整叶子章节；
  带子标题的父标题只读取自身正文并返回直接子标题；
- 模型不能提交页码、block、headingNodeId、canonical offset 或对象位置；
- 所有可引用文本仍由 Java 登记为 `E#`，并受 canonical 总预算约束。

## 4. 单轮执行链路

```text
鉴权并固定 activeVersion 快照
→ Redis ANSWER 幂等 OWNER
→ Java 使用原问题执行初始 search
→ 将问题和初始 SearchResult 交给 LangChain4j AiServices
→ Agent 按需调用 search / open
→ LangChain4j 管理工具消息续接
→ DocQuery 在工具钩子中检查预算、记录审计并续租 Redis
→ 模型返回严格最终 JSON
→ Java 校验状态、Evidence ID、逐段/逐项引用和输出边界
→ 完成 Redis 结果或 fail-closed 释放 OWNER
```

不配置 ChatMemory；一次 `AiServices` 实例只服务当前 Answer 请求。

## 5. 预算与失败

- 沿用现有工具轮次、调用总数、并行调用数、模型调用数、canonical、答案、引用和超时上限；
- LangChain4j 负责工具请求/结果消息与循环，DocQuery 观察每次模型响应和工具执行并执行硬上限；
- 未知工具、非法字段或无效 Ref 返回结构化 `INVALID_ARGUMENT`，允许 Agent 改正；
- ES、Embedding、canonical、模型或 Redis 失败保持既有稳定语义，不伪装为 `NO_MATCH` 或
  `INSUFFICIENT_EVIDENCE`；
- `INSUFFICIENT_EVIDENCE` 仍是 HTTP 200 知识终态；本阶段不额外引入末端 Reviewer。

## 6. 免费验证

- 单元测试覆盖初始 search、全库/文档范围 search、`D#` 目录打开、`S#` 最小章节读取、
  Ref 越界、重复搜索复用、工具/模型预算、引用注册和 Redis 续租；
- 适配器测试确认生产只声明 `search/open`，并由 LangChain4j 高层工具循环执行；
- 既有 Answer 幂等、审计、外部契约和 `/retrieve` 回归继续通过；
- 免费验证完成后停止，不自动执行固定 5 题真实复验。

## 7. 当前实现结果

- 生产 Answer 已改用 LangChain4j `AiServices` 高层循环，运行时只注册 `search/open`；
- 原问题初始 `search` 由 Java 在首个模型调用前执行，Agent 可以直接回答，也可以改写查询、
  限定 `D#` 搜索或打开 `D#/S#`；
- 完成条件仍由同一个 Agent 在循环内判断，Java 机械校验最终 JSON、引用集合、Evidence 存在性
  以及每个事实段落/列表项的引用；没有增加第二个 Reviewer 模型调用；
- 拒答只允许输出严格 `INSUFFICIENT_EVIDENCE + null + []`。提示词要求在所需事项尚未解决时
  继续改写/缩小搜索或打开章节，并禁止把工具故障伪装成证据不足；
- 本地协议测试确认 Responses 请求只声明两个工具且 Function Calling 结果由框架自动续接；
- 70 个单元测试通过，真实 MySQL、Redis、SeaweedFS、Elasticsearch 的 `RetrieveIT` 回归通过；
- 用户明确授权后已执行 PackyAPI 固定 5 题真实复验，结果失败，见第 8 节。

## 8. 固定 5 题真实复验

参数保持 `HYBRID / topK=10`，不传 `documentIds`。结果：

| Case | HTTP | Answer 状态 | Agent 工具调用 | 人工正确 |
| --- | ---: | --- | ---: | ---: |
| `0562` | 200 | `INSUFFICIENT_EVIDENCE` | 0 | 否 |
| `0607` | 200 | `INSUFFICIENT_EVIDENCE` | 0 | 否 |
| `0831` | 503 | `ANSWER_EXECUTION_LIMIT_EXCEEDED` | 首次 3，重试 0 | 否 |
| `0937` | 200 | `INSUFFICIENT_EVIDENCE` | 2 | 否 |
| `1032` | 200 | `INSUFFICIENT_EVIDENCE` | 0 | 否 |

汇总：逻辑成功 4/5，回答 0，受控拒答 4，执行上限错误 1，人工正确 0/5，Gold 页
覆盖率 0。`0562`、`0607`、`1032` 在 Java 初始搜索后没有调用任何 Agent 工具即拒答；
`0831` 两次均因单轮请求工具过多触发边界；`0937` 从 A6 的正确回答回退为拒答。

结论：高层框架接管循环和 `search/open` 工具收敛本身没有实现可机械验证的任务完成条件，
也没有阻止一次初始搜索后过早拒答。A8 未达到验收点，不扩大到 20/80 题。
