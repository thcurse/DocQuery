## 1. 阶段门禁

本章记录 N2.1 实施前冻结的范围、数据、上传受理契约和验收点。用户已于 2026-08-02 明确说“确认开始 N2.1”，因此开始门禁已经满足。

实现完成并提供测试证据后，用户已于 2026-08-02 明确确认“N2.1 完成”。该完成确认不授权自动进入 N2.2。

## 2. 产品结果

N2.1 建立可靠文档入库所需的 MySQL 业务事实和上传受理边界：

- 使用 `Document` 表示长期存在的逻辑文档。
- 使用 `DocumentVersion` 表示一次具体文件内容。
- 使用 `ProcessingJob` 表示某个版本的一次处理尝试。
- 使用 `OutboxEvent` 表示需要可靠发布的处理事件。
- 冻结首次上传和上传新版本的管理面 HTTP 契约。
- 在一个数据库事务中创建版本、初始任务和待发布 Outbox 事实。
- 通过稳定 ID、唯一约束、行锁和幂等键防止并发重复业务结果。

N2.1 完成后仍然不能宣称文件已经能够真正上传或处理，也不会产生 `READY` 版本。

## 3. 本阶段范围

### 3.1 实现范围

- 四张表及其字段、索引、唯一约束和字段备注。
- 与四张表一一对应的 Entity、Mapper 和字符串数字代码枚举。
- 文档上传受理的 DTO、VO 和 Service 接口/实现。
- 接收“已经持久化的原文件描述”后创建数据库事实的事务。
- 首次版本和新版本的版本号、并发、幂等及状态行为。
- 正常、异常、越权、重复和并发集成测试。
- 保持现有 `Controller -> Service -> service.impl -> Mapper -> Entity` 分层。

### 3.2 明确不做

- 不引入对象存储 Client、RabbitMQ、Redis、Elasticsearch 或 LangChain4j 依赖。
- 不修改 `compose.yaml` 增加外部服务。
- 不读取或保存真实二进制文件。
- 不发布或消费 RabbitMQ 消息。
- 不解析 PDF、DOCX、TXT 或 Markdown。
- 不生成标准化原文、标题树、DocumentProfile、RetrievalNode 或 Embedding。
- 不建立 Elasticsearch 索引。
- 不把任何版本切换为 `READY`。
- 不提供任务重试、文档删除、版本回滚或手动激活。
- 不提供文档列表、版本历史和处理任务管理的完整管理 API。
- 不实现 `KNOWLEDGE_BASE_ADMIN`。
- 不允许 Application Credential 通过 HTTP 使用 `WRITE` 权限上传文件。

## 4. 为什么 N2.1 不开放成功的文件上传接口

真实对象存储中的原文件保存属于 N2.2。N2.1 如果直接开放一个能够返回成功的二进制上传接口，会出现数据库显示 `PROCESSING`、但原文件没有任何持久保存位置的伪流程。

因此冻结以下边界：

1. N2.1 只冻结外部 HTTP 契约，不注册能够成功接收文件的上传 Controller。
2. N2.1 的事务 Service 只接受完整的、已经持久化的原文件描述，包括 Bucket、Object Key、文件大小和内容 SHA-256。
3. 集成测试使用受控的原文件描述测试数据库事务，不声称对应对象存储对象真实存在。
4. N2.2 接入 S3 兼容对象存储后，先完成原文件持久化，再调用 N2.1 的事务 Service，最后才正式开放上传 Controller。

N2.1 不创建空 Document、不增加 `UPLOAD_PENDING` 占位状态、不把文件写入 MySQL BLOB，也不使用本机临时目录冒充持久对象存储。

## 5. 数据关系

```text
KnowledgeBase
└─ Document
   ├─ activeVersionId
   ├─ latestVersionId
   └─ DocumentVersion
      └─ ProcessingJob
         └─ OutboxEvent
```

- `activeVersionId` 表示当前参与检索的版本，可以为空。
- `latestVersionId` 表示最新受理的版本，不代表该版本已经可检索。
- 首次版本处于 `PROCESSING` 时，`activeVersionId` 为空，`latestVersionId` 指向 v1。
- 新版本处理期间或失败后，已有 `activeVersionId` 保持不变。
- N2.1 只创建 `PROCESSING` 版本、`PENDING` Job 和 `PENDING` Outbox。

## 6. 通用数据库规则

- 主键统一使用 `BIGINT AUTO_INCREMENT`，Java 使用 `Long`。
- 关联 ID 是逻辑外键，不创建物理 `FOREIGN KEY`。
- 不使用数据库 `CHECK` 或级联操作承担业务规则。
- 状态、格式、任务类型和事件类型使用有文档说明的 `VARCHAR` 字符串数字代码。
- 时间使用 MySQL UTC `DATETIME(6)`；VO 返回带 `Z` 的 UTC ISO-8601 时间。
- 每个字段都必须有数据库备注；枚举字段备注列出数字代码含义。
- 所有业务写入通过 Service 事务完成，Mapper SQL 显式携带可信 `tenant_id`。
- 唯一索引承担并发兜底，Service 仍需先给出稳定业务错误。
- 不同租户可以使用相同名称、文件内容、版本号或幂等键。

## 7. `document` 表

### 7.1 职责

`Document` 是知识库中的长期逻辑文档。文件内容更新时创建新版本，不创建无关的新 Document。

### 7.2 字段

| 字段 | 规则 |
| --- | --- |
| `id` | `BIGINT AUTO_INCREMENT` 主键 |
| `tenant_id` | 所属租户逻辑 ID，非空 |
| `knowledge_base_id` | 所属知识库逻辑 ID，非空 |
| `name` | 去除首尾空格后 1–200 个 Unicode 字符 |
| `status` | Document 状态字符串数字代码 |
| `active_version_id` | 当前生效版本逻辑 ID，可空 |
| `latest_version_id` | 最新受理版本逻辑 ID；创建事务提交后非空 |
| `created_by_admin_id` | 创建该文档的租户管理员逻辑 ID |
| `created_at` | 创建时间 |
| `updated_at` | 最后更新时间 |

### 7.3 状态代码

| 代码 | 名称 | 含义 |
| --- | --- | --- |
| `"1"` | `ACTIVE` | 文档正常存在；是否可检索仍由 `active_version_id` 决定 |
| `"2"` | `DELETING` | 已停止参与新检索，正在清理；N2.1 不产生此状态 |
| `"3"` | `DELETED` | 清理完成；N2.1 不产生此状态 |

### 7.4 约束和索引

- `(tenant_id, knowledge_base_id, name)` 使用 `utf8mb4_0900_as_cs` 大小写敏感唯一。
- 名称唯一性不包含状态；删除后的名称仍被原逻辑文档保留，不能创建另一个同名 Document。
- 建立 `(tenant_id, knowledge_base_id, status, id)` 查询索引。
- `active_version_id` 和 `latest_version_id` 只允许指向同一 Document、同一 Tenant 的版本，由 Service 和集成测试保证。

## 8. `document_version` 表

### 8.1 职责

`DocumentVersion` 表示某次上传的确定文件内容。内容哈希只用于完整性、幂等和重复内容判断，不替代稳定资源 ID。

### 8.2 字段

| 字段 | 规则 |
| --- | --- |
| `id` | `BIGINT AUTO_INCREMENT` 主键 |
| `tenant_id` | 所属租户逻辑 ID，非空 |
| `document_id` | 所属 Document 逻辑 ID，非空 |
| `version_no` | 从 1 开始的单文档递增版本号 |
| `status` | 版本状态字符串数字代码 |
| `source_format` | 原文件格式字符串数字代码 |
| `original_filename` | 原始文件名，保存展示值，不作为文档身份 |
| `source_bucket` | 对象存储 Bucket；N2.1 事务入参必须提供 |
| `source_object_key` | 持久对象 Key；消息中不传预签名 URL |
| `source_size_bytes` | 原文件字节数，必须大于 0 |
| `source_sha256` | 小写 64 位十六进制 SHA-256 |
| `source_content_type` | 客户端或存储记录的 Content-Type，仅作元数据，不单独决定文件格式 |
| `idempotency_key_hash` | 管理面幂等键的 SHA-256，不保存原始键 |
| `request_fingerprint` | 规范化请求内容的 SHA-256 |
| `accepted_by_admin_id` | 受理上传的租户管理员逻辑 ID |
| `failure_code` | 稳定失败分类，可空 |
| `failure_message` | 面向管理员的脱敏失败摘要，可空；不保存堆栈 |
| `ready_at` | 进入 READY 的时间，可空；N2.1 不写入 |
| `failed_at` | 进入 FAILED 的时间，可空；N2.1 不写入 |
| `created_at` | 上传受理时间，也是响应中的 `acceptedAt` |
| `updated_at` | 最后更新时间 |

### 8.3 状态代码

| 代码 | 名称 | 含义 |
| --- | --- | --- |
| `"1"` | `PROCESSING` | 已受理但尚未完成全部投影，不能单独证明可检索 |
| `"2"` | `READY` | 处理和投影校验完成；是否参与查询还必须匹配 `active_version_id` |
| `"3"` | `FAILED` | 处理失败，不参与检索 |

### 8.4 文件格式代码

| 代码 | 格式 |
| --- | --- |
| `"1"` | `PDF` |
| `"2"` | `DOCX` |
| `"3"` | `TXT` |
| `"4"` | `MARKDOWN` |

### 8.5 约束和索引

- `(document_id, version_no)` 唯一。
- `(tenant_id, idempotency_key_hash)` 唯一。
- `(source_bucket, source_object_key)` 唯一，禁止多个版本引用同一个上传对象。
- 建立 `(tenant_id, document_id, status, version_no)` 索引。
- 创建新版本前锁定 Document 行，读取最新版本并分配下一个版本号。
- MySQL 没有使用部分唯一索引；“最多一个处理中版本”由 Document 行锁、Service 状态检查和并发测试保证。

## 9. `processing_job` 表

### 9.1 职责

一个 `ProcessingJob` 表示某个版本的一次处理尝试。重试不覆盖原 Job，而是以递增 `attempt_no` 创建新 Job；N2.1 只创建首次尝试。

### 9.2 字段

| 字段 | 规则 |
| --- | --- |
| `id` | `BIGINT AUTO_INCREMENT` 主键 |
| `tenant_id` | 所属租户逻辑 ID |
| `document_version_id` | 所属版本逻辑 ID |
| `job_type` | 任务类型字符串数字代码 |
| `attempt_no` | 从 1 开始的处理尝试号 |
| `status` | Job 状态字符串数字代码 |
| `failure_code` | 稳定失败分类，可空 |
| `failure_message` | 脱敏失败摘要，可空 |
| `started_at` | 开始处理时间，可空 |
| `finished_at` | 成功或失败结束时间，可空 |
| `created_at` | 创建时间 |
| `updated_at` | 最后更新时间 |

### 9.3 类型和状态代码

- Job 类型：`"1" = INGEST`。
- Job 状态：`"1" = PENDING`、`"2" = RUNNING`、`"3" = SUCCEEDED`、`"4" = FAILED`。

### 9.4 约束和索引

- `(document_version_id, attempt_no)` 唯一。
- 建立 `(tenant_id, status, updated_at, id)` 任务查询索引。
- 一个版本任意时刻最多有一个非终态 Job，由版本行锁和 Service 规则保证。
- Job 成功不自动等于版本 READY；N2.5 还必须完成双索引投影校验和 `active_version_id` 切换。

## 10. `outbox_event` 表

### 10.1 职责

`OutboxEvent` 保存已经随业务事实提交、但尚未可靠发布的处理事件。它解决 MySQL 事务和 RabbitMQ 发布不能原子提交的问题，不保证消息只投递一次。

### 10.2 字段

| 字段 | 规则 |
| --- | --- |
| `id` | `BIGINT AUTO_INCREMENT` 主键，同时作为稳定 `eventId` |
| `tenant_id` | 所属租户逻辑 ID |
| `document_version_id` | 目标版本逻辑 ID |
| `processing_job_id` | 目标处理 Job 逻辑 ID |
| `event_type` | 事件类型字符串数字代码 |
| `payload` | JSON，只保存稳定 ID 和必要关联信息 |
| `status` | Outbox 状态字符串数字代码 |
| `attempt_count` | 发布尝试次数，初始为 0 |
| `available_at` | 下一次允许发布的时间 |
| `locked_by` | Publisher 租约持有者，可空 |
| `locked_until` | Publisher 租约到期时间，可空 |
| `last_error_code` | 最近发布失败分类，可空 |
| `last_error_message` | 最近发布失败脱敏摘要，可空 |
| `sent_at` | RabbitMQ Confirm 成功时间，可空 |
| `created_at` | 创建时间 |
| `updated_at` | 最后更新时间 |

### 10.3 类型和状态代码

- 事件类型：`"1" = DOCUMENT_VERSION_PROCESS_REQUESTED`。
- Outbox 状态：`"1" = PENDING`、`"2" = PUBLISHING`、`"3" = SENT`。
- 发布失败时回到 `PENDING` 并更新 `attempt_count`、`available_at` 和错误摘要；N2.2 再冻结具体退避参数。

### 10.4 Payload 边界

Payload 至少包含：

- `tenantId`
- `knowledgeBaseId`
- `documentId`
- `documentVersionId`
- `processingJobId`

Publisher 发布时使用 Outbox 主键作为 `eventId`。Payload 和 MQ 消息禁止包含：

- 文件正文
- Application Secret 或管理员身份秘密
- `Authorization` Header
- 对象存储预签名 URL
- 模型密钥

### 10.5 约束和索引

- `(event_type, processing_job_id)` 唯一。
- 建立 `(status, available_at, locked_until, id)` Publisher 扫描索引。
- N2.1 只创建 `PENDING` 事件，不实现 Publisher。

## 11. 上传受理权限

- 只接受已登录、状态有效且所属 Tenant 为 ACTIVE 的 `TENANT_ADMIN`。
- `PLATFORM_ADMIN` 不自动拥有租户内部文档管理权限。
- 路径 `tenantId` 必须与 `AdminPrincipal` 中的可信租户一致，否则返回 `403 TENANT_SCOPE_FORBIDDEN`。
- KnowledgeBase 必须属于同一 Tenant 且状态为 ACTIVE。
- 路径属于当前租户、但 KnowledgeBase 或 Document ID 实际属于其他租户时返回 `404`，隐藏资源存在性。
- 管理面修改请求继续要求正确的 CSRF Token。
- N2.1 不实现 `KNOWLEDGE_BASE_ADMIN` 与知识库绑定关系。
- N2.1 不开放 Application Credential 的 HTTP `WRITE` 上传入口。

## 12. 管理面 HTTP 契约

以下契约在 N2.1 冻结，但只有 N2.2 完成原文件持久化后才注册成功路由。

### 12.1 首次上传

```text
POST /api/admin/v1/tenants/{tenantId}/knowledge-bases/{knowledgeBaseId}/documents
Content-Type: multipart/form-data
Idempotency-Key: <opaque-key>
X-CSRF-TOKEN: <登录后的 token>
```

Parts：

```text
metadata: application/json
{"documentName":"S1设备维修手册"}

file: 原始二进制文件
```

- `documentName` 去除首尾空格后为 1–200 个 Unicode 字符。
- 文件原始名称单独保存在 `DocumentVersion`，不能替代 Document 名称。
- 首次上传原子创建 Document、v1、attempt 1 Job 和 Outbox。

### 12.2 上传新版本

```text
POST /api/admin/v1/tenants/{tenantId}/knowledge-bases/{knowledgeBaseId}/documents/{documentId}/versions
Content-Type: multipart/form-data
Idempotency-Key: <opaque-key>
X-CSRF-TOKEN: <登录后的 token>
```

Parts：

```text
file: 原始二进制文件
```

- 通过路径中的稳定 `documentId` 选择逻辑文档，不按原文件名或 Document 名称猜测。
- 上传新版本不修改 Document 名称。
- 新版本成功受理后只更新 `latest_version_id`，不修改 `active_version_id`。

### 12.3 成功响应

原文件已经持久化、数据库事务已经提交后返回：

```text
202 Accepted
```

```json
{
  "documentId": 101,
  "documentVersionId": 201,
  "versionNo": 1,
  "processingJobId": 301,
  "documentStatus": "1",
  "versionStatus": "1",
  "jobStatus": "1",
  "acceptedAt": "2026-08-02T10:00:00Z"
}
```

- 不返回 `outboxEventId`、Bucket、Object Key、内容哈希或内部错误信息。
- 幂等重放返回相同业务 ID，不创建新记录；状态字段返回这些资源在重放时的当前状态。

## 13. 文件受理校验边界

N2.1 冻结以下外部行为，实际二进制校验在 N2.2 接入 S3 兼容对象存储时落地：

- 文件不能为空。
- 原文件名必须存在且不能包含路径穿越语义。
- 仅接受 PDF、DOCX、TXT、Markdown 对应的允许扩展名和基础格式声明。
- 不只信任客户端 `Content-Type`。
- 上传大小必须小于等于可配置上限；超过返回 `413 FILE_TOO_LARGE`。
- 具体默认大小上限不在 N2.1 凭空指定，在 N2.2 存储基线测试后单独确认。
- 扫描 PDF、损坏文档、文本编码和深层格式合法性由 N2.3 解析阶段判断；上传受理成功不代表文件一定能够解析。

## 14. 幂等规则

### 14.1 Key 范围

- 两个上传接口都必须提供非空 `Idempotency-Key`。
- 原始 Key 不写入数据库和日志，只保存 SHA-256。
- 唯一范围为当前可信 `tenantId`；同一 Key 不能在同一 Tenant 内用于另一上传请求。

### 14.2 请求指纹

请求指纹至少覆盖以下规范化内容：

- 操作类型：首次上传或新版本。
- `tenantId`、`knowledgeBaseId`。
- 首次上传的规范化 Document 名称，或新版本的 `documentId`。
- 原始文件名。
- 文件格式和字节数。
- 文件内容 SHA-256。

### 14.3 行为

- 相同 Tenant、相同 Key、相同指纹：返回原有 Document、Version 和 Job ID，不新增记录。
- 相同 Tenant、相同 Key、不同指纹：返回 `409 IDEMPOTENCY_CONFLICT`。
- 两个并发相同请求都可能在 N2.2 暂时写入各自对象，但数据库唯一约束只允许一组业务记录；失败方必须清理自己产生的孤立对象。
- 不同 Tenant 可以复用同一个 Key。
- Redis 不参与上传幂等或文档处理正确性。

## 15. 版本和重复上传行为

### 15.1 首次上传

同一事务中：

1. 创建 `ACTIVE` Document。
2. 创建 v1 `PROCESSING` Version。
3. 创建 attempt 1、`PENDING` Job。
4. 创建 `PENDING` Outbox。
5. 将 `latest_version_id` 指向 v1，`active_version_id` 保持为空。

### 15.2 新版本

- 使用 `SELECT ... FOR UPDATE` 锁定当前 Tenant 下的 Document。
- 如果最新版本仍是 `PROCESSING`，返回 `409 DOCUMENT_VERSION_IN_PROGRESS`。
- 如果上传内容与当前 activeVersion 或 latestVersion 完全相同，不能创建无意义的新版本。
- 如果最新版本为 FAILED 且内容相同，返回 `409 FAILED_VERSION_RETRY_REQUIRED`，后续应重试原失败版本。
- 如果最新版本为 FAILED 且新内容不同，可以创建下一个版本。
- 新版本受理后更新 `latest_version_id`，已有 `active_version_id` 保持不变。
- 一旦创建了更高版本，较早 FAILED 版本不能再通过重试成为 activeVersion。

### 15.3 重复内容

- 同 Key、同请求属于幂等重放，不报错。
- 不同 Key 但内容与当前 activeVersion 或 latestVersion 相同，返回 `409 DOCUMENT_CONTENT_UNCHANGED`。
- 内容相同不构成跨 Document 或跨 Tenant 去重；内容哈希不能替代稳定资源 ID。

## 16. 事务边界

N2.1 的数据库受理事务必须完成：

```text
复查可信管理员、Tenant 和 KnowledgeBase
→ 处理幂等重放或冲突
→ 锁定或创建 Document
→ 校验并发版本和重复内容
→ 创建 DocumentVersion
→ 创建 ProcessingJob
→ 创建 OutboxEvent
→ 更新 Document.latestVersionId
→ 提交
```

- 首次上传创建 Document 时，允许在事务内先插入 `latest_version_id = null`，创建 v1 后再回写；事务提交后不允许留下没有 latestVersion 的 Document。
- 任一步失败时 Document、Version、Job、Outbox 和指针更新必须全部回滚。
- N2.2 的完整外部顺序是“先持久化原文件，再执行上述数据库事务”。
- 对象存储写入失败时不能创建数据库记录。
- 数据库事务失败时不能返回成功；N2.2 对本次新对象进行限定目标、可恢复的清理。

## 17. 错误契约

错误响应继续使用稳定 `code` 和 `message`，不返回堆栈、SQL、对象存储凭证、文件正文或哈希。

| HTTP | 错误码 | 场景 |
| --- | --- | --- |
| `400` | `VALIDATION_FAILED` | Document 名称、幂等键或请求结构不合法 |
| `400` | `FILE_EMPTY` | 文件为空 |
| `401` | `UNAUTHENTICATED` | 管理员 Session 无效 |
| `403` | `TENANT_SCOPE_FORBIDDEN` | 管理员访问其他 Tenant 路径 |
| `403` | `ACCESS_DENIED` | CSRF 失败或角色无权操作 |
| `404` | `KNOWLEDGE_BASE_NOT_FOUND` | KnowledgeBase 不存在、停用或不属于当前 Tenant |
| `404` | `DOCUMENT_NOT_FOUND` | Document 不存在或不属于路径中的 Tenant/KnowledgeBase |
| `409` | `DOCUMENT_NAME_CONFLICT` | 同一 KnowledgeBase 已有大小写精确相同的 Document 名称 |
| `409` | `DOCUMENT_VERSION_IN_PROGRESS` | 已有非终态候选版本 |
| `409` | `IDEMPOTENCY_CONFLICT` | 相同 Key 对应不同请求指纹 |
| `409` | `DOCUMENT_CONTENT_UNCHANGED` | 不同 Key 上传与 active/latest 相同的内容 |
| `409` | `FAILED_VERSION_RETRY_REQUIRED` | 与最新 FAILED 版本内容相同，应重试原版本 |
| `413` | `FILE_TOO_LARGE` | 超过配置的上传大小上限 |
| `415` | `UNSUPPORTED_DOCUMENT_FORMAT` | 不属于首批支持格式 |
| `503` | `OBJECT_STORAGE_UNAVAILABLE` | N2.2 中对象存储无法可靠保存原文件，数据库不得受理 |

KnowledgeBase 停用对租户管理员返回 `KNOWLEDGE_BASE_NOT_FOUND`，与 N1 已有租户内资源存在性隐藏方式保持一致。

## 19. 验收测试

### 19.1 迁移和结构

- 空库依次执行 V1、V2、V3 和 N2.1 新迁移。
- 四表、字段类型、字段备注、枚举备注、索引和唯一约束与本文档一致。

- 不存在物理外键、`CHECK` 或数据库级联。
- 已发布的 V1、V2、V3 不被修改。

### 19.2 正常事务

- 首次受理原子创建 Document、v1、Job 和 Outbox。
- 首次受理后 Document 为 ACTIVE、v1 为 PROCESSING、Job 和 Outbox 为 PENDING。
- 首次受理后 `latest_version_id = v1`、`active_version_id = null`。
- 有 READY activeVersion 的文档受理新版本时，activeVersion 不改变，latestVersion 指向新版本。
- Outbox payload 只包含规定的稳定 ID。

### 19.3 回滚

- 创建 Version、Job、Outbox 或更新 latestVersion 任一步失败时全部业务写入回滚。
- 不留下没有 latestVersion 的 Document。
- 不留下孤立 Job 或 Outbox。

### 19.4 租户和权限

- 只有所属 Tenant 的 TENANT_ADMIN 可以受理。
- PLATFORM_ADMIN、其他 Tenant 管理员和应用身份被拒绝。
- 路径 Tenant 不匹配返回 403。
- 跨 Tenant KnowledgeBase 和 Document 返回 404，且数据库无写入。
- Tenant 或 KnowledgeBase 停用后不能受理。

### 19.5 幂等和并发

- 相同 Key、相同指纹的顺序重放返回相同业务 ID。
- 相同 Key、相同指纹的并发请求只产生一组 Document/Version/Job/Outbox。
- 相同 Key、不同指纹返回 409 且不增加业务记录。
- 并发首次创建同名 Document 只有一个成功，另一请求得到稳定名称冲突。
- 并发创建新版本时最多一个请求创建新版本，版本号不重复。

### 19.6 生命周期

- 最新版本 PROCESSING 时拒绝继续上传新版本。
- 新版本 PROCESSING 或 FAILED 时旧 activeVersion 保持不变。
- 首次版本 FAILED 时仍然没有 activeVersion。
- 与 active/latest 内容相同的新请求不创建版本。
- 与最新 FAILED 版本内容相同的请求得到重试提示。
- FAILED 后上传不同内容可以创建下一个版本。

### 19.7 安全和回归

- VO 和错误响应不泄露 Bucket、Object Key、SHA-256、幂等键、Outbox ID 或内部异常。
- 日志不记录原始幂等键、文件正文或敏感凭证。
- Testcontainers 使用临时 MySQL 8.4.10，不连接本机 MySQL 或 Compose 持久化数据库。
- 现有 N1 36 项测试全部继续通过。
