## 1. 产品结果

本子阶段回答两个问题：RAGFlow DeepDoc 能否在不调用付费供应商的前提下，为 DocQuery 当前拒绝的真实复杂 PDF 提供可定位、可标准化的文本块；同一批文档使用 GPU 是否能显著降低耗时。

P0 不直接替换生产解析器。验证通过后，才单独冻结 Java 到文档解析容器的正式 HTTP 契约、生命周期接入和 100 份 PDF 准入目标。

## 2. 冻结范围

- 使用 RAGFlow 稳定版本 `v0.26.4`，镜像为 `infiniflow/ragflow:v0.26.4`。
- 只启动一个一次性文档解析容器；不启动 RAGFlow 的 MySQL、Elasticsearch、MinIO、Redis、Web 或任务服务。
- 第一轮使用 CPU：不声明 GPU 设备，设置 `DEVICE=cpu` 和空的 `CUDA_VISIBLE_DEVICES`。
- 用户随后明确要求使用 GPU 解析相同两份文档做速度对照。GPU 使用 RTX 4060 Ti、PyTorch `2.13.0+cu126` 和 ONNX CUDA provider，CPU/GPU 分别写入独立报告。
- 官方基础镜像缺少 PyTorch 和 CUDA 12 用户态库，直接设置 `DEVICE=gpu` 会安装失败并静默回落 CPU。为避免假 GPU，使用固定 Dockerfile 构建派生镜像，并要求解析前必须在实际 ONNX session 中发现 `CUDAExecutionProvider`，否则立即失败。
- 容器禁用网络；模型必须来自固定镜像，缺失时显式失败，不在运行时漂移下载。
- 使用 DeepDoc `PdfParser.parse_into_bboxes` 完整解析固定原始 PDF。原计划为 10 份；第 1 份完成后，用户明确将本次范围缩减为原固定顺序的前 2 份，因此第 2 份完成后立即停止，不再处理后续 8 份。
- 输出块数量、版面类型、页码/矩形位置、证据页覆盖、耗时和进程内存；报告不保存正文。
- 原始 PDF 只读挂载，结果只写入 `evaluation/mmlongbench-docquery-v1/reports/`。
- CPU/GPU 服务已统一放入项目根 `compose.yaml`，分别使用 `deepdoc-p0-cpu` 和 `deepdoc-p0-gpu` profile；默认 `docker compose up` 不会启动它们。原独立 P0 Compose 文件已移除，runner 和 GPU Dockerfile 仍集中在 `tools/document-parser-p0/`。

最初固定顺序保存在 `deepdoc-p0-sample-v1`。用户缩减数量后，最终复现样本为 `deepdoc-p0-sample-v2`，严格取原顺序前 2 份，没有按结果换文档：

| 文件 | 页数 | 生产解析基线 | 代表内容 |

| `BESTBUY_2023_10K.pdf` | 75 | `PDF_COMPLEX_LAYOUT_UNSUPPORTED` | 财务年报 |
| `2312.09390v1.pdf` | 49 | `PDF_COMPLEX_LAYOUT_UNSUPPORTED` | 学术论文 |

## 4. 输出契约

P0 报告使用 `docquery-deepdoc-p0-report-v1`：

- `engine`：RAGFlow 版本、镜像、设备和网络边界；
- `modelInitializationMillis`：模型初始化耗时；
- `runtime`：PyTorch/CUDA 状态和实际 ONNX session provider；
- `results[]`：文件指纹、页数、非空块数、版面类型计数、含文本页、证据页覆盖、耗时、内存和稳定错误；
- `summary`：成功数、失败数、原本受控失败文档的恢复数、证据页覆盖和延迟汇总；
- 不保存完整正文、图片、表格截图或上游二进制。

P0 输出只是解析可行性证据，不是 `canonical.jsonl` v2，也不能直接进入 N5.2。

## 5. 失败处理

- 文件大小或 SHA-256 不匹配：`SOURCE_INTEGRITY_MISMATCH`，不调用解析器；
- DeepDoc 初始化失败：报告初始化错误并停止，不能回退到 PDFBox 后伪装成功；
- 单文档解析异常：记录异常类型和脱敏摘要，继续后续固定样本；
- 没有非空文本块：`NO_NONBLANK_BLOCKS`；
- 有文本但缺少官方证据页：保留 `PARSED`，同时明确 `evidenceCoverageComplete=false`；
- 容器 OOM、非计划终止或环境不可用：保持未完成报告，不声称通过；
- 本次原始报告在第 2 份结果原子落盘后按用户范围主动停止，所以 `completed=false` 且 Compose 退出码为 137；Docker 最终状态明确为 `OOMKilled=false`、`RestartCount=0`，该退出码不计为解析失败。

## 6. P0 验收点

- 官方固定镜像能够在单个 CPU-only 容器中初始化，Docker 未请求或挂载 GPU；
- 固定派生镜像能够在 GPU 容器中初始化，且版面、表格、OCR 检测和 OCR 识别 session 均实际包含 `CUDAExecutionProvider`；
- 最终固定 2 份原始 PDF 均得到成功结果或稳定失败记录；
- 两份原本被生产解析器以 `PDF_COMPLEX_LAYOUT_UNSUPPORTED` 拒绝的 PDF，均应得到非空且带页码/矩形位置的块；
- 对具有官方证据页的成功文档，分别报告证据页是否存在非空块，不用“整份有文字”代替；
- 报告包含 CPU/GPU 条件下的逐文档耗时、内存、设备和 provider 证据；
- 不调用 DeepSeek、百炼 Embedding、VLM、MinerU SaaS 或其他付费服务；
- 不修改现有 Java 解析器、数据库迁移、入库状态机和公开 API；根 Compose 只新增默认关闭的 P0 profiles。

## 7. 明确非目标

- 不在 P0 完成 Java HTTP Adapter 或生产回退策略；
- 不把 RAGFlow 整套知识库产品嵌入 DocQuery；
- 不验证 DOCX、Excel、PPT、图片等其他格式的正式质量；
- 不做表格问答、图片语义、公式语义或官方 MMLongBench-Doc 榜单；
- 不运行真实 Chat/Embedding 质量、成本或端到端延迟评测；
- 不开始 N5.2、多轮 Conversation、会话记忆或流式 Answer。

## 10. 结论边界

P0 已证明：DeepDoc 能在单个断网 CPU 容器中，将两份当前生产解析器拒绝的复杂文本型 PDF 恢复为带页位置的非空版面块，并覆盖官方证据页。因此，继续设计独立解析服务的技术路线具有可行性。

P0 同时证明 CPU 代价不可忽略：两份共 124 页耗时约 18 分钟；GPU 将累计解析耗时降低到约 2.64 分钟，速度优势明确，但需要约 6.68 GiB 的本地派生镜像、CUDA 运行环境和额外 GPU 资源。P0 没有验证扫描件 OCR、DOCX/Excel/PPT、100 份总体成功率、表格/图片语义质量，也没有替换 DocQuery 生产解析器。生产接入仍需单独冻结范围和开始授权。
