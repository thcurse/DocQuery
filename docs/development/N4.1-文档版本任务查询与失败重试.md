# DocQuery N4.1 文档、版本、任务查询与失败重试

> 状态：已实现、验证并经用户验收  
> 前置阶段：N0—N3.4 已完成并经用户验收，N3 已关闭  
> 本阶段门禁：用户已于 2026-08-12 明确说“确认开始 N4.1”
> 完成门禁：用户已于 2026-08-12 明确说“确认 N4.1 完成”

## 1. 阶段目标

N4.1 补齐管理后台所需的文档、版本和处理任务只读契约，并允许租户管理员对符合条件的最终失败入库任务发起一次新的人工处理尝试。

本阶段必须让管理员明确区分：

- `activeVersion`：当前实际参与服务面检索的版本；
- `latestVersion`：最近受理或正在重试的版本；
- RabbitMQ 自动重试：同一个 `ProcessingJob.attemptNo` 内的技术重试；
- 管理员人工重试：为同一个 `DocumentVersion` 创建新的 `ProcessingJob.attemptNo`。

人工重试成功前，已有 `activeVersionId` 保持不变；再次失败也不能影响旧版本服务。

## 2. 本阶段明确不做

- 不实现文档删除或 Elasticsearch、对象存储物理清理；
- 不实现应用、知识库物理删除；
- 不新增知识库管理员角色，仍使用 `PLATFORM_ADMIN` 与 `TENANT_ADMIN`；
- 不实现管理操作审计；
- 不实现管理后台前端、概览指标或 Demo；
- 不改变 `/retrieve`、`/answer`、查询审计和评测契约；
- 不使用 Redis 保存管理请求幂等；人工重试幂等以 MySQL 事实为准。

## 3. 权限边界

- 管理接口只允许当前租户的 `TENANT_ADMIN` 访问；
- `PLATFORM_ADMIN` 不自动获得租户内部文档管理权；
- Application Credential 不能访问管理接口；
- 路径中的 `tenantId` 必须与 Session 中可信租户一致；
- 跨租户路径返回 `TENANT_SCOPE_FORBIDDEN`，其他租户的具体资源按不存在处理；
- 停用的 KnowledgeBase 允许读取历史事实，但禁止提交人工重试；
- 停用 Tenant 的既有管理 Session 按现有规则立即失效。

## 4. HTTP 契约

### 4.1 文档和版本

```http
GET /api/admin/v1/tenants/{tenantId}/knowledge-bases/{knowledgeBaseId}/documents
GET /api/admin/v1/tenants/{tenantId}/knowledge-bases/{knowledgeBaseId}/documents/{documentId}
GET /api/admin/v1/tenants/{tenantId}/knowledge-bases/{knowledgeBaseId}/documents/{documentId}/versions
```

文档列表支持：

- `name`：文档名大小写敏感包含查询；
- `documentStatus`：`DocumentStatus` 字符串数字代码；
- `latestVersionStatus`：`DocumentVersionStatus` 字符串数字代码；
- `page`、`size`：从 0 开始，`size` 范围为 1—100；
- 固定排序：`updatedAt DESC, id DESC`。

版本历史使用 `page`、`size`，固定按 `versionNo DESC, id DESC` 排序。

文档响应同时返回 `activeVersion` 与 `latestVersion`。版本响应包含格式、原始文件名、大小、状态、是否生效、脱敏失败摘要、失败是否可人工重试、时间和最近一次 ProcessingJob；不返回 Bucket、Object Key、原文件摘要、幂等键摘要或请求指纹。

### 4.2 处理任务

```http
GET /api/admin/v1/tenants/{tenantId}/processing-jobs
GET /api/admin/v1/tenants/{tenantId}/processing-jobs/{processingJobId}
```

任务列表支持：

- `knowledgeBaseId`、`documentId`、`documentVersionId`；
- `status`：`ProcessingJobStatus` 字符串数字代码；
- `from`、`to`：按任务创建时间过滤，`from` 包含、`to` 不包含；
- `page`、`size`；
- 固定排序：`updatedAt DESC, id DESC`。

任务详情返回选中尝试及同一版本的全部 attempt 历史。面向管理员只返回稳定失败码、脱敏摘要和可重试标记，不返回 Lease、堆栈、供应商原始响应或文件正文。

### 4.3 人工重试

```http
POST /api/admin/v1/tenants/{tenantId}/processing-jobs/{processingJobId}/retry
Idempotency-Key: 1—128 个可见 ASCII 字符
```

成功返回 `202 Accepted`，包含：

- 原失败 `processingJobId`；
- `documentId`、`documentVersionId`；
- 新 `processingJobId` 和 `attemptNo`；
- 当前版本和任务状态；
- `replayed`；
- UTC 受理时间。

同一租户、相同 Key、相同重试命令返回第一次创建的 attempt，并令 `replayed=true`；相同 Key 绑定不同命令返回 `IDEMPOTENCY_KEY_REUSED`。

## 5. 人工重试状态规则

只有同时满足以下条件才允许重试：

1. 指定任务存在于当前租户且状态为 `FAILED`；
2. 指定任务是该版本最近一次 attempt，旧 attempt 不能绕过最新失败结论；
3. 最近失败被明确持久化为 `failureRetryable=true`；
4. 目标版本状态为 `FAILED`；
5. 目标版本仍等于 Document 的 `latestVersionId`；
6. Document 状态为 `ACTIVE`；
7. Tenant 与 KnowledgeBase 均为启用状态；
8. 该版本不存在 `PENDING` 或 `RUNNING` 的任务。

受理事务按 KnowledgeBase、Document、DocumentVersion、源 ProcessingJob 的稳定顺序锁定并复核事实，然后原子执行：

```text
DocumentVersion FAILED -> PROCESSING，清除版本失败字段
→ 创建 ProcessingJob(attemptNo=max+1, PENDING)
→ 创建 DOCUMENT_VERSION_PROCESS_REQUESTED OutboxEvent
→ 提交
```

不创建新 Document 或 DocumentVersion，不修改 `Document.activeVersionId`。后续继续复用已经验收的 canonical、retrieval 和投影幂等链路。

## 6. 数据模型

V10 只扩展 `processing_job`：

- `failure_retryable`：最终失败是否允许人工重试；非失败状态为空；
- `idempotency_key_hash`：人工重试幂等键 SHA-256；初始任务为空；
- `request_fingerprint`：绑定租户和源任务的稳定命令指纹；初始任务为空；
- 唯一约束 `(tenant_id, idempotency_key_hash)`；MySQL 允许多个 `NULL`，因此不影响初始任务；
- 增加文档、版本和任务管理列表所需的稳定分页索引。

迁移前已经处于 `FAILED` 的任务没有可靠的原始 retryable 事实，统一回填为 `false`，按 fail-closed 处理。

Consumer 最终标记失败时同时保存 `DocumentProcessingException.retryable`。自动重试耗尽仍保存 `true`，允许管理员在依赖恢复后提交新的人工 attempt；确定性失败保存 `false`。

## 7. 稳定错误

| HTTP | 错误码 | 含义 |
| --- | --- | --- |
| 400 | `VALIDATION_FAILED` | ID、分页、筛选、时间范围或 Idempotency-Key 非法 |
| 403 | `TENANT_SCOPE_FORBIDDEN` | Session 不属于路径租户 |
| 404 | `KNOWLEDGE_BASE_NOT_FOUND` | 当前租户内知识库不存在 |
| 404 | `DOCUMENT_NOT_FOUND` | 当前知识库内文档不存在 |
| 404 | `PROCESSING_JOB_NOT_FOUND` | 当前租户内任务不存在 |
| 409 | `PROCESSING_JOB_NOT_FAILED` | 任务不是最终失败状态 |
| 409 | `PROCESSING_JOB_SUPERSEDED` | 指定任务不是该版本最近一次 attempt |
| 409 | `PROCESSING_JOB_NOT_RETRYABLE` | 最近失败明确不可人工重试 |
| 409 | `DOCUMENT_VERSION_SUPERSEDED` | 失败版本已经不是 latestVersion |
| 409 | `RETRY_ALREADY_IN_PROGRESS` | 该版本已有 PENDING/RUNNING attempt |
| 409 | `KNOWLEDGE_BASE_NOT_ACTIVE` | 知识库已停用 |
| 409 | `DOCUMENT_NOT_ACTIVE` | 文档不处于 ACTIVE |
| 409 | `IDEMPOTENCY_KEY_REUSED` | Key 已绑定其他重试命令 |

## 8. 验收点

1. 文档列表和详情能够同时展示 active v1 与 latest v2 的 PROCESSING/FAILED 差异；
2. 版本历史按版本倒序，且响应不泄露对象位置、摘要和幂等内部字段；
3. 任务列表、详情和 attempt 历史支持稳定分页与筛选；
4. 人工重试在一个 MySQL 事务中创建新 attempt、重置同一版本并写 Outbox；
5. 重试成功前旧 activeVersion 不变，再次失败时旧版本继续服务；
6. 相同 Idempotency-Key 重放返回同一新任务，不同命令冲突；
7. 并发重试最多创建一个新 attempt；
8. 不可重试失败、旧 attempt、旧版本、活跃任务、停用知识库和非 ACTIVE 文档均被拒绝；
9. Tenant 隔离、平台管理员拒绝和 Application Credential 管理面拒绝成立；
10. 真实 MySQL、SeaweedFS、RabbitMQ、Elasticsearch + Fake Gateway 完成“失败 → 人工重试 → READY”端到端；
11. 默认完整回归不访问真实供应商并保持通过。

## 9. 实施与验证结果

- 已实现文档列表、文档详情、版本历史、任务列表、任务详情和人工重试共 6 个管理面路由；只允许当前租户的 `TENANT_ADMIN` 使用。
- V10 已持久化最终失败的 `failure_retryable`、人工重试幂等摘要和命令指纹，并增加稳定分页索引；未使用物理外键或 `CHECK`。
- 人工重试在同一 MySQL 事务内锁定并复核事实，原子重置原版本、创建递增 attempt 和 Outbox；不改变旧 `activeVersionId`。
- 管理契约、并发、幂等、跨租户、停用状态及失败边界相关 4 个集成套件共 20/20 通过。
- 真实 MySQL 8.4.10、SeaweedFS 4.40、RabbitMQ 4.3.4、Elasticsearch 9.4.4 + Fake Gateway 已完成“旧版本继续服务 → 新版本失败 → 人工重试 → READY → 原子切换”端到端验证。
- N4.1 当时执行的 `./mvnw.cmd verify` 所有有效测试均通过，其中 Failsafe 90/90。其后曾把未清理报告目录中的一个 7 项旧 Surefire XML 一并汇总，因而误记为 32 个套件、137 项；2026-08-12 的 `clean verify` 已确认 N4.1 有效基线应为 31 个套件、130 项：128 项执行通过、2 项真实供应商冒烟按设计跳过、0 failure、0 error。该更正只修正报告统计，不代表测试文件丢失或 N4.1 行为回退。
- 全量负载暴露的三个既有对象孤儿回收测试已改为先等待对象明确进入 `lastModified < cutoff` 的清理窗口，不放宽生产 fail-closed 回收规则。
- 未修改 `pom.xml` 或 `compose.yaml`；未连接 Compose 持久数据，未调用真实 Chat/Embedding 供应商。
