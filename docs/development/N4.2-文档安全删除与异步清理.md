# DocQuery N4.2 文档安全删除与异步清理

> 状态：已实现、验证并经用户验收  
> 前置阶段：N0—N4.1 已实现、验证并经用户验收  
> 本阶段门禁：用户已于 2026-08-12 明确说“确认开始 N4.2”

## 1. 阶段目标

N4.2 为租户管理员提供整个逻辑 Document 的不可恢复删除能力。删除受理事务提交后，该 Document 必须立即退出新查询的 activeVersion 快照；Elasticsearch 投影、canonical/retrieval 派生对象和原文件随后通过可靠异步任务最终清理。

外部生命周期固定为：

```text
ACTIVE
  → 删除受理事务：DELETING + activeVersionId=null + DeletionJob + Outbox
DELETING
  → 全部外部内容清理并提交终态：DELETED
```

删除失败只能让 Document 保持 `DELETING`，不能重新变为 `ACTIVE` 或重新参与检索。

## 2. 本阶段明确不做

- 不删除单个历史版本或失败版本；一次命令删除整个逻辑 Document 及其全部版本内容；
- 不支持恢复、撤销删除、手工激活或版本回滚；
- 不强制取消正在 `PENDING` 或 `RUNNING` 的入库任务；此时拒绝删除；
- 不删除 Application、KnowledgeBase、查询审计、Document/Version/ProcessingJob 历史事实；
- 不建设通用管理操作审计；删除任务自身保存可信发起管理员和时间；
- 不实现管理后台前端；
- 不改变 `/retrieve`、`/answer` 的请求或响应结构；
- 不新增基础设施容器，不修改 Redis 职责，不执行成熟公开数据集真实供应商评测。

## 3. 权限和并发边界

- 只允许当前租户的 `TENANT_ADMIN`；
- `PLATFORM_ADMIN`、Application Credential 和跨租户 Session 不能访问；
- Tenant 停用后既有管理 Session 按现有规则失效；
- KnowledgeBase 停用后仍允许删除，因为停用不能阻止数据清理；
- Document 存在 `PENDING` 或 `RUNNING` 入库任务时返回 `DOCUMENT_PROCESSING_IN_PROGRESS`；
- 删除受理事务锁定 KnowledgeBase、Document，并复核全部版本任务状态；
- 删除提交前已经固定的查询快照允许完成；提交后创建的新快照必须排除该 Document；
- 删除 Consumer 和入库最终激活均以 `Document.status` 为事实门禁，删除后不得重新激活。

## 4. HTTP 契约

### 4.1 首次删除

```http
DELETE /api/admin/v1/tenants/{tenantId}/knowledge-bases/{knowledgeBaseId}/documents/{documentId}
Idempotency-Key: 1—128 个可见 ASCII 字符
```

首次受理返回 `202 Accepted`：

```json
{
  "documentId": 123,
  "deletionJobId": 456,
  "attemptNo": 1,
  "documentStatus": "2",
  "jobStatus": "1",
  "replayed": false,
  "acceptedAt": "2026-08-12T12:00:00Z"
}
```

相同租户、相同 Key、相同 Document 返回原任务并令 `replayed=true`；同一 Key 绑定其他删除命令返回 `IDEMPOTENCY_KEY_REUSED`。Document 已经 `DELETED` 且不是既有 Key 重放时返回 `204 No Content`。

### 4.2 最终失败后的人工重试

```http
POST /api/admin/v1/tenants/{tenantId}/knowledge-bases/{knowledgeBaseId}/documents/{documentId}/deletion/retry
Idempotency-Key: 1—128 个可见 ASCII 字符
```

仅当 Document 为 `DELETING`、最近删除任务为最终 `FAILED`、`failureRetryable=true` 且没有删除任务正在执行时，创建递增 attempt 和新 Outbox，返回相同的 `202 Accepted` 结构。

### 4.3 管理查询

N4.1 文档列表和详情增加可空的 `latestDeletionJob`，包含删除任务 ID、attempt、状态、脱敏失败信息、可重试标记和时间。DocumentVersion 增加可空 `contentDeletedAt`，表示该版本的外部内容已经清理。

## 5. 删除受理事务

首次删除在一个 MySQL 事务中：

```text
锁定并复核 KnowledgeBase / Document
→ 拒绝存在 PENDING/RUNNING 入库任务的 Document
→ Document ACTIVE -> DELETING
→ activeVersionId = null
→ deletionRequestedAt = now
→ 创建 DocumentDeletionJob(attemptNo=1, PENDING)
→ 创建 DOCUMENT_DELETE_REQUESTED OutboxEvent
→ 提交
```

`latestVersionId` 和所有历史事实保留。文档名称在 `DELETING` 期间仍被占用，只有进入 `DELETED` 后才释放，之后可用新 Idempotency-Key 创建同名但 ID 不同的新 Document。

## 6. 数据模型

V11 增加：

- `document.active_name`：ACTIVE/DELETING 时等于 name，DELETED 时为空；替换原三列名称唯一约束，使完成删除后可以复用名称；
- `document.deletion_requested_at`、`document.deleted_at`；
- `document_version.content_deleted_at`；
- `document_deletion_job`：租户、知识库、Document、attempt、状态、租约、失败、可重试性、管理员、幂等摘要和时间；
- `outbox_event.document_id`、`document_deletion_job_id`，并允许入库专用的 Version/ProcessingJob 引用为空；
- 删除事件唯一约束 `(event_type, document_deletion_job_id)`。

不使用物理外键或 `CHECK`。既有入库 Outbox 行保持原语义。

## 7. RabbitMQ 和清理链路

单一 Transactional Outbox Publisher 按 `eventType` 路由：

- `DOCUMENT_VERSION_PROCESS_REQUESTED` 继续进入既有入库拓扑；
- `DOCUMENT_DELETE_REQUESTED` 进入独立 durable 删除主队列、三级 TTL 重试队列和 DLQ。

删除 Consumer 使用 MySQL Job 租约和至少一次幂等处理。对每个版本依次执行：

1. 按完整租户、知识库、Document、Version 范围删除 Evidence 和 Navigation 投影，不依赖单一投影指纹；
2. 删除 canonical 对象；
3. 删除 retrieval 对象；
4. 删除原文件对象。

外部删除均以“不存在即成功”处理。所有外部清理成功后，在最终 MySQL 事务中删除 artifact/projection 清单、写入各版本 `contentDeletedAt`、标记 Job `SUCCEEDED` 并将 Document 改为 `DELETED`、释放 `activeName`。DocumentVersion、ProcessingJob、DeletionJob、Outbox 和查询审计历史继续保留。

## 8. 失败处理

- 依赖瞬时失败按删除队列的 5/30/300 秒三级自动重试；
- 自动重试耗尽后 Job 进入 `FAILED` 并进入 DLQ；
- 错误只保存稳定分类、脱敏摘要和 `failureRetryable`；
- 任一步失败时 Document 始终保持 `DELETING`、`activeVersionId=null`；
- 部分外部对象已删除时再次执行仍然安全；
- 管理员人工重试创建新的删除 attempt，不复用已完成的 Job；
- 确定性失败按 fail-closed 拒绝人工重试，等待运维修复事实或后续版本处理。

## 9. 稳定错误

| HTTP | 错误码 | 含义 |
| --- | --- | --- |
| 400 | `VALIDATION_FAILED` | ID、Idempotency-Key 非法 |
| 403 | `TENANT_SCOPE_FORBIDDEN` | Session 不属于路径租户 |
| 404 | `KNOWLEDGE_BASE_NOT_FOUND` | 当前租户内知识库不存在 |
| 404 | `DOCUMENT_NOT_FOUND` | 当前知识库内文档不存在 |
| 409 | `DOCUMENT_PROCESSING_IN_PROGRESS` | 存在 PENDING/RUNNING 入库任务 |
| 409 | `DOCUMENT_DELETION_IN_PROGRESS` | 删除任务正在执行 |
| 409 | `DOCUMENT_NOT_DELETING` | 人工重试时 Document 不是 DELETING |
| 409 | `DOCUMENT_DELETION_NOT_FAILED` | 最近删除任务不是最终失败 |
| 409 | `DOCUMENT_DELETION_NOT_RETRYABLE` | 最近删除失败不可人工重试 |
| 409 | `IDEMPOTENCY_KEY_REUSED` | Key 已绑定其他删除命令 |

## 10. 验收点

1. 删除受理事务提交后，新 Retrieve/Answer 快照立即排除 Document；
2. 删除前已经固定的在途快照可以完成，删除后不能新建包含该 Document 的快照；
3. 文档列表/详情显示 DELETING、DELETED 和最近删除任务；
4. ES 两类投影、全部版本的 source/canonical/retrieval 对象最终消失；
5. MySQL 墓碑、版本、任务、Outbox 和查询审计历史保留；
6. 任一外部依赖故障时 Document 仍不可检索，恢复后可重复清理；
7. 相同删除命令幂等，不同命令冲突，并发删除最多创建一个 attempt；
8. 自动重试耗尽后可由管理员创建新 attempt；不可重试失败被拒绝；
9. 正在入库的 Document 被拒绝；停用 KnowledgeBase 仍允许删除；
10. 删除完成后同一 KnowledgeBase 可以创建同名新 Document；
11. Tenant 隔离、平台管理员拒绝和 Application Credential 管理面拒绝成立；
12. 真实 MySQL、SeaweedFS、RabbitMQ、Elasticsearch + Fake Gateway 完成 READY → 删除 → DELETED 端到端；
13. 默认完整回归不访问真实供应商并保持通过。

## 12. 实现结果

- V11 已落地 Document 删除墓碑、版本内容清理时间、删除任务、删除 Outbox 引用和完成删除后名称复用所需的数据事实；既有入库事件语义保持不变。
- 两个管理命令已按冻结契约开放：首次删除在单个 MySQL 事务内完成 `ACTIVE → DELETING`、清空 `activeVersionId`、创建删除任务和 Outbox；人工重试只接受最近一次可重试的最终失败。
- 删除消息使用独立 durable 主队列、三级 TTL 重试队列和 DLQ；共用既有 Transactional Outbox Publisher，但按事件类型严格路由。
- 删除 Processor 已按全部版本清理 Evidence/Navigation 投影、canonical、retrieval 和 source 对象；外部删除幂等，全部成功后才提交 MySQL 清单删除、`contentDeletedAt`、Job `SUCCEEDED` 和 Document `DELETED`。
- N4.1 管理查询已能显示 `DELETING`、`DELETED`、`latestDeletionJob` 和版本 `contentDeletedAt`；墓碑、版本、处理任务、删除任务、Outbox 和查询审计历史继续保留。
- 没有修改 `/retrieve`、`/answer` 契约、Redis 职责、`pom.xml` 或 `compose.yaml`，也没有增加管理后台前端、恢复/撤销删除或单版本删除。
