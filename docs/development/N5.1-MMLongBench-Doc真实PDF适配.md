# N5.1 MMLongBench-Doc 真实 PDF 适配

> 状态：候选数据、DeepDoc P0/P1 和真实租户完整入库 P2 均已完成并经用户确认；正式冻结结果为 100/100 READY、80/80 case 保留；N5.2 仍为 `NOT_STARTED`。

## 1. 阶段目标

N5.1 只准备正式公开数据集评测的确定性输入并验证它能否由当前 DocQuery 承载：

1. 使用公开数据集提供的真实原始 PDF，不生成、不转换、不改写文档；
2. 固定 100 份文档和 80 个问题，保存上游版本、原始标注和 SHA-256；
3. 把官方问题、答案、不可回答标记和证据页映射为 DocQuery 评测 case；
4. 使用生产 `PdfDocumentParser`、`CanonicalDocumentAssembler` 和 `CanonicalDocumentValidator` 做初始免费准入校验；
5. 经 P0、P1 验证并接入 DeepDoc 后，在独立 P2 中使用“测试科技”租户完成 100 份文档的真实完整入库并冻结 N5.2 输入。

最初的数据适配和免费校验没有调用供应商，也没有产生检索/回答质量、成本或端到端延迟分数。后续独立授权的 DeepDoc P0 验证了复杂 PDF 解析可行性，P1 完成生产 HTTP Adapter；P2 已在既有“测试科技”租户中完成 DeepDoc、检索卡、真实 Embedding、双索引和激活。P2 的入库 token 未统一采集、费用未计算；Retrieve/Answer 质量、查询成本和端到端延迟仍属于尚未开始的 N5.2。

## 2. 数据来源与许可证

- 官方仓库：<https://github.com/mayubo2333/MMLongBench-Doc>
- Hugging Face 数据集：<https://huggingface.co/datasets/yubo2333/MMLongBench-Doc>
- 上游锁定 revision：`2ff6aa9237fc777b6627dc57a486e9225ac5fb86`
- 官方 Parquet SHA-256：`bcdac3c96669634c34184814cede4fe57cf7ac0f98dde0e85936394f6a56a02d`
- 上游规模：1,091 个问题、135 份 PDF、7 个文档领域
- 许可证边界：研究用途，CC BY-NC 4.0；不得把语料作为 DocQuery 自有数据或商用语料重新分发

仓库中的 PDF 由上游提供。DocQuery 只锁定下载地址、文件名、字节数和 SHA-256；100 份 PDF 二进制共 `481,923,789` 字节，保存在本地评测目录但由 `.gitignore` 排除，避免把上游大文件提交到项目仓库。

## 3. 确定性选择

版本名为 `mmlongbench-docquery-v1`，选择种子为 `docquery-mmlongbench-pure-text-v1`。

### 3.1 问题

- 64 个可回答问题：答案格式限 `Str`、`Int`、`Float`、`List`，必须具有证据页，且官方 `evidence_sources` 必须恰好为 `Pure-text (Plain-text)`；
- 16 个不可回答问题：官方答案为 `Not answerable`，证据页和证据来源均为空；
- 排除依赖 `Generalized-text (Layout)`、`Table`、`Chart` 或 `Figure` 的可回答题；
- 7 个领域都固定配额，最终为 Academic 10、Administration/Industry 14、Brochure 10、Financial 10、Guidebook 13、Research 13、Tutorial 10；
- 选择只依赖锁定标注和种子，不依赖 DocQuery、Embedding 或模型结果，后续不能因结果不好而换题。

### 3.2 文档

上游纯文本证据可回答题共 134 个，但只覆盖 60 份不同 PDF，因此 80 题无法做到一题一文档。选择器先尽量扩大问题来源文档覆盖面，再从同一数据集确定性补足干扰文档：

- 100 份真实 PDF；
- 69 份 `CASE_SOURCE`；
- 31 份 `DISTRACTOR`；
- 不将 Markdown、网页正文或人工生成的 PDF 混入正式语料。

## 4. 数据映射

| 上游字段 | DocQuery 字段 | 规则 |
| --- | --- | --- |
| 行号 | `sourceRowIndex` / `caseId` | `caseId=mmlongbench-{四位行号}` |
| `doc_id` | `sourceDocumentId` / `displayName` | 保留原始 PDF 文件名 |
| `doc_type` | `sourceDomain` | 保留官方领域 |
| `question` | `question` | 不翻译、不改写 |
| `answer` | `referenceAnswer` / `goldAnswers` | 可回答题保留参考答案；不可回答题的 `goldAnswers` 为空 |
| `answer_format` | `answerFormat` / `questionType` | 上游字符串 `None` 规范化为 JSON `null` 和 `NONE` |
| `evidence_pages` | `relevance[].evidencePages` | 保留官方 1-based 证据页 |
| `evidence_sources` | `relevance[].evidenceSources` | 只接受纯文本证据标签 |

MMLongBench-Doc 给出证据页而非逐字答案锚点，因此这里不伪造 `anchorTexts`。后续质量报告只能表述为“DocQuery 在确定性 MMLongBench-Doc 文本证据子集上的结果”，不能表述为官方榜单、完整 MMLongBench-Doc 结果或视觉文档问答能力。

## 5. 产物与复现

冻结目录：`evaluation/mmlongbench-docquery-v1/`。

- `manifest.json`：来源、选择规则、100 份文档及其指纹；
- `cases.jsonl`：80 个问题与证据页映射；
- `source-annotations.jsonl`：1,091 条官方标注的规范化快照；
- `corpus-checksums.sha256`：100 份原始 PDF 的校验和；
- `checksums.sha256`：上述三个元数据文件的校验和；
- `README.md`：来源、许可、边界和复现命令。

生成器：`tools/evaluation/build_mmlongbench_subset.py`。它先校验 Hugging Face 当前 revision，再获取官方标注和固定 revision 的 PDF；已有合法缓存时不重复下载。

```powershell
python tools/evaluation/build_mmlongbench_subset.py all `
  --cache tmp/pdfs/mmlongbench-source `
  --output evaluation/mmlongbench-docquery-v1
```

## 6. 免费校验结果

### 6.1 已通过

- Python 选择测试 3/3：`None` 规范化、顺序无关的确定性配额、配额不足时 fail-closed；
- 使用同一锁定缓存完整重建后，`source-annotations.jsonl`、`cases.jsonl`、`corpus-checksums.sha256` 和 `manifest.json` 四个文件均与冻结产物逐字节一致；
- Java 元数据测试 1/1：100 文档、80 case、来源 revision、领域/答案配额、稳定键、证据页映射和 100 条 PDF 校验和清单通过；该默认测试不依赖被 Git 排除的 PDF 二进制；
- 7 个领域各选 1 份代表 PDF 渲染并目视检查，均为上游真实的论文、表单、手册、报告或演示文档；
- 真实 PDF 暴露的空字体名曾触发 1 个 `NullPointerException`，已做空值保护；复跑后 100 份文档均得到 canonical 成功或稳定业务失败码，不再有未分类异常。
- P1 四格式默认接入收口时的最终 `clean verify` 为 37 个 Java 测试套件共 155 项，其中 153 项执行通过、2 项真实供应商冒烟按设计跳过，0 failure、0 error；前端 Vitest 13/13。该结果替代早先 Docker 未启动时未能形成的完整集成回归。

### 6.2 生产解析准入未通过

显式命令：

```powershell
mvnw.cmd -q -Dtest=N5PublicEvaluationPdfCorpusCheck surefire:test
```

结果为 100 份中仅 8 份解析成功，92 份受控失败：

| 结果 | 文档数 | 含义 |
| --- | ---: | --- |
| canonical 成功 | 8 | 其中 7 份是 case 来源，仅覆盖 7 个 case：6 个可回答、1 个不可回答 |
| `PDF_COMPLEX_LAYOUT_UNSUPPORTED` | 69 | 当前首版只承诺可靠阅读顺序的普通文本型单栏 PDF |
| `PDF_NO_EXTRACTABLE_TEXT` | 22 | PDFBox 没有取得可用文本，通常需要 OCR 或上游文本层修复 |
| `ENCRYPTED_DOCUMENT_UNSUPPORTED` | 1 | 当前产品明确不支持加密 PDF |

这不是供应商或检索质量失败，而是入库前解析能力边界。官方 `Pure-text (Plain-text)` 只说明答案证据的模态，不保证整份 PDF 是 DocQuery 当前支持的单栏文本型版面。因此，该子集目前不能直接进入 N5.2：只对 6 个可回答 case 运行模型既不代表 80 题，也不能形成可信效果结论。

## 7. DeepDoc P0 技术验证

用户于 2026-08-16 明确授权“确认开始 N5.1-P0 DeepDoc 技术验证”。P0 使用固定 RAGFlow `v0.26.4` 官方镜像，在单个断网、4 CPU、12 GiB、无 GPU 设备请求的容器中运行。原计划验证固定 10 份；第 1 份完成后用户把范围缩减为原固定顺序前 2 份，因此第 2 份结果落盘后主动停止，后续 8 份未执行。

两份均是当前生产解析器以 `PDF_COMPLEX_LAYOUT_UNSUPPORTED` 拒绝的真实 PDF：75 页年报耗时 701.914 秒，49 页论文耗时 377.729 秒；两份均得到非空且带页位置的版面块，124/124 页有文本块，7/7 官方证据页覆盖。容器主动停止后的状态为 `OOMKilled=false`、`RestartCount=0`；没有调用任何付费供应商。详细证据见 [`N5.1-P0 DeepDoc 技术验证`](./N5.1-P0-DeepDoc技术验证.md)。

用户随后要求使用 GPU 对相同两份文档做速度对照。固定 PyTorch CUDA 12.6 派生镜像中，版面、表格、OCR 检测和 OCR 识别 session 均实际使用 CUDA provider；两份 GPU 耗时分别为 108.475 秒和 49.688 秒，相对 CPU 分别加速 6.471 倍和 7.602 倍，总体加速 6.826 倍，页覆盖和 7/7 证据页覆盖保持一致。CPU/GPU 的块数和字符数有小幅差异，不能声称正文逐字节等价。

该结果只证明 DeepDoc 路线对两份复杂文本型 PDF 可行，同时证明 GPU 能显著降低这两份样本的解析延迟。它不能外推到扫描件 OCR、`PDF_NO_EXTRACTABLE_TEXT`、DOCX/Excel/PPT、100 份总体成功率或生产吞吐，也没有改变当前 Java 生产解析准入的 8/100 事实。

## 8. 当前阶段结论和决策门

MMLongBench-Doc 已证明它适合作为“100 份真实复杂 PDF 的解析可靠性压力集”，但与当前 DocQuery 的单栏文本 PDF 产品边界不匹配，不能同时担当最小成本的正式检索/回答效果集。

在 P2 执行前，当前状态必须保持为：

- N5.1 候选数据适配完成，P1 前的本地解析准入历史基线仍为 8/100；DeepDoc P0、P1 均已验收关闭；
- N5.2 为 `NOT_STARTED`；
- 真实 DeepSeek、百炼 Embedding 的质量、成本和端到端延迟仍为 `NOT_EXECUTED`；
- 不得把两份 P0 成功写成生产系统已经支持复杂 PDF/OCR，也不得静默绕过 DocQuery 生产解析器。

P0、P1、P2 均已由用户确认完成并关闭。P2 在既有“测试科技”租户完成 100 份真实 PDF 的完整入库并冻结 80 个 N5.2 case；结果为 100/100 READY、Canonical/Retrieval/Projection 各 100、Evidence 78,062/78,062、Navigation 2,422/2,422。该完成确认不授权开始 N5.2。详见 [`N5.1-P2 测试科技租户完整入库与评测集冻结`](./N5.1-P2-测试科技租户完整入库与评测集冻结.md)。
