## 1. 产品结果

DocQuery 继续通过既有文档上传接口一次提交多份文档，每份文档仍形成独立 `ProcessingJob` 和既有 RabbitMQ 消息。生产环境默认由项目内 DeepDoc GPU HTTP 服务统一解析 PDF、DOCX、TXT 和 Markdown，返回带各格式原生位置的中立文本块，再复用既有 canonical、检索卡、Embedding、索引和版本激活链路。

P1 不增加解析队列或后处理队列。一个 Spring Boot 实例可通过既有 `consumer-concurrency=M` 启动 M 个 Consumer，`prefetch=1` 保证每个 Consumer 同时只持有一条未 ACK 消息；DeepDoc 服务内部解析并发固定为 1，其他 HTTP 请求等待解析槽位，不把正常繁忙映射为 `429`。

## 2. 冻结范围

- 继续使用现有 `docquery.document.processing.v1` 主队列、三级延迟重试队列和 DLQ，不声明新队列，不启用 Single Active Consumer。
- 每条消息仍执行完整链路：canonical → retrieval → 双索引投影 → 版本激活 → ACK。
- `DOCQUERY_CONSUMER_CONCURRENCY` 继续表示同一 Spring Boot 实例的整链路并发 M；`DOCQUERY_CONSUMER_PREFETCH=1` 保持不变。
- 新增一个常驻 DeepDoc HTTP 容器，固定 RAGFlow `v0.26.4` 和 P0 已验证的 GPU 运行时。
- DeepDoc HTTP 服务只启用一个模型实例和一个解析槽位；并发请求在服务内等待，不建立第二套持久任务状态。
- PDF、DOCX、TXT 和 Markdown 四种受理格式全部由一个 DeepDoc HTTP Adapter 接管；不按格式建立独立服务或队列。
- DeepDoc 返回中立块和格式原生位置：PDF 使用页码、页内顺序和 UTF-16 字符范围，DOCX 使用正文元素位置，TXT/Markdown 使用源行位置；Java `CanonicalDocumentAssembler` 继续独占稳定 ID、标题树、canonical range 和摘要生成责任。
- `DOCQUERY_DEEPDOC_ENABLED` 默认值固定为 `true`；只有显式设置为 `false` 才恢复原本地四格式 Adapter。默认回归测试配置单独显式关闭，以避免免费测试隐式依赖本机 GPU 服务。

## 3. HTTP 契约

### 3.1 健康检查

- `GET /health/live`：HTTP 进程存活。
- `GET /health/ready`：模型已初始化，且实际 ONNX Session 包含配置要求的 Provider。

### 3.2 解析

`POST /v1/parse` 使用 `multipart/form-data`，文件字段固定为 `file`，请求头 `X-Source-SHA256` 固定原文件 SHA-256，`X-Source-Format` 固定为 `PDF`、`DOCX`、`TXT` 或 `MARKDOWN`。响应 Schema 固定为 `docquery-deepdoc-http-v1`，至少包含：

- `sourceSha256`、`sourceFormat`、`pageCount`、`elapsedMillis`；非 PDF 的 `pageCount` 为 `null`；
- `blocks[]`：`kind`、`text`、`sourceType`、对应格式的位置字段和可选标题字段；
- `warnings[]`：稳定代码、通用消息和可选页码。

PDF 的 DeepDoc `title` 映射为真实可见标题候选，但 P1 没有可靠 PDF 标题层级模型，所以除首个第一页文档标题外统一映射为一级标题并产生一次降级 Warning。DOCX 使用 DeepDoc 恢复的真实样式名识别 Title/Heading，Markdown 使用 DeepDoc 元素提取器识别标题、列表、引用和代码块，TXT 使用 DeepDoc 分段器并回绑原始行范围。表格只保留 DeepDoc 恢复的扁平文本；P1 不声称恢复单元格网格、合并关系或表格语义。PDF figure 只保留返回文字，不保存或理解图片。

## 4. 失败与重试

- 格式声明不受支持、文件与声明不匹配、SHA-256 不匹配、加密/损坏文档、非法 UTF-8、页数/解压大小/块数超限、无非空块或缺失位置：稳定永久失败，不重试。
- DeepDoc 未就绪、HTTP 连接失败、响应超时、非法响应或内部解析依赖异常：稳定可重试失败，交给既有三级 RabbitMQ 重试。
- 正常忙碌不返回 `429`；等待时间包含在 Listener 的长任务租约和心跳范围内。
- RabbitMQ 至少一次投递保持不变。canonical 已存在且摘要有效时直接复用，后续失败重投不能制造第二份业务清单。
- 日志和错误响应不输出正文、原文件名、对象地址或第三方完整堆栈。

## 5. 验收点

- DeepDoc 容器出现在根 `compose.yaml` 的 `docquery-greenfield` 项目中。P1 验收时使用显式 profile；用户随后要求将生产 DeepDoc 改为默认服务，以便 Docker Desktop 一键启动整个分组。P0 CPU/GPU 验证任务仍保留为显式 profiles，不属于默认分组。
- Ready 证据包含真实 `CUDAExecutionProvider`，不能静默回落 CPU。
- 两个同时到达的解析请求最终都得到响应，服务观测到的最大实际解析并发为 1，正常等待请求不收到 `429`。
- Java Adapter 校验响应 Schema、源摘要、页数、块类型和位置，并能映射为既有 `ParsedDocument`。
- 默认配置下只有一个 DeepDoc Adapter 且支持全部四种格式；显式关闭时恢复原本地 PDF、DOCX、TXT、Markdown 四个 Adapter。
- RabbitMQ 拓扑没有新增队列；`consumer-concurrency=M`、`prefetch=1` 和整链路 ACK 语义保持不变。
- 至少完成一次真实 GPU HTTP 解析冒烟；不调用 DeepSeek、百炼 Embedding 或其他付费供应商。

## 6. 非目标

- 不验证双 GPU 解析并发，不把 P0 的 1.7 GiB 显存样本外推为安全并发容量。
- 不实现 PPT、Excel、图片、HTML 等新增格式的受理或生产接入。
- 不升级 canonical Schema 保存 bbox、表格网格、图片或公式语义。
- 不执行 100 份正式准入、真实供应商质量/成本/端到端延迟评测。
- 不开始 N5.2、多轮 Conversation、会话记忆或流式 Answer。

## 7. 已实现内容

- 新增 `tools/deepdoc-service/`：基于固定 P0 GPU 镜像构建常驻 HTTP 服务，以 Uvicorn 单 Worker 启动；只初始化一个 GPU `PdfParser`，同时初始化 DeepDoc 的 DOCX/TXT Parser 和 Markdown 元素提取入口。
- 服务实现 `/health/live`、`/health/ready` 和 `/v1/parse`；请求体、摘要、显式格式、PDF 页数、DOCX 解压大小、块数和非空位置均有上限或完整性校验，临时文件在请求结束后删除。
- `PARSER_MAX_CONCURRENCY` 在 P1 被强制固定为 `1`；进程内 Semaphore 让后续请求等待，不用 `429` 表示正常繁忙。
- 根 `compose.yaml` 中的生产 `deepdoc` 当前属于默认服务。容器属于 `docquery-greenfield`，显式占用 GPU，宿主只监听 `127.0.0.1:18080`。
- 新增统一 `DeepDocDocumentParser`，默认接管四种格式；显式 `DOCQUERY_DEEPDOC_ENABLED=false` 时恢复四个本地 Adapter。
- Java Adapter 以流式 multipart 上传原文件，限制响应体大小，并校验 Schema、源 SHA-256、源格式、块类型、对应格式的位置、标题约束和 Warning 页码。
- RabbitMQ 拓扑、Listener、ProcessingJob 状态机和 ACK 位置没有修改；仍由既有 Consumer 执行完整入库链路。
