## 1. 验证边界

本阶段只验证超长真实章节能否生成少量、连续、可定位的派生导航子分区。

- 触发阈值固定为 `64,000` 估算 token；P0 对英文公开 PDF 使用 `ceil(正文字符数 / 4)` 的确定性估算，不冒充供应商精确 token。
- canonical 真实标题树、原文 block 和页码不变；派生子分区不是原文标题，也不作为引用证据。
- 每个子分区必须绑定连续 canonical block 范围，完整覆盖原章节，不能重叠或漏块。
- 最终标题数量由长度下界约束并优先最少：3M 样本允许 3—4 个，Activision 样本允许 2—3 个。
- 固定 token 窗口不能直接成为最终检索结果；模型负责语义边界，本地程序负责数量、连续性和最大长度。
- 只验证两份已入库真实公开 PDF，不修改正式 Retrieval Artifact、Elasticsearch Mapping 或查询链路，不执行 R2、Answer 或批量重建。

## 3. 第一轮：模型直接返回最终分区

每份文档只调用一次 DeepSeek V4 Flash，整章作为一次输入，不做固定窗口切分。

- 3M 返回 3 个连续分区，block 覆盖率 `1.0`、无 gap、无 overlap，但最后一个范围估算为 96,796 token，超过 64K 上限。
- Activision 返回的最终分区数量不满足 2—3 个约束，本地校验拒绝。
- 3M 请求实际 `prompt_tokens=159,489`、`completion_tokens=784`，`finish_reason=stop`，耗时约 14.1 秒，证明整章请求和 JSON 返回链路可行。

结论：让模型同时负责语义、数量、长度和精确 block 边界不够可靠。

## 4. 第二轮：模型返回稠密边界候选

原型改为让模型返回 6—13 个语义边界候选，再由本地约束选择器形成 2—4 个最终连续范围。仍只对同样两份文档各调用一次。

两份响应都因“候选数量未达到提示范围”被旧版严格校验提前拒绝。该失败说明候选数量只能作为模型提示，不能作为正确性条件；当时的工具在本地结构校验前没有先保存 safe usage 和候选数量，因此这两次失败调用的精确 token 证据不可恢复，报告不得推算成本。

## 5. 最终原型契约

P0 最终原型已改为：

1. DeepSeek 读取完整真实章节，只返回带 block ordinal、标题、主题和强度的语义边界候选；
2. 候选数量只是提示，只要数量足以形成最终范围即可；
3. 本地选择器从候选中优先选择最少分区；
4. 每段硬性约束为 8K—64K 估算 token；
5. 结束 block 由下一个入选起点自动闭合，最后一段闭合到真实章节末尾；
6. 只有最终范围进入后续派生导航卡，未入选候选不持久化、不向量化；
7. 供应商 usage 和候选数量必须先于结构校验记录，失败也保留脱敏诊断。

这不是传统固定切块：长度只约束可行解，最终边界必须来自模型选择的语义候选。
