# DocQuery N3.1 查询授权、版本快照与 Redis 幂等

> 状态：已实现、验证并经用户验收

> 查询技术依据：[`检索生成与查询技术选型`](../technical-decisions/02-03-检索生成与查询技术选型.md)  
> 已验收投影依据：[`N2.5 双索引投影与版本激活`](./N2.5-双索引投影与版本激活.md)

## 1. 阶段目标

N3.1 建立正式服务 API 在执行检索前必须使用的可信查询执行边界：

- 从 `Authorization: Bearer <dq_app_...>` 解析 Application Credential；
- 对路径中明确指定的一个 `knowledgeBaseId` 执行 `READ` Grant 校验；
- 用一条 MySQL 查询读取该 KnowledgeBase 当前全部可见 `activeVersionId`，形成一次请求内不可变的版本快照；
- 使用 Redis 对相同 Application、接口类型和 `Idempotency-Key` 竞争唯一昂贵执行权，并短期复用成功结果；
- 保证缓存命中不能绕过 Credential/Grant 撤销、KnowledgeBase 停用或 activeVersion 变化。

N3.1 只提供内部可复用契约和真实 Redis/MySQL 验证。它不会注册一个无法返回真实检索结果的假 `/retrieve` 路由；N3.2 完成 BM25/KNN、RRF、canonical 原文和引用后才开放 Retrieve HTTP 接口。

## 2. 本阶段明确不做

- 不生成查询 Embedding；
- 不查询 Elasticsearch，不执行 BM25、KNN、RRF 或 Top-K；
- 不读取 `canonical.jsonl`，不组装原文证据或引用；
- 不实现 `/retrieve`、`/answer` Controller；
- 不实现 Answer Agent、工具调用、模型回答或多轮会话；
- 不新增查询审计表，不更新 Credential `last_used_at`；这些属于 N3.4；
- 不缓存 Credential、Grant、KnowledgeBase 状态、activeVersion 或管理员 Session；
- 不修改 N2.5 的索引、投影验收单、READY 或版本激活规则；
- 不增加数据库迁移。

## 3. 外部服务契约基线

N3 后续正式服务 API 路径冻结为：

```text
POST /api/v1/service/knowledge-bases/{knowledgeBaseId}/retrieve
POST /api/v1/service/knowledge-bases/{knowledgeBaseId}/answer
```

共同 Header：

```text
Authorization: Bearer dq_app_<keyId>.<secret>
Idempotency-Key: <1—128 个可见 ASCII 字符>
```

`knowledgeBaseId` 由租户管理员在管理面创建 KnowledgeBase 后交付给接入开发者，并作为业务后端环境配置保存。服务 API 不接受 `tenantId`，也不提供列出或自动发现知识库的能力。

第一版对外错误隐藏基线：

| HTTP | 错误码 | 外部语义 |
| --- | --- | --- |
| `401` | `APPLICATION_CREDENTIAL_INVALID` | Header 缺失、格式错误、Secret 错误、Credential/Application/Tenant 已不可用 |
| `404` | `KNOWLEDGE_BASE_NOT_AVAILABLE` | KnowledgeBase 不存在、停用、跨租户、无 Grant、Grant 已撤销或只有 WRITE |
| `409` | `IDEMPOTENCY_CONFLICT` | 同一作用域 Key 对应不同规范化请求 |
| `409` | `IDEMPOTENCY_CONTEXT_CHANGED` | Key 原执行绑定的 activeVersion 快照已变化 |
| `409` | `REQUEST_IN_PROGRESS` | 相同请求已有执行者且尚未完成 |
| `503` | `QUERY_IDEMPOTENCY_UNAVAILABLE` | Redis 未启用或当前不可用，不能承诺幂等 |

内部异常仍保留更准确原因，后续查询审计可以区分撤销、跨租户、权限不足和依赖异常，但服务响应不暴露其他租户资源存在性。

## 4. 固定执行顺序

```text
解析 Bearer Credential
→ 得到可信 credentialId/applicationId/tenantId
→ 复查 Credential、Application、Tenant 当前状态
→ 校验目标 KnowledgeBase 归属、状态和 READ/READ_WRITE Grant
→ 单条 MySQL 查询读取当前 activeVersion 快照
→ 计算确定性 snapshotFingerprint
→ 使用可信 Tenant/Application、接口类型和 Idempotency-Key 竞争 Redis 执行权
→ N3.2/N3.3 才执行实际 Retrieve 或 Answer
```

Redis 位于授权和快照之后。每次请求，包括成功结果重放，都必须先重新执行 Credential、Grant 和 KnowledgeBase 状态检查；Redis 不能把过去的授权结果变成当前授权事实。

## 5. activeVersion 查询快照

一次查询只使用一个不可变快照。MyBatis 使用一条带 Tenant、KnowledgeBase 和状态条件的联表 SQL，返回：

- `documentId`；
- `documentVersionId = document.active_version_id`；
- `versionNo`；
- `documentName`。

SQL 只包含 `Document=ACTIVE`、`active_version_id IS NOT NULL` 且对应 `DocumentVersion=READY` 的记录，并按 `documentId` 稳定排序。处理中、失败、删除中、已删除、没有 activeVersion 或 activeVersion 不处于 READY 的文档全部不可见。

快照指纹使用固定 `query-active-snapshot-v1` 格式，覆盖可信 Tenant、KnowledgeBase 及按序排列的 `documentId/documentVersionId`。空知识库也产生稳定指纹。N3.2 的 BM25、KNN、canonical 读取以及 N3.3 的所有工具必须携带同一组 Version ID，不能分别重新读取 activeVersion。

快照仅存在于当前查询上下文和 Redis 幂等记录中，不建立 MySQL 快照表，也不构成 activeVersion 缓存。

## 6. Redis 幂等模型

### 6.1 Key 与作用域

Redis Key 格式：

```text
docquery:query-idempotency:v1:{tenantId}:{applicationId}:{operation}:{sha256(Idempotency-Key)}
```

- `operation` 区分 `RETRIEVE` 与 `ANSWER`；
- 原始 `Idempotency-Key` 不写入 Redis Value、日志、MySQL 或错误消息；
- 不同 Application、不同接口类型可以复用同一个原始 Key；
- 请求指纹由 N3.2/N3.3 对规范化请求体计算，本服务只接受 64 位小写 SHA-256；
- Redis Value 绑定请求指纹和 activeVersion 快照指纹。

### 6.2 状态

| 状态 | 含义 |
| --- | --- |
| `RUNNING` | 一个带随机 owner token 的执行者拥有昂贵链路执行权 |
| `SUCCEEDED` | 已保存成功响应，可以在短 TTL 内重放 |

第一请求通过原子 Lua 脚本创建 `RUNNING`。相同请求并发到达时只有一个 `OWNER`，其他请求得到 `IN_PROGRESS`；相同 Key 不同请求得到 `IDEMPOTENCY_CONFLICT`；快照变化得到 `IDEMPOTENCY_CONTEXT_CHANGED`。

成功完成、续租和失败释放都必须通过 Lua 比较 owner token。旧执行者在租约过期并被新执行者接管后，不能覆盖新执行者结果。业务执行失败时只释放当前 owner 的 `RUNNING`，失败响应不进入成功结果缓存。

### 6.3 默认资源边界

| 参数 | 默认值 |
| --- | ---: |
| RUNNING TTL | 10 分钟 |
| SUCCEEDED 结果 TTL | 5 分钟 |
| 单个缓存响应上限 | 1 MiB UTF-8 |
| Redis Key 前缀 | `docquery:query-idempotency:v1` |

N3.3 的 Answer 总执行时限必须显著小于 RUNNING TTL，并在工具轮次之间续租。Redis 数据允许丢失；丢失最多导致只读查询在恢复后重新执行，不改变权限、版本或文档事实。

## 7. 依赖和本地运行

- Java 使用 Spring Boot 管理的 `spring-boot-starter-data-redis` 与 Lettuce；业务代码只依赖 `QueryIdempotencyService`；
- 本地和 Testcontainers 使用官方 `redis:8.8.1`；
- Compose 只绑定宿主回环地址，使用本地开发密码、`restart: "no"`，不配置持久卷；
- Redis 默认不在应用启动时建立业务事实，只有查询幂等调用才访问；
- `docquery.query.idempotency.enabled` 默认关闭，正式服务 API 启用前必须显式开启；关闭或连接失败统一 fail-closed 为 `QUERY_IDEMPOTENCY_UNAVAILABLE`。

## 9. 验收点

### 9.1 授权和隐藏

- 正确 Bearer Credential 和 READ/READ_WRITE Grant 可以得到可信查询上下文；
- 缺失、错误、撤销 Credential 以及停用 Application/Tenant 统一认证失败；
- 不存在、停用、跨租户 KnowledgeBase，无 Grant、撤销 Grant 和 WRITE-only 统一表现为不可用；
- 管理员 Session 不能生成服务查询上下文；调用方没有覆盖 tenantId 的入口；
- 每次重放前重新授权，撤销后不能取得旧缓存结果。

### 9.2 快照

- 一条 SQL 得到同一 KnowledgeBase 当前全部 activeVersion；
- PROCESSING/FAILED、非 active 的历史 READY、删除中文档均被排除；
- 同一集合产生相同指纹，版本切换后指纹变化；
- 返回列表不可修改，后续两路查询只能消费该快照。

### 9.3 Redis

- 相同作用域、Key、请求和快照的并发竞争只有一个 OWNER；
- RUNNING 重复请求不重复执行，完成后可精确重放成功结果；
- 同 Key 不同请求冲突，不同 Application/接口互不复用；
- 快照变化不能重放旧版本结果；
- 续租、完成和释放都校验 owner token，过期 owner 不能覆盖新 owner；
- Key/Value 不包含原始幂等键、Credential、Authorization 或 Secret；
- Redis 关闭、未启用和结果过大返回稳定受控失败。

### 9.4 回归和边界

- 使用真实 MySQL 8.4.10 和 Redis 8.8.1 Testcontainers；
- 不连接 Compose 持久数据，不调用真实模型或 Elasticsearch；
- N0—N2.5 既有回归继续通过；
- N3.1 不注册 Retrieve/Answer HTTP 路由，不新增数据库表，不进入 N3.2。
