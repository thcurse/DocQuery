# DocQuery N3.4 查询审计、检索评测与性能基线

> 状态：已实现、验证并于 2026-08-12 经用户验收
> 前置阶段：N0—N3.3 均已实现、验证并经用户验收
> 上游依据：产品设计、开发计划、检索生成与查询技术选型及 N3.1—N3.3 实施文档

## 1. 阶段目标

N3.4 不改变 `retrieve-ranking-v1` 或 `answer-policy-v1`，只补齐三类可验证事实：

1. 对真实 `/retrieve`、`/answer` 尝试形成应用级访问审计；
2. 建立项目自有、无隐私、可复现的 `n3-eval-v1` 冒烟夹具和指标执行器；
3. 记录确定性服务基线，并为后续公开数据集真实效果评测保留执行能力。

## 2. 明确不做

- 不调整 BM25 权重、KNN、RRF、Top-K、Prompt、工具预算或失败语义；
- 不引入 Reranker、语义切分、RAPTOR、GraphRAG、多轮聊天或流式回答；
- 不保存完整问题、回答、Prompt、Evidence 正文、Authorization、Secret 或原始幂等键；
- 不提供 Application Credential 查询审计的接口；
- 不实现 N4 管理后台页面；
- 不用 Fake Gateway 的结果声称真实模型效果；
- 不在没有实测基线前承诺 Recall、延迟或吞吐目标。

## 3. 应用访问审计

### 3.1 覆盖范围

- 请求格式在进入 Controller 前已失败、Credential 缺失/格式错误/Secret 错误时，只进入安全日志；没有可信 Application，不能伪造应用审计主体。
- Credential 已可信后，知识库隐藏、Grant 拒绝、幂等冲突、依赖失败、正常成功、明确降级和成功重放都写审计。
- 每次 HTTP 尝试有独立 `requestId`；成功重放创建新审计记录，但沿用原 `queryExecutionId`。
- 调用方可传 `X-DocQuery-Trace-Id` 和 `X-DocQuery-Actor-Ref`。二者只用于排障，不参与授权和幂等指纹。

### 3.2 可靠性

```text
可信 Credential
→ 插入 STARTED
→ 执行既有授权、快照、Redis 幂等、Retrieve/Answer
→ 持久化 SUCCEEDED/FAILED/REJECTED
→ 成功响应
```

- `STARTED` 无法持久化时返回 `503 QUERY_AUDIT_UNAVAILABLE`，不执行昂贵查询；
- 成功结果只有在审计终态持久化后才返回；终态更新失败返回同一 503；
- 已经失败的业务请求保留原错误，审计更新失败作为附加故障记录；
- 超过最大查询时限仍为 `STARTED` 的记录由维护任务改为 `INTERRUPTED`；
- 默认保留 90 天，维护任务按有限批次清理。

### 3.3 数据最小化

审计只保存主体、目标、执行状态、失败码、耗时、模式、降级、版本快照摘要、结果计数和 Agent 计数。问题只保存规范化文本的 SHA-256 和字符数；凭证只保存内部 ID 与 Key ID 摘要。

### 3.4 管理查询

仅 Tenant Admin 可访问：

```text
GET /api/admin/v1/tenants/{tenantId}/query-audits
GET /api/admin/v1/tenants/{tenantId}/query-audits/{auditId}
```

支持时间、Application、KnowledgeBase、操作、结果、requestId、queryExecutionId 和调用方 traceId 过滤。列表稳定按 `startedAt DESC, id DESC` 分页；无修改或单条删除接口。

## 4. n3-eval-v1 确定性冒烟夹具

`n3-eval-v1` 只验证格式解析、数据映射、指标计算和评测链路，不是合格的质量 Gold Set，不得据此评价 DocQuery 的真实检索或回答效果。正式质量评测延期到完整功能落地后的发布前最终门禁，优先适配成熟公开数据集，不再继续人工扩写本夹具。

### 4.1 语料

- 12 份完全虚构的企业内部资料，覆盖 PDF、DOCX、TXT、Markdown；
- 40 个问题：24 个单证据可回答、8 个多证据可回答、8 个知识库内不可回答；
- 24 个开发用例、16 个冻结验收用例；
- 覆盖无标题长 PDF、只有一级标题、超长章节、口语/专业术语差异和跨章节证据。

### 4.2 标注

每个 case 固定问题、可回答性、相关逻辑文档、真实标题、原始位置锚点、必需证据组和关键事实。标注使用源文件 SHA-256 与逻辑位置，不依赖运行时数据库 ID；这些标注只承担确定性夹具职责，不具有人工 Gold 标注的质量结论。

### 4.3 执行与指标

同一问题分别执行 `KEYWORD`、`SEMANTIC`、`HYBRID`，记录：

- Document Recall@5/10；
- Section/原始位置 Recall@5/10；
- MRR@10；
- 有分级标签时的 nDCG@10；
- `ANSWERED`/`INSUFFICIENT_EVIDENCE` 判断；
- 引用 ID/原文位置机械正确率；
- 关键事实和引用支持程度的人工复核表；
- Agent 工具轮数、模型调用量、上下文字符量与可获得成本。

Fake Gateway 只做确定性回归。正式质量评测将在发布前使用成熟公开数据集和真实供应商显式执行，并记录数据集版本、模型、时间、配置版本和费用；未执行时必须明确标为未执行。

## 5. 查询性能基线

- `/retrieve` 与 `/answer` 分开报告；
- OWNER 首次执行与 Redis REPLAY 分开报告；
- 固定向量/Fake Answer 的服务开销与真实供应商端到端延迟分开报告；
- 记录机器、JDK、依赖版本、数据规模、并发、请求数、吞吐、错误率、P50/P95/P99、降级率；
- 基准工具从外部 HTTP 调用正式接口，不绕过 Credential、Grant、activeVersion、Redis 或审计。

## 6. 验收点

1. V9 可从空库创建审计表，保持无物理外键、无 CHECK；
2. 可信应用成功、拒绝、依赖失败、幂等冲突和重放均有独立审计；
3. 无效 Credential 不产生伪造应用审计；
4. 审计不可用时成功访问 fail-closed；
5. 审计不包含问题正文、回答、原文、Secret、Authorization 或原始幂等键；
6. Tenant Admin 只能查询自己租户，Application Credential 和跨租户管理员均被拒绝；
7. `n3-eval-v1` 冒烟夹具的文件、清单、SHA-256、40 个 case 和锚点通过自动校验；
8. 指标计算器使用固定样例验证 Recall、MRR、nDCG 和引用判定；
9. 生成确定性评测报告，并为真实供应商报告保留明确的执行/未执行状态；
10. 性能脚本可复现 OWNER/REPLAY、Retrieve/Answer 的 P50/P95/P99；
11. N0—N3.3 默认回归继续通过，真实供应商仍默认关闭。

## 7. 实现与验证证据

- V9 已新增 `application_query_audit`，审计覆盖可信应用的成功、拒绝、依赖失败、幂等冲突、降级与重放；无效 Credential 不写应用审计。
- `/retrieve`、`/answer` 已统一经过 fail-closed 审计包装，并返回 `X-DocQuery-Request-Id`；管理面已提供租户隔离的列表和详情查询。
- `evaluation/n3-eval-v1` 已生成 12 份完全虚构语料和 40 个固定 case：24 个开发集、16 个验收集，题型为 24 个单证据、8 个多证据、8 个不可回答；用户复核后将其定性为冒烟夹具，不作为正式质量 Gold Set。
- 生产 PDF/DOCX/TXT/Markdown 解析器已完成语料、SHA-256 与锚点自动校验；3 份 PDF 和 3 份 DOCX 共 13 页已逐页渲染检查，无截断或不可读内容。
- 指标执行器的 Recall、MRR、nDCG、拒答与百分位固定样例测试 4/4 通过；HTTP 性能快照覆盖 Retrieve/Answer 的 OWNER 与 Redis REPLAY，共 60/60 成功且形成 60 条审计。
- `./mvnw.cmd -q verify` 在 JDK 17.0.12、Docker 29.6.2 下完成：30 个测试套件共 124 项，122 项执行通过，2 项真实供应商冒烟按设计跳过，0 failure、0 error；其中 Failsafe 84/84 通过，`RetrieveIT` 9/9 通过。
- 正式公开数据集与真实供应商效果评测延期到完整功能落地后的发布前最终门禁；当前状态为 `NOT_EXECUTED`，不声明真实检索质量、回答质量、成本或延迟结果。

用户已于 2026-08-12 明确说“确认 N3.4 完成”，N3.4 与整个 N3 阶段验收关闭。该确认不授权直接实施 N4；N4 仍须先讨论并冻结范围，再取得“确认开始 N4”。
