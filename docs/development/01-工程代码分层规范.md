# DocQuery 工程代码分层规范

> 状态：当前已实现代码必须遵守  
> 适用范围：DocQuery Spring Boot 单体工程  
> 基线：2026-08-02

## 1. 目的和依据

产品开发计划已经约定传统 Spring Boot 分层。结合当前项目使用 MyBatis，以及用户确认的 JavaBean 代码风格，本仓库固定为：

```text
Controller -> Service 接口 -> service.impl -> Mapper -> MySQL
    DTO              DTO/VO          Entity      Entity/查询 DTO
    VO 响应
```

分层用于明确数据边界和依赖方向，不是为了提前创建未来业务的空类。只有对应表或接口已经进入当前开发阶段时，才创建它的 Entity、DTO、VO、Mapper 和 Service 方法。

## 2. 目录和职责

| 目录 | 职责 | 可以包含 | 不可以包含 |
| --- | --- | --- | --- |
| `controller` | HTTP 参数绑定、基础校验、提取可信身份、调用 Service、组装 HTTP 状态和 Location | 路由、`@Valid @RequestBody` DTO、VO 返回 | SQL、事务、租户业务判断、内部 request/response 类型 |
| `dto` | 接口请求参数、分页条件、按 ID 或组合条件查询数据库时的条件或投影 | 普通 class、Lombok、Jakarta Validation、字段注释 | 对外响应模型、数据库表实体 |
| `vo` | 接口返回数据 | 普通 class、只读 getter、构造器、分页 VO、错误 VO | 任意业务 setter、密码哈希、数据库写入状态、Entity 引用 |
| `entity` | 与真实数据库表字段对应的持久化对象 | MyBatis 可读写 JavaBean、生成主键 | HTTP 注解、业务授权、对外直接返回 |
| `mapper` | MyBatis SQL 和数据库访问 | Entity 返回、查询 DTO、计数和写入方法 | 产品规则、角色判断、事务编排、VO |
| `service` | 公开业务能力接口 | 方法签名、DTO 入参、VO 返回 | `@Service` 实现、SQL、内部 Entity 暴露 |
| `service.impl` | 业务规则、租户授权、事务边界、Entity 与 VO 转换 | `@Service`、`@Transactional` | HTTP 请求和响应对象、Controller 逻辑 |
| `enums` | 数据库和接口使用的字符串枚举代码及其语义转换 | 状态、管理员角色、Grant 权限枚举 | 分散的魔法字符串、数据库访问、业务事务 |
| `exception` | 稳定业务错误和统一 HTTP 错误映射 | `BusinessException`、全局处理器 | 具体领域事务实现 |

### 2.1 注释和可读性

- 每个生产 Java 类型必须有类型级 Javadoc，说明它承担的业务职责、边界和重要非目标。
- Service 接口的公开方法必须说明业务结果；Controller 路由必须说明对外动作，具体实现通过接口继承契约，不重复逐行翻译代码。
- Entity 的关键字段必须说明租户归属、状态、时间基准、敏感性以及 active/latest 等容易混淆的语义。
- 事务、锁、幂等、权限隐藏、密钥处理和异常恢复等无法仅从语法看出的决定，必须在对应分支附近说明“为什么”。
- 不为普通 getter/setter、显然的赋值或简单格式转换添加无信息量注释；注释必须随行为变更同步维护。

## 3. DTO、VO 和 Entity 的边界

### 3.1 DTO

DTO 只负责传递输入或查询数据，当前包括三类：

1. HTTP JSON 请求，例如 `CreateTenantDTO`、`UpdateApplicationDTO`。
2. URL 查询参数转换后的条件，例如 `PageQueryDTO`。
3. Mapper 查询条件或联表投影，例如 `TenantResourceQueryDTO`、`AdminIdentityDTO`。

请求 DTO 使用普通 class 和 Lombok `@Data`，字段提供业务含义注释。`@NotBlank`、`@Size`、`@Pattern` 等 Jakarta Validation 注解处理基础格式；唯一性、租户隔离、不可变字段和状态流转仍由 Service Impl 处理。DTO 不作为接口响应。密码可以短暂存在于请求 DTO 中，但不能进入 VO、日志或错误响应。

### 3.2 VO

VO 是 Controller 对外返回的唯一业务模型。当前包括 `AdminVO`、`TenantVO`、`ApplicationVO`、`KnowledgeBaseVO`、`CredentialVO`、`CreatedCredentialVO` 和通用 `PageVO` 等。VO 使用普通 class、Lombok `@Getter` 和构造器，不提供任意修改字段的 setter。

VO 不参与 Mapper 写入，也不包含 Entity。数据库中的 UTC `LocalDateTime` 由 Service Impl 转为带偏移量的 `OffsetDateTime` 后再写入 VO。

### 3.3 Entity

一个 Entity 对应一张当前真实存在并已进入业务实现阶段的数据库表：

| Entity | 数据库表 |
| --- | --- |
| `AdminUserEntity` | `admin_user` |
| `TenantEntity` | `tenant` |
| `ApplicationEntity` | `application` |
| `KnowledgeBaseEntity` | `knowledge_base` |
| `CredentialEntity` | `credential` |
| `ApplicationGrantEntity` | `application_grant` |
| `DocumentEntity` | `document` |
| `DocumentVersionEntity` | `document_version` |
| `ProcessingJobEntity` | `processing_job` |
| `OutboxEventEntity` | `outbox_event` |

Entity 使用普通 JavaBean，是因为 MyBatis 需要写回数据库生成的 BIGINT 主键并映射查询结果。Entity 不直接作为 Controller 返回值。尚未进入实现阶段的表不提前创建 Entity。

## 4. Service 接口和实现

`service` 目录只保留接口：

- `AdminBootstrapService`
- `AdminIdentityService`
- `TenantManagementService`
- `ApplicationService`
- `KnowledgeBaseService`
- `CredentialService`
- `ApplicationCredentialResolver`
- `ApplicationGrantService`
- `KnowledgeBaseAccessAuthorizer`
- `DocumentUploadAcceptanceService`

对应实现全部位于 `service.impl`，类名统一以 `Impl` 结尾。Controller、Security、Command 和测试只注入 Service 接口，不依赖实现类。

事务边界和业务校验放在实现类中。常规事务使用 `@Transactional`；N2.1 上传受理为了让数据库唯一冲突事务先完整回滚、再在新事务读取已提交的幂等结果，使用配置为 READ COMMITTED 的 `TransactionTemplate`，仍然不把事务编排下沉到 Mapper。接口不返回 Entity，Mapper 不返回 VO。Application 和 KnowledgeBase 使用各自的 Controller、Service、ServiceImpl 和 Mapper，不使用笼统的对象管理 Service 合并两个业务对象。

## 5. 一次请求的数据流

以创建 Application 为例：

1. Controller 将 JSON 映射为 `CreateApplicationDTO`。
2. Controller 将可信 `AdminPrincipal`、路径 Tenant ID 和 DTO 传给 `ApplicationService`。
3. `ApplicationServiceImpl` 执行租户边界、字段和唯一性检查，并构造 `ApplicationEntity`。
4. `ApplicationMapper` 写入 Entity，由 MyBatis 回填生成主键。
5. Service Impl 按 Tenant ID 和资源 ID 查询 Entity，转换成 `ApplicationVO`。
6. Controller 返回 VO 和 `201 Location`。

整个流程中，Controller 不接触 Entity，Mapper 不接触 VO，Service 接口不暴露实现细节。

N2.1 尚未开放文件上传 Controller。`DocumentUploadAcceptanceService` 接收 DTO 表达的“已持久化原文件描述”，在一个数据库事务中创建 DocumentVersion、ProcessingJob 和 OutboxEvent；N2.2 的 S3 兼容对象存储协调层完成真实文件保存后才可以调用该 Service 并注册管理面上传路由。

## 6. 明确禁止的写法

- 不使用 record 代替当前项目约定的 DTO 和 VO 普通 class。
- 不在 Controller 内声明请求 DTO、响应 VO 或错误 VO 的内部类型。
- 不在 Service 接口或实现类中声明 `*View`、`*Row`、`*Insert`、`*Update` 等内部数据类型。
- 不在 Mapper 中使用内部类代替 Entity。
- 不把具体 Service 实现类直接放在 `service` 目录。
- 不从 Controller 直接调用 Mapper。
- 不将 Entity 直接序列化为接口响应。
- 不为尚未进入当前阶段的表或接口提前创建空分层文件。

## 7. 当前验证要求

分层调整必须满足以下验收：

1. 主代码和测试代码在 Java 17 下编译通过。
2. N1.3、N1.4 原有 HTTP JSON、状态码、权限和数据库行为不变，N1.5 凭证响应不泄露 Secret 或摘要。
3. Testcontainers 使用临时 Docker MySQL，不能改用本机 MySQL 或 Compose 持久化数据库。
4. 完整 `clean verify` 通过后，才能请求当前阶段完成确认。
