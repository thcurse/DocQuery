## 2. 产品结果

N2.2 完成后，租户管理员可以通过 N2.1 已冻结的管理面 multipart 契约上传真实文件，并在原文件已经持久保存、数据库受理事务已经提交后获得 `202 Accepted`。

系统同时具备：

- 私有对象存储中的不可变原文件。
- 从 PENDING Outbox 到 RabbitMQ 的可靠发布。
- 带 Confirm、Return、租约和恢复的至少一次投递。
- durable/quorum 工作队列、延迟重试队列和最终死信队列骨架。
- 可被后续完整入库处理器使用的 Consumer、任务租约和失败记录边界。

N2.2 完成后文档仍然只会停留在 `PROCESSING`，不会解析正文、生成检索卡、写 Elasticsearch、切换 `activeVersionId` 或产生 `READY`。

## 3. 实施前基线

- N2.1 已创建 `Document`、`DocumentVersion`、`ProcessingJob` 和 `OutboxEvent` 事实。
- `DocumentUploadAcceptanceService` 已处理 Tenant 权限、上传幂等、内容去重、版本并发和数据库原子事务。

## 4. 本阶段范围

### 4.1 实现范围

- 为首次上传和新版本上传注册 N2.1 已冻结的两个 multipart Controller 路由。
- 流式保存原文件、计算字节数与 SHA-256，并调用 N2.1 数据库受理 Service。
- 提供对象存在性、读取、精确删除和孤立对象回收能力。
- Outbox 批量领取、RabbitMQ 发布、Confirm/Return 处理、失败退避和过期租约恢复。
- RabbitMQ v1 交换机、工作队列、三级延迟重试队列和最终 DLQ。
- Consumer 消息校验、任务租约领取、重复消息判断、重试分类和死信失败记录骨架。
- MySQL、对象存储和 RabbitMQ 的 Testcontainers 集成测试。
- 本地 Compose 增加对象存储和 RabbitMQ 服务，但不自动启动 DocQuery 应用进程。

### 4.2 明确不做

- 不解析 PDF、DOCX、TXT 或 Markdown 正文。
- 不生成标准化原文、标题树、位置映射、DocumentProfile 或 RetrievalNode。
- 不调用模型、不生成 Embedding、不连接 Elasticsearch 或 Redis。
- 不将 DocumentVersion 或 ProcessingJob 标记为成功，不切换 `activeVersionId`，不产生 `READY`。
- 不实现管理员手动重试、文档删除、版本回滚或处理任务管理 API；这些仍属于后续生命周期阶段。
- 不开放 Application Credential 的 `WRITE` 上传接口；本阶段仍只允许当前 Tenant 的有效租户管理员使用 Session 和 CSRF 上传。

## 5. 已确认的对象存储方案

用户已于 2026-08-03 确认 N2.2 默认自托管对象存储使用 SeaweedFS。这里确认的是对象存储 Server 方案，不代表 N2.2 整体设计已确认或已经获得实施授权。

代码边界保持供应商无关：

- 业务 Service 只依赖 `SourceObjectStore`，首个实现命名为 `S3SourceObjectStore`，不出现 SeaweedFS 业务分支。
- 本地开发和 Testcontainers 使用官方 SeaweedFS 镜像的固定版本或 digest，并以单节点模式提供 S3 API。
- 本地单节点只用于开发和测试，不承诺生产高可用。
- 私有化生产可以部署多 Master、Filer、Volume Server 和 S3 Gateway，并配置副本、负载均衡、备份与恢复。
- 阿里云生产可以通过另一个 `SourceObjectStore` 适配配置接入 OSS；接入前必须通过相同对象存储契约测试，不假设所有 S3 实现行为完全一致。

选择 SeaweedFS 的原因是它使用 Apache-2.0 许可证、仍在维护、提供本地 S3 兼容入口并支持多节点扩容；它解决 DocQuery 的独立部署默认实现问题，不被描述为托管 OSS 的全面替代品。

MinIO AIStor Free 的单节点限制不等于旧 MinIO 技术上不能分布式部署；本项目不把需要许可证的 AIStor 作为默认自托管依赖。Java S3 Client 已单独选择 AWS SDK for Java 2.x，不能把这理解为对象必须保存在 AWS。

## 6. 管理面上传契约

继续使用 N2.1 已冻结的两个接口：

```text
POST /api/admin/v1/tenants/{tenantId}/knowledge-bases/{knowledgeBaseId}/documents
POST /api/admin/v1/tenants/{tenantId}/knowledge-bases/{knowledgeBaseId}/documents/{documentId}/versions
```

共同要求：

- `Content-Type: multipart/form-data`
- `Idempotency-Key` 为 1–128 个可见 ASCII 字符。
- 浏览器 Session 已认证且 CSRF Token 有效。
- 首次上传包含 JSON `metadata` Part 和二进制 `file` Part；新版本只包含 `file` Part。
- Controller 不接受客户端声明的 Tenant、Bucket、Object Key、文件 SHA-256 或格式代码。

成功仍返回 N2.1 的 `DocumentUploadAcceptedVO` 和 `202 Accepted`。响应禁止包含对象存储地址、内容摘要、Outbox ID、RabbitMQ 信息或内部异常。

## 7. 文件校验和受理顺序

推荐顺序：

```text
校验管理员、Tenant、KnowledgeBase和路径参数
→ 校验文件名、扩展名、声明大小和配置上限
→ 生成本次请求唯一且不可预测的对象Key
→ 流式写入私有Bucket，同时计算实际字节数和SHA-256
→ 校验实际字节数与上传元数据一致
→ 调用N2.1 DocumentUploadAcceptanceService
→ 确认本次对象是否被返回的DocumentVersion实际引用
→ 数据库事务已提交后返回202
```

文件基础规则：

- 空文件拒绝。
- 格式只根据安全化原始文件名扩展名推断：`.pdf`、`.docx`、`.txt`、`.md`、`.markdown`。
- `Content-Type` 只作为元数据保存，不单独决定格式。
- 损坏文件、扫描 PDF、编码、压缩包内部结构和可解析性留给 N2.3。
- Servlet multipart 限制和业务流式计数使用同一个大小上限，避免只信任 `Content-Length`。

第一版上限确认为 `50 MiB`，通过 `DOCQUERY_UPLOAD_MAX_BYTES` 配置。N2.2 验收必须记录 1 MiB、10 MiB、50 MiB 样本的耗时与内存，不满足基线时重新讨论而不是静默调整。

## 8. Bucket 与对象键

### 8.1 Bucket

- 使用一个私有 Bucket，默认名为 `docquery-source`。
- 应用启动时只校验 Bucket 存在和可访问，不在生产环境自动创建。
- 本地 Compose 初始化步骤和集成测试负责创建 Bucket。
- 不开放匿名读取，不生成长期预签名 URL，不把访问凭证写入日志或数据库。

### 8.2 对象键

对象键格式：

```text
source/{tenantId}/{yyyy}/{MM}/{randomUuid}
```

约束：

- 不包含原文件名、Document 名称、登录名、Bucket 凭证或幂等键。
- 不依赖尚未创建的 Document ID。
- 每次物理上传使用新的随机 Key，不按内容哈希跨请求或跨租户合并。
- 对象创建后视为不可变；同一 Key 不允许覆盖。
- 数据库中的 Bucket/Object Key 是唯一引用事实，业务身份仍使用 DocumentVersion ID。

## 9. 数据库失败与孤立对象回收

对象存储与 MySQL 无法组成分布式事务，采用“立即清理 + 延迟兜底”策略：

1. 本次调用知道自己生成的精确 Bucket/Object Key。
2. 数据库受理失败时，只删除本次调用创建且数据库未引用的精确对象。
3. 幂等重放可能返回另一个并发请求创建的版本；协调层必须检查本次 Key 是否被实际引用，未引用时删除本次对象。
4. 删除失败不伪装为上传成功；原业务错误照常返回，同时记录脱敏告警。
5. 定时孤立对象回收器只扫描 `source/` 前缀中超过宽限期的对象，逐个查询数据库引用后删除。
6. 数据库查询异常、对象年龄不足或引用状态不确定时一律不删除。

默认参数：

- 孤立对象宽限期：24 小时。
- 扫描周期：15 分钟。
- 单次最多检查：100 个对象。

不新增“上传临时表”或把文件写入 MySQL BLOB。

## 10. Outbox Publisher

### 10.1 领取

每个应用实例生成不含主机秘密的 `publisherInstanceId`。每轮在短数据库事务内：

- 按 ID 领取 `PENDING and available_at <= now` 的事件。
- 同时回收 `PUBLISHING and locked_until < now` 的过期租约。
- 使用 `FOR UPDATE SKIP LOCKED` 支持多实例并行且不重复领取同一行。
- 将领取行更新为 `PUBLISHING`，设置 owner/lease，并增加 `attempt_count`。
- 提交数据库事务后再访问 RabbitMQ，不在数据库事务内等待网络 Confirm。

### 10.2 发布和确认

- 使用 Spring AMQP `RabbitTemplate`。
- 开启 correlated publisher confirms、publisher returns 和 `mandatory=true`。
- AMQP Message 持久化，`messageId` 与 `correlationId` 使用十进制 Outbox ID。
- Confirm ACK 且没有 Return 才在新事务中把 Outbox 标记为 `SENT`。
- NACK、NO_ROUTE、Confirm 超时或连接异常都把当前租约拥有的事件退回 `PENDING`，写入脱敏错误并推进 `available_at`。
- 更新 `SENT` 或重置失败时必须同时匹配 `id + status=PUBLISHING + locked_by`，旧实例不能覆盖新租约。

如果消息已进入队列但进程在写 `SENT` 前崩溃，租约到期后会再次发布；这是预期的至少一次语义。

### 10.3 默认参数

- Poll：1 秒。
- Batch：50。
- Publisher 租约：30 秒。
- 单消息 Confirm 超时：5 秒。
- 发布失败退避：1 秒、5 秒、30 秒、2 分钟、10 分钟封顶，并加入最多 20% jitter。
- RabbitMQ 不可用时不设置最大次数；事件保持 PENDING 并持续低频恢复，不能因短期中断永久丢任务。

## 11. RabbitMQ v1 拓扑

所有名称带版本，避免以后通过修改已有 Queue 不兼容参数进行原地升级：

```text
Exchange: docquery.document.processing.v1
Routing:  document.version.process.requested.v1
Queue:    docquery.document.processing.v1.q

Exchange: docquery.document.processing.retry.v1
Queues:   docquery.document.processing.retry.1.v1.q  TTL 5s
          docquery.document.processing.retry.2.v1.q  TTL 30s
          docquery.document.processing.retry.3.v1.q  TTL 300s

Exchange: docquery.document.processing.dlx.v1
Queue:    docquery.document.processing.dlq.v1.q
```

- Exchange、Queue 和 Binding 都是 durable、non-auto-delete。
- 工作、重试和 DLQ 使用 quorum queue；本地单节点只验证语义，生产高可用需要 RabbitMQ 集群。
- 重试队列以 TTL 到期后通过 DLX 返回主 Exchange。
- 重试队列启用 quorum at-least-once dead-lettering、`reject-publish` overflow 和有限 max-length，避免 TTL 转发静默丢失。
- 所有消息标记为 persistent。
- 第一版不使用 delayed-message 插件、Kafka、Redis 锁或临时匿名队列。

## 12. 消息契约

JSON 消息固定为：

```json
{
  "schemaVersion": 1,
  "eventId": 401,
  "eventType": "1",
  "tenantId": 1,
  "knowledgeBaseId": 11,
  "documentId": 101,
  "documentVersionId": 201,
  "processingJobId": 301
}
```

规则：

- `eventId` 使用 Outbox 主键，其他 ID 来自 N2.1 已提交事实。
- Consumer 不信任消息声明的关联关系，必须从 MySQL 加载并交叉校验。
- 消息和 Header 不包含 Secret、Authorization、Session、CSRF、原文件正文、Bucket、Object Key、SHA-256、预签名 URL 或完整异常堆栈。
- `x-docquery-retry-count` 从 0 开始，只由 DocQuery Consumer 维护。
- 未知 `schemaVersion`、未知事件类型、缺字段或非法 ID 视为不可重试消息。

## 13. Consumer 与任务租约

### 13.1 为什么需要租约

只把 Job 从 PENDING 改成 RUNNING 不足以处理进程崩溃：崩溃后重复消息会看到永久 RUNNING。N2.2 通过 V5 为 `processing_job` 增加：

- `lease_owner VARCHAR(128) NULL`
- `lease_until DATETIME(6) NULL`
- `(status, lease_until, id)` 恢复索引

领取 Job 时使用条件更新；PENDING 或租约已过期的 RUNNING Job 才能被当前实例领取。长任务通过心跳续租，更新必须匹配当前 owner。

### 13.2 消费行为

- Listener 使用手动 ACK 和 per-consumer prefetch。
- 先验证消息、版本、Job、Tenant 和状态，再领取租约。
- 已经成功的 Job 收到重复消息时直接 ACK；已经失败的 Job 不重复执行业务，但会把同一稳定消息 ID 再投递到 DLQ 后 ACK，避免“失败事实已提交、首次 DLQ 发布前崩溃”造成运维副本丢失，因此 DLQ 消费方必须容忍重复。
- 其他实例持有未过期租约时，ACK 当前冗余副本，不并发处理同一 Job；正在处理的原消息若因进程崩溃未 ACK，RabbitMQ 仍会重投，并在 MySQL 租约过期后接管。
- 处理成功后才 ACK；重试消息或 DLQ 消息获得 Publisher Confirm 后才 ACK 原消息。
- 进程崩溃导致 Channel 关闭时，RabbitMQ 重投；MySQL 租约到期后可以安全接管。

### 13.3 N2.2 的诚实边界

N2.2 尚无解析到索引的完整 `DocumentIngestionProcessor`，因此生产 Listener 默认不启动：

- N2.2 实现真实 Consumer 编排、租约、重试和死信组件。
- 集成测试注入受控测试 Processor，验证成功、重复、暂时失败、永久失败和崩溃恢复。
- Outbox 可以正常发布，消息在 durable 主队列积压，文档保持 PROCESSING。
- 只有后续阶段具备完整处理器后才启用生产 Listener；不能用 no-op Processor ACK 并丢弃任务，也不能伪造 SUCCEEDED/READY。

默认 Consumer 参数：并发 1、prefetch 1、任务租约 15 分钟、每 1 分钟续租，均允许按部署覆盖。

## 14. 自动重试与 DLQ

自动重试是消息处理的技术重试，不等于管理员对 FAILED Job 发起的新 `attempt_no`；后者不在 N2.2。

- 可重试：对象存储短暂不可用、数据库连接短暂失败、后续处理器声明的暂时依赖错误。
- 不可重试：消息结构非法、资源关系不一致、对象引用永久缺失、未知事件版本。
- 初次处理失败后依次进入 5 秒、30 秒、300 秒重试队列，共 3 次自动重试。
- 每次向重试 Exchange 发布都等待 Confirm；失败则 NACK/requeue 原消息。
- 第 4 次失败或不可重试错误，先以事务记录 Job/Version 的脱敏失败事实，再把消息 Confirm 发布到 DLQ，最后 ACK 原消息。
- 失败记录不得修改 Document 的 `activeVersionId`；旧 READY 版本继续服务。
- DLQ 只保存运维排查副本，MySQL Job/Version 才是失败业务事实。

## 15. 错误契约

上传接口沿用 N2.1 错误，并补充/落地：

| HTTP | 错误码 | 行为 |
| --- | --- | --- |
| `400` | `INVALID_UPLOAD_FILE` | 文件为空、文件名非法或 multipart 缺失 |
| `403` | 既有管理面权限错误 | 不写对象、不写数据库 |
| `404` | 既有资源不存在错误 | 不写对象、不写数据库 |
| `409` | N2.1 幂等/版本/内容冲突 | 清理本次未引用对象 |
| `413` | `FILE_TOO_LARGE` | 流式计数超限，终止上传并清理部分对象 |
| `415` | `UNSUPPORTED_DOCUMENT_FORMAT` | 扩展名不属于首批格式 |
| `503` | `OBJECT_STORAGE_UNAVAILABLE` | 对象未可靠保存，数据库不得受理 |

RabbitMQ 不可用不让已经成功保存文件并提交数据库的上传请求返回失败；此时 Outbox 保持 PENDING，版本保持 PROCESSING，Publisher 恢复后继续发送。

## 16. 已确认的依赖、镜像与配置边界

### 16.1 Maven

- `spring-boot-starter-amqp`：版本由 Spring Boot 4.1.0 管理。
- Java S3 Client 使用 AWS SDK for Java `2.47.5` BOM，并只引入 `software.amazon.awssdk:s3` 与同步 `apache5-client`。
- 第一版使用同步 `S3Client` 配合 Servlet 流式上传，不引入 CRT、Transfer Manager 或异步上传链路。
- Endpoint、Region、Access Key、Secret Key 和 path-style 开关均由配置提供；SeaweedFS 本地端点使用自定义 Endpoint，OSS 适配必须使用其要求的虚拟主机访问方式并通过契约测试。
- `org.testcontainers:testcontainers-rabbitmq`：测试版本沿用项目 Testcontainers 2.0.5 BOM/管理版本。
- SeaweedFS 对象存储测试使用 `GenericContainer`，不虚构不存在的官方 Testcontainers 专用模块。

### 16.2 本地 Compose

- RabbitMQ 使用官方固定补丁版本 `rabbitmq:4.3.4-management`，容器端口为 `5672/15672`；本地宿主默认发布为 `25672/15672`，避开当前 Windows/WSL2 的 TCP 动态排除段，并允许环境变量覆盖。服务使用独立命名卷和 `restart: "no"`。
- SeaweedFS 固定为 `chrislusf/seaweedfs:4.40`，以 `weed mini` 单节点方式提供本地 S3 API、私有 Bucket 和独立命名卷。
- Compose 中的单节点配置不得复制为生产高可用方案。
- 所有密码来自环境变量；仅允许显式的本地开发默认值，不在日志输出。
- 服务提供 healthcheck，DocQuery 应用配置不因 Compose 启动而自动运行。


Mapper 只增加对象引用检查、Outbox 领取/完成/失败和 ProcessingJob 租约所需方法。不创建 Parser、AI、ES、Redis 或检索目录占位文件。

## 18. 验收测试

### 18.1 上传与对象

- 四类允许扩展名可真实上传并由对象存储读回相同字节。
- 数据库中的实际大小和 SHA-256 与上传内容一致。
- SeaweedFS/S3 写入失败时没有 Document/Version/Job/Outbox。
- 数据库受理任一步失败时本次对象被立即删除，模拟删除失败后由回收器最终清理。
- 幂等顺序和并发重放只留下一个被数据库引用的对象。
- 超限、空文件、非法文件名和不支持格式不留下对象或数据库事实。

### 18.2 Outbox

- RabbitMQ 中断时 Outbox 保持 PENDING，`available_at` 按退避推进。
- RabbitMQ 恢复后事件最终 SENT 且主队列收到消息。
- NO_ROUTE、NACK、Confirm 超时都不能标记 SENT。
- 发布成功但标记 SENT 前崩溃，租约到期后允许重复消息。
- 两个 Publisher 实例不会同时拥有同一未过期租约。

### 18.3 Consumer、重试和死信

- 相同消息重复投递只允许一个有效任务租约和一次测试业务副作用。
- Consumer 领取后崩溃，Rabbit 重投且 MySQL 租约到期后可恢复。
- 暂时失败按 5 秒、30 秒、300 秒顺序重试；三个 TTL 均为可覆盖配置，集成测试统一覆盖为 1 秒并验证初次执行加 3 次重试。
- 永久失败和重试耗尽进入 DLQ，并形成 Job/Version FAILED 事实。
- DLQ 或重试 Exchange 不可路由时原消息不能被 ACK 丢失。
- 消息、日志、HTTP 响应和错误摘要不泄露对象键、摘要、文件正文或凭证。

### 18.4 边界和回归

- N2.2 不产生 READY，不修改 activeVersion，不生成解析或索引事实。
- 未提供生产 Processor 时 Listener 不启动，消息保留在 durable 队列。
- Testcontainers 使用临时 MySQL、RabbitMQ 和对象存储，不访问 Compose 持久卷。
- 完整 `./mvnw.cmd clean verify` 通过并报告测试数量。
