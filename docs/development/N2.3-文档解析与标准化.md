## 1. 阶段门禁

用户已确认本文的范围、解析输出、数据模型、失败边界和验收点，并于 2026-08-05 明确说“确认开始 N2.3”。本阶段实现和自动化验证完成后，用户又于 2026-08-06 明确确认“N2.3 完成”。

该确认正式关闭 N2.3。N2.4 随后取得单独实施授权并完成实现与验证，已于 2026-08-10 经用户确认完成；这不改变 N2.3 已关闭的范围。

## 2. 产品结果

N2.3 要把 N2.2 已可靠保存的原文件，转换成一份无模型、可追溯、可重复读取的标准化文档事实：

- 支持文本型 PDF、DOCX、TXT 和 Markdown。
- 保留按原始顺序排列的正文证据块。
- 只根据文件中真实存在的标题建立标题树。
- 每个证据块都能回到页码、段落或行号等原始位置。
- 将解析结果保存为一个不可变的标准化对象，并在 MySQL 保存小型清单。
- 为 N2.4 的检索卡生成和 N2.5 的 BM25 原文投影提供稳定输入。

N2.3 完成后，文档版本仍保持 `PROCESSING`，不会产生可对外检索的 `READY` 版本。

## 3. 本阶段范围

### 3.1 实现范围

- 四种格式的显式 Parser Adapter，不进行不受控的通用格式猜测。
- 文件真实格式、可解析性、编码和资源上限校验。
- 标准化正文 `EvidenceBlock`。
- 根节点和真实标题组成的 `HeadingNode` 树。
- PDF 页码、DOCX 正文元素、Markdown 源码行、TXT 行号的位置映射。
- 单个不可变 `canonical.jsonl` 派生对象及 MySQL 清单。
- 解析结果的结构、范围、校验和与幂等校验。
- 正常格式样本、无标题样本和不支持文件测试。

### 3.2 明确不做

- 不调用 Chat Model 或 Embedding Model。
- 不做语义切分、Contextual Retrieval、RAPTOR 或模型生成的虚拟目录。
- 不生成 `DocumentProfile`、`RetrievalNode` 检索卡、摘要、主题、别名或可回答问题。
- 不接入 Elasticsearch，不建立 BM25 或向量索引。
- 不实现查询、Agent、回答或引用接口。
- 不做扫描件 OCR、图片语义、公式识别、复杂表格结构恢复或复杂版面模型。
- 不把文档版本改为 `READY`，不切换 `activeVersionId`，不把 `ProcessingJob` 标记为成功。
- 不在本阶段开放新的 HTTP API。
- 不在完整入库处理器存在前开启生产 RabbitMQ Listener。

## 4. 核心方案

### 4.1 N2.3 做结构感知解析，不做最终检索切分

“不做固定长度 Chunk”不等于“不拆开文档”。N2.3 仍会把文档拆成可定位的证据块，但边界优先来自原文件结构：

| 格式 | N2.3 的证据块边界 |
| --- | --- |
| PDF | 物理页内按阅读顺序恢复出的标题、段落、列表项或文本块 |
| DOCX | 标题、段落、列表项、表格单元格文本、代码或预格式段落 |
| Markdown | AST 中的标题、段落、列表、引用和代码块 |
| TXT | 由空行分隔的段落，保留起止行号 |

这些 `EvidenceBlock` 是标准化原文的可追溯存储单元，不是语义向量 Chunk。它们不生成 Embedding，也不直接决定最终回答上下文。

如果一个源元素异常巨大，只按句号、换行等自然边界做无重叠的安全拆分，并通过 `continuationGroupId` 表明它们原本属于同一元素。这个拆分只用于控制单条记录大小，不创造新章节或新语义。

### 4.2 真实标题树不需要大模型总结

标题树由确定性规则形成：

1. 建立一个必有的文档根节点。
2. 按源文件顺序读取真实标题及其级别。
3. 使用标题级别栈寻找最近的更浅父标题。
4. 同级标题关闭上一个同级章节；更浅标题同时关闭其后代章节。
5. 标题级别发生跳跃时保留原级别、连接到最近的真实父节点并记录警告，不补造不存在的中间标题。

根节点只是文档容器，可使用 MySQL 中的逻辑文档名称作为显示名；它不冒充文件中的真实标题。只有真实标题才能创建根节点之外的 `HeadingNode`。

封面或首页中只用于标识整份文档的主标题保存为 `TITLE` 证据块，并归属于根节点，不单独创建章节节点。只有确实引出后续章节正文的标题才创建非根节点。

因此：

- PDF 有多个一级标题时，得到根节点和这些一级节点。
- 文档只有一个封面标题、没有章节标题时，标题文本仍作为原文证据保存，但标题树只有根节点。
- 文档没有任何标题时同样只有根节点，这不是解析失败。

### 4.3 PDF 不只读取书签

PDFBox 不只用于书签。N2.3 按以下优先级识别可验证的真实标题：

1. PDF Tagged Structure 中能够映射到可见文本的 `H1`–`H6`。
2. 能够解析到目标页，并能在目标位置附近找到对应可见文本的 Outline/书签。
3. 普通单栏 PDF 中，根据字号、字重、上下留白、行长、重复样式和页面位置共同判断的高置信可见标题。

可见样式识别必须满足组合条件，不能因为“一行字比较大”就生成标题。重复页眉页脚、页码、图表编号和孤立短句应先排除。不同标题样式按稳定的视觉层级映射为级别。

如果结构和样式证据冲突或置信不足，宁可把文本保留在根节点正文中并记录警告，也不创建不可靠标题。第一版只承诺普通文本型、正常阅读顺序的单栏 PDF；复杂多栏、旋转排版或无法确定阅读顺序的文件不静默产出错误结果。

### 4.4 为什么现在不选语义切分、上下文检索或 RAPTOR

- 语义切分依赖 Embedding 或模型阈值，会让“标准化事实”随模型版本改变，适合作为后续可重建投影，不适合作为 N2.3 唯一原文。
- Contextual Retrieval 是给已有检索块补充上下文的索引增强方式，不是文件解析方式。
- RAPTOR 需要模型递归摘要并建立语义树，成本、稳定性和评测工作都高于当前校招项目的必要范围。
- N2.3 先保证原文、结构和位置正确。完整链路完成后，再用精简问题清单验证真实标题树方案的薄弱点。

后续如果基线效果确实不足，可以从“给无标题长文增加派生语义段落”或“给证据块增加上下文”开始，不需要推翻 N2.3 的标准化原文。

## 5. 对象与数据关系

```text
DocumentVersion
├─ source object                 原始上传文件，N2.2 已保存
└─ DocumentCanonicalArtifact    N2.3 新增的一份标准化派生对象清单
   └─ canonical.jsonl object     正文、真实标题树和位置映射
```

每个文档版本最终是“一个原文件对象 + 一个标准化派生对象”，不是再生成 `content.txt` 和 `structure.json` 两个派生对象。

选择单个 `canonical.jsonl` 的原因：

- 正文、标题和位置映射在同一个校验和下提交，不存在两对象只成功一个的原子性问题。
- JSONL 可以逐条读取，不要求把长文全文一次性加载到内存。
- N2.4 和 N2.5 可以从它重建自己的模型卡片或 ES 投影。
- 原文件仍保留，标准化规则升级时可以重新解析。

MySQL 只保存清单和完整性信息，不保存全文 BLOB。Elasticsearch 在 N2.5 只是可重建投影，也不替代标准化对象。

## 6. MySQL 清单模型

实施后计划新增 `document_canonical_artifact`，一行代表一个已经完整写入并通过校验的标准化对象：

| 字段 | 建议类型 | 说明 |
| --- | --- | --- |
| `id` | `BIGINT` | 自增主键 |
| `tenant_id` | `BIGINT` | 冗余可信租户范围，逻辑外键 |
| `document_version_id` | `BIGINT` | 文档版本逻辑外键，第一版唯一 |
| `schema_version` | `INT UNSIGNED` | `canonical.jsonl` 结构版本，第一版为 1 |
| `source_format` | `VARCHAR(32)` | 与 DocumentVersion 已确认格式一致 |
| `parser_name` | `VARCHAR(64)` | DocQuery 解析器名称 |
| `parser_version` | `VARCHAR(32)` | 解析规则版本，不只记录第三方库版本 |
| `canonical_bucket` | `VARCHAR(63)` | 私有对象所在 Bucket |
| `canonical_object_key` | `VARCHAR(1024)` | 不可变对象 Key，全局唯一 |
| `canonical_size_bytes` | `BIGINT` | JSONL 对象实际字节数 |
| `canonical_sha256` | `CHAR(64)` | 整个 JSONL 对象 SHA-256 |
| `canonical_text_sha256` | `CHAR(64)` | 按规则重建的标准化全文 SHA-256 |
| `text_length` | `BIGINT` | 标准化全文 UTF-16 code unit 数量 |
| `block_count` | `INT UNSIGNED` | 证据块数量 |
| `heading_count` | `INT UNSIGNED` | 包含根节点的标题节点数量 |
| `warning_count` | `INT UNSIGNED` | 非致命解析警告数量 |
| `page_count` | `INT UNSIGNED NULL` | PDF 物理页数，其他格式为空 |
| `created_at` | `DATETIME(6)` | UTC 创建时间 |

约束：

- `document_version_id` 唯一，第一版每个不可变版本只保留一份有效标准化事实。
- `(canonical_bucket, canonical_object_key)` 唯一。
- 表中不增加 `status`；行存在即表示对象已完整写入并校验，处理中的临时状态仍属于 `ProcessingJob`。
- Parser 或 Schema 升级后的批量重建策略不在 N2.3 首版中实现，不能在普通重试中静默改写既有事实。

标准化对象可与原文件共用当前私有 S3 兼容存储，使用独立前缀；不增加新的对象存储产品。推荐 Key：

```text
canonical/{tenantId}/{documentVersionId}/v1/{randomUuid}.jsonl
```

随机物理 Key 防止重试覆盖已有对象，DocumentVersion ID 才是业务幂等身份。

## 7. Canonical JSONL v1

### 7.1 记录类型

一个对象由以下记录组成：

```text
header
block *
heading *
warning *
footer
```

- `header`：Schema、版本、源格式、源文件 SHA-256、Parser 和生成时间。
- `block`：按原文件阅读顺序排列的标准化原文证据。
- `heading`：根节点和真实标题树，按树的前序顺序排列。
- `warning`：不会导致失败，但需要评测或运维关注的降级事实。
- `footer`：计数、标准化全文 SHA-256 和完整性结束标志。

`footer` 必须存在且计数与实际记录一致；缺少 Footer 的对象视为未完成对象，不能写入 MySQL 清单。

### 7.2 Header 示例

```json
{"recordType":"header","schemaVersion":1,"documentVersionId":201,"sourceFormat":"PDF","sourceSha256":"...","parserName":"docquery-canonical-parser","parserVersion":"1","generatedAt":"2026-08-05T12:00:00Z"}
```

### 7.3 EvidenceBlock

核心字段：

| 字段 | 含义 |
| --- | --- |
| `blockId` | `{documentVersionId}:b:{六位顺序号}`，同一输入和 Parser 版本下稳定 |
| `ordinal` | 从 0 连续递增的阅读顺序 |
| `kind` | `TITLE`、`HEADING`、`PARAGRAPH`、`LIST_ITEM`、`TABLE_CELL`、`CODE_BLOCK` 等 |
| `text` | 标准化后的原文，不保存模型改写文本 |
| `canonicalStart` | 标准化全文中的 0-based 起点 |
| `canonicalEnd` | 标准化全文中的 half-open 终点 |
| `headingNodeId` | 当前真实章节；无标题内容引用根节点 |
| `continuationGroupId` | 只有超大源元素被安全拆分时存在 |
| `sourcePosition` | 格式专属原始位置 |

标准化全文定义为所有 `block.text` 按 `ordinal` 使用两个换行符连接，末尾不额外添加换行。`canonicalStart` 和 `canonicalEnd` 使用 Java/Lucene 一致的 UTF-16 code unit、0-based、左闭右开规则。

文本标准化只做证据读取所需的确定性处理：

- 换行统一为 `\n`。
- 去掉文件 BOM 和块边界的空白行。
- PDF 恢复明确的单词间空格，并把同一段的视觉换行合并。
- 普通段落不做大小写转换、词干化、同义改写或 Unicode 兼容归一化。
- Markdown 代码块和预格式文本保留内部空白。

### 7.4 HeadingNode

核心字段：

| 字段 | 含义 |
| --- | --- |
| `nodeId` | 根为 `{documentVersionId}:h:root`，其他节点使用稳定顺序号 |
| `parentNodeId` | 根为空，其他节点指向真实父节点 |
| `declaredLevel` | 源文件声明或可验证样式得到的标题级别 |
| `depth` | 在实际树中的深度，根为 0 |
| `title` | 文件中真实可见的标题文本；根节点显示名来自逻辑文档名称 |
| `sourceHeadingBlockId` | 真实标题对应的原文块；根节点为空 |
| `detectionSource` | `PDF_TAG`、`PDF_OUTLINE`、`PDF_VISIBLE_STYLE`、`DOCX_OUTLINE` 或 `MARKDOWN_HEADING` |
| `sectionStartBlockOrdinal` | 章节范围起点 |
| `sectionEndBlockOrdinalExclusive` | 下一个同级或更浅标题前的范围终点 |

HeadingNode 只表达导航结构，不包含摘要、主题、别名、问题或向量。

### 7.5 SourcePosition

| 格式 | 必备位置 |
| --- | --- |
| PDF | 1-based `pageNumber`、页内 `blockOrdinal`、页内字符起止位置 |
| DOCX | 0-based `bodyElementIndex`；段落或表格的行、列、单元格内段落位置 |
| Markdown | 1-based 起止行、起止列 |
| TXT | 1-based 起止行 |

坐标用于让后续系统说明“来自第几页、哪一段或哪几行”。N2.3 不直接生成面向最终用户的引用格式。

## 8. 各格式解析规则

### 8.1 PDF

首版依赖 Apache PDFBox，支持未加密或允许文本提取、具有可靠阅读顺序的文本型单栏 PDF。

- 按物理页读取，不把印刷页码误当作物理页码。
- 提取可见文本及字号、字重、坐标等布局事实。
- 排除在多页固定位置重复出现的页眉、页脚和页码后，再判断可见标题。
- Tagged Structure、书签和可见样式最终都必须落到真实可见文本块。
- 页面没有正文可以记录警告；整份文档没有可提取文本则失败。
- 检测到明显多栏、旋转文本主导或阅读顺序无法稳定确定时，返回不支持，不输出“看似成功但顺序错误”的标准化原文。

不支持 OCR、图片文字、复杂表格结构、脚注关联、数学公式语义和精确视觉还原。

### 8.2 DOCX

首版依赖 Apache POI `poi-ooxml`。

- 按 `document.xml` 正文顺序读取段落和表格。
- 标题来自 OOXML outline level、Heading 样式及其样式继承关系，不依赖英文样式名硬编码。
- 手工把普通段落调大加粗但没有标题语义的内容，第一版保留为正文，不强行生成标题。
- 列表项保留列表层级；表格按行、列读取单元格文本，但不恢复合并单元格语义。
- 页眉、页脚、批注、修订历史、文本框、宏和嵌入对象不进入正文主链路。

### 8.3 Markdown

首版依赖 CommonMark Java，并开启 Source Span。

- ATX 和 Setext 标题形成真实标题树。
- 段落、列表、引用和代码块按 AST 顺序输出。
- 链接保留可见文本；URL 是否作为独立词项由 N2.5 决定。
- 标准 CommonMark 之外的表格或原始 HTML 不恢复结构，但可见源码文本不能静默丢失。

### 8.4 TXT

首版使用 JDK 严格 UTF-8 解码，允许 UTF-8 BOM。

- 不自动猜测 GBK、Big5 或系统默认编码。
- NUL、非法 UTF-8 或二进制特征导致失败。
- 空行分隔段落，保留真实起止行号。
- TXT 没有可靠标题语义，首版标题树只有根节点。

## 9. 格式与资源安全

扩展名只决定候选 Adapter，Parser 还必须验证实际文件：

- PDF 必须具有合法 PDF 头和可读取结构。
- DOCX 必须是合法 OOXML 包，并包含必要的 Word 部件。
- Markdown/TXT 必须通过严格 UTF-8 和文本特征校验。

所有 Parser 共享以下限制：

- 原文件仍受 N2.2 的 50 MiB 上限约束。
- PDF 页数、DOCX 解压规模、证据块数量、标准化文本大小和单块大小均有可配置硬上限。
- 超限使用稳定错误码失败，不能只依赖 JVM OOM。
- 不执行宏、不加载外部链接、不访问文档声明的外部资源。
- Parser 临时资源在成功、失败和超时后都必须关闭或清理。

首版默认值冻结为：

| 配置 | 默认值 | 目的 |
| --- | --- | --- |
| `max-pdf-pages` | 2,000 | 避免极端页数占用处理线程 |
| `max-docx-expanded-bytes` | 200 MiB | 配合 POI 压缩包保护限制解压膨胀 |
| `max-canonical-bytes` | 100 MiB | 限制标准化 JSONL 和正文膨胀 |
| `max-blocks` | 200,000 | 限制结构记录数量 |
| `max-block-chars` | 65,536 UTF-16 code units | 只对异常大源元素做连续安全拆分 |

这些是安全上限，不是检索调参。实现时集中放入 `docquery.parsing` 配置并做边界测试；后续只有运行证据表明确需调整时才修改。

## 10. 解析流程与幂等

```text
按 documentVersionId 读取 MySQL 可信事实
→ 通过 SourceObjectStore 打开原文件
→ 校验实际格式、资源上限和可解析性
→ 选择显式格式 Adapter
→ 生成 EvidenceBlock、HeadingNode、SourcePosition 和 Warning
→ 校验文本、范围、树和位置映射
→ 写入随机 Key 的单个 canonical.jsonl 并计算 SHA-256
→ 读回/HEAD 校验对象大小和完整性
→ 插入 document_canonical_artifact 清单
→ 返回已验证的 artifactId
```

N2.3 的业务幂等身份是 `documentVersionId`：

1. 如果清单已存在且对象大小、校验和可验证，直接复用，不重复解析。
2. 如果两个执行者并发生成，数据库唯一约束只允许一个清单成功，失败者只删除自己创建的精确对象。
3. 对象写入成功但数据库插入失败时立即删除本次精确对象。
4. 删除失败或进程在插入前崩溃时，由只扫描 `canonical/` 前缀、具有宽限期且逐个检查数据库引用的安全回收任务兜底。
5. 数据库状态未知、对象年龄不足或引用检查失败时不删除。

这延续 N2.2 的“立即清理 + 延迟兜底”，不引入对象存储和 MySQL 的伪分布式事务。

## 11. 校验规则

标准化对象写入 MySQL 前必须同时满足：

- Header、Footer 和 Schema Version 合法。
- `block.ordinal` 从 0 连续递增，Block ID 唯一。
- 按定义重建的全文与所有 canonical range 完全一致。
- 每个证据块有且只有一个合法 SourcePosition。
- 标题树只有一个根、无环，所有父节点和标题原文块存在。
- 每个非根标题都能映射到文件中真实可见的标题证据。
- 章节范围合法并覆盖对应标题后的连续证据。
- Footer 计数、标准化文本 SHA-256、对象 SHA-256 与 MySQL 清单一致。
- 解析结果至少包含一个非空证据块。

任何核心校验失败都不能保存成功清单。

## 12. 失败与警告契约

### 12.1 不可重试失败

| 错误码 | 场景 |
| --- | --- |
| `DOCUMENT_FORMAT_MISMATCH` | 扩展名与真实文件结构不符 |
| `DOCUMENT_VERSION_NOT_FOUND` | 指定文档版本不存在 |
| `DOCUMENT_VERSION_NOT_PROCESSING` | 文档版本已不处于可生成标准化对象的 `PROCESSING` 状态 |
| `DOCUMENT_CORRUPT` | PDF、DOCX 或文本结构损坏 |
| `ENCRYPTED_DOCUMENT_UNSUPPORTED` | 加密或禁止文本提取 |
| `PDF_NO_EXTRACTABLE_TEXT` | 整份 PDF 没有可用文本，通常是扫描件 |
| `PDF_COMPLEX_LAYOUT_UNSUPPORTED` | 主体阅读顺序无法可靠确定 |
| `TEXT_ENCODING_UNSUPPORTED` | TXT/Markdown 不是合法 UTF-8 文本 |
| `DOCUMENT_PARSE_LIMIT_EXCEEDED` | 页数、解压规模、文本或记录数超过上限 |
| `CANONICAL_VALIDATION_FAILED` | 输出树、范围或校验和不一致 |
| `SOURCE_OBJECT_MISSING` | MySQL 引用的原文件永久不存在 |
| `SOURCE_OBJECT_INTEGRITY_MISMATCH` | 原文件实际大小或 SHA-256 与 MySQL 可信事实不一致 |

### 12.2 可重试失败

| 错误码 | 场景 |
| --- | --- |
| `SOURCE_OBJECT_UNAVAILABLE` | S3 兼容对象存储暂时不可读 |
| `CANONICAL_OBJECT_UNAVAILABLE` | 标准化对象暂时无法写入或校验 |
| `PROCESSING_DATABASE_UNAVAILABLE` | 解析清单暂时无法读写 |

Parser 使用带 `code` 和 `retryable` 的受控异常；完整处理器以后再映射到 N2.2 已有的 Consumer 重试和失败契约。异常消息不能包含正文、Bucket、Object Key 或第三方完整堆栈。

### 12.3 非致命警告

以下情况允许成功，但写入 Warning：

- `NO_REAL_HEADINGS`：只有根节点。
- `HEADING_LEVEL_JUMP`：真实标题级别发生跳跃，未补造中间标题。
- `PDF_OUTLINE_UNRESOLVED`：部分书签无法映射到可见文本，已忽略。
- `EMPTY_SOURCE_PAGE`：PDF 个别页面没有正文。
- `STRUCTURE_FLATTENED`：表格等结构保留了文本，但没有恢复完整结构语义。

警告不是用户可见状态，也不能用于伪造额外标题。材料级文本丢失、顺序不确定或输出不完整必须失败，不能降级为警告。

## 13. 依赖边界

| 格式 | 选择 | 原因 |
| --- | --- | --- |
| PDF | Apache PDFBox | 可读取文本、物理页、书签、Tagged Structure 和布局属性 |
| DOCX | Apache POI `poi-ooxml` | 直接读取 OOXML 段落、样式和表格 |
| Markdown | CommonMark Java | AST 和 Source Span 能同时保留结构与源码位置 |
| TXT | JDK Charset API | 严格 UTF-8 足够，无需额外探测库 |

第一版不引入 Apache Tika。当前只支持四种已知格式，并且需要格式专属的标题和位置规则；通用 Parser 不会替代这些 Adapter，反而会增加隐藏行为和依赖面。

实施时已结合工程实际的 Java 17、Spring Boot 4.1.0 和官方版本信息完成核验，`pom.xml` 固定为 Apache PDFBox 3.0.8、Apache POI 5.5.1 和 CommonMark Java 0.28.0；TXT 继续只使用 JDK API。没有引入 Apache Tika、模型、Elasticsearch 或 Redis 依赖。

## 14. 服务接口与最小代码边界

N2.3 只新增完成本阶段所需的边界：

```text
parser/DocumentFormatParser
parser/PdfDocumentParser
parser/DocxDocumentParser
parser/MarkdownDocumentParser
parser/TextDocumentParser
service/DocumentCanonicalService
service/CanonicalArtifactStore
service.impl/...
entity/DocumentCanonicalArtifactEntity
mapper/DocumentCanonicalArtifactMapper
config/DocumentParsingProperties
```

核心接口语义：

- `DocumentCanonicalService.ensureCanonical(documentVersionId)`：从 MySQL 加载可信版本和对象引用；已有有效清单时复用，否则完成解析、校验、对象写入和清单登记。
- `DocumentFormatParser.parse(ParseSource)`：格式 Adapter 只产生标准记录和受控警告，不访问数据库、不改变业务状态、不调用模型。
- `CanonicalArtifactStore`：供应商无关的派生对象写入、打开、校验、精确删除和有限前缀列举端口；可以与 `SourceObjectStore` 共用同一个 AWS SDK S3 Client 和 SeaweedFS 服务，但不能让 Parser 依赖 SeaweedFS 类。
- `DocumentCanonicalArtifactMapper`：只负责清单查询、插入、引用检查和回收所需数据库访问。

所有公开入口只接收稳定 `documentVersionId`；Bucket、Object Key、Tenant 和源格式从 MySQL 可信事实加载，不由调用方覆盖。N2.3 不创建 Controller、上传 DTO 或新的外部响应契约。

`DocumentCanonicalService` 只返回已验证的 Artifact ID/清单，不修改 `DocumentVersion`、`ProcessingJob` 或 `Document.activeVersionId`。解析失败只抛出受控失败，由后续完整处理器决定业务状态转换。

## 15. 与异步链路的衔接边界

N2.2 的生产 Listener 当前默认关闭，这是正确状态。N2.3 只提供可被完整入库处理器调用的解析与标准化能力，并通过 Service/集成测试直接验证。

不能在 N2.3 创建一个“只解析就返回成功”的生产 `DocumentIngestionProcessor`，否则 Consumer 会 ACK 消息，但 N2.4、N2.5 尚未执行，Job 也无法诚实完成。

生产 Listener 只有在后续完整处理器能够依次完成解析、检索卡、双索引、投影校验和 READY 切换后才开启。

## 16. N2.3 验收点

### 16.1 正常解析

- 文本型单栏 PDF：没有书签但有明显可见标题时，得到正确标题树、正文顺序和物理页码。
- 根节点 PDF：只有文档标题而没有章节标题时，只生成根节点，正文和页码不丢失。
- DOCX：Heading 层级、普通段落、列表和表格文本的顺序及位置正确。
- Markdown：ATX/Setext 标题、列表、引用、代码块和源码行位置正确。
- TXT：UTF-8/BOM、段落边界和行号正确，标题树只有根节点。

### 16.2 真实性与可追溯

- Golden Fixture 中的标准化全文逐字匹配预期，不能用只比较非空或块数量代替。
- 任取证据块，可根据 SourcePosition 找到原文件中的正确页、段落或行。
- 标题级别跳跃不会生成虚拟中间节点。
- 标题树每个非根节点都有真实标题原文块。
- JSONL 重建全文、范围、计数和两个 SHA-256 全部一致。

### 16.3 持久化与重复执行

- 每个 DocumentVersion 只有一个有效 MySQL 清单和一个被引用的标准化派生对象。
- 重复调用返回同一有效结果，不新增对象。
- 并发生成只保留数据库胜者，败者精确对象被清理。
- 数据库写入失败、对象写入失败和读回校验失败都不会留下有效清单。
- 超过宽限期且无数据库引用的 `canonical/` 对象可被安全回收；状态不明时不删除。

### 16.4 失败边界

- 扫描/纯图片 PDF、加密 PDF、损坏 PDF、损坏 DOCX、非法 UTF-8、格式伪装和资源超限分别返回稳定错误码。
- 明显复杂多栏或阅读顺序不确定的 PDF 不产生伪成功结果。
- 暂时对象存储/数据库失败标记为可重试，确定性文件失败标记为不可重试。
- 错误日志和数据库失败摘要不泄露正文或对象地址。

### 16.5 阶段边界

- 不新增模型、Embedding、Elasticsearch 或 Redis 依赖。
- 不产生 `DocumentProfile`、`RetrievalNode` 或向量。
- 不切换 `activeVersionId`，不产生 `READY`，不启用生产 Listener。
- N0、N1、N2.1、N2.2 既有自动化测试继续通过，并增加 N2.3 格式 Fixture 和对象持久化测试。

完整链路效果不作为 N2.3 验收条件；需要观察的检索薄弱点记录在 [`N2 检索与回答评测问题清单`](./N2-检索与回答评测问题清单.md)，待 N2.5/N3 链路完成后构建小型测试集验证。

## 17. 已确认并实现的设计结论

本设计建议一次确认以下结论：

1. N2.3 使用格式专属、无模型的结构感知解析。
2. 原文件之外只新增一个 `canonical.jsonl` 派生对象，MySQL 只存清单。
3. PDF 支持普通文本型单栏、书签/Tagged Structure 和高置信可见标题；复杂版面、扫描件和 OCR 不做。
4. `EvidenceBlock` 是可追溯原文单元，不是语义 Chunk；语义切分、Contextual Retrieval 和 RAPTOR 留给链路评测后的按需优化。
5. N2.3 不接管完整 Consumer 成功状态，不产生 READY，也不提前进入 N2.4。
