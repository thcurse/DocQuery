## 2. 三十秒说明

DocQuery 第一版不采用“固定长度 Chunk + Overlap + 全部 Chunk 向量化 + Top-K Chunk 直接回答”的传统主链路。

总体选择是：

- MySQL 保存文档、版本、处理任务、Outbox 和生效状态，是业务事实源。
- S3 兼容对象存储保存原文件和不可变标准化对象，默认自托管 Server 为 SeaweedFS。
- RabbitMQ 异步触发文档处理，Transactional Outbox 解决数据库提交与消息发布的可靠衔接。
- 四种格式使用无模型的结构感知解析，只保留真实标题、正文和原始位置。
- 后续由模型为文档和真实章节生成检索卡，Embedding 只负责语义导航。
- Elasticsearch 对原文做 BM25，对检索卡做向量导航；Java 使用 RRF 融合两路排名。
- 检索结果必须回到原文证据，受控 Agent 读取原文后才能回答。
- Redis 只负责检索/问答请求幂等和短期结果复用，不承担权限或文档处理正确性。

一句话概括：

> 向量负责导航，关键词负责定位，原文负责举证，Agent 负责受控地继续查找。

## 3. 总体数据流

### 3.1 文档入库

```text
上传文件
→ S3兼容对象存储保存原文件
→ MySQL事务创建DocumentVersion、ProcessingJob、OutboxEvent
→ Outbox Publisher发布documentVersionId
→ RabbitMQ至少一次投递
→ 生成标准化原文、真实标题树和位置映射
→ 生成DocumentProfile与真实章节RetrievalNode
→ 保存单一retrieval JSONL检索卡与导航向量产物
→ ES写入原文BM25投影和检索卡向量投影
→ 校验投影完整性
→ MySQL原子切换activeVersionId并将版本置为READY
```

### 3.2 查询与回答

```text
校验Application Credential和KnowledgeBase Grant
→ Redis处理请求幂等
→ ES原文BM25与检索卡KNN并行召回
→ Java RRF融合并返回原文地址
→ Retrieve读取原文证据
→ Answer受控Agent按需继续读取
→ 只根据已读取原文生成答案和引用
```

## 4. 组件职责

| 组件 | 第一版职责 | 是否业务事实源 |
| --- | --- | --- |
| MySQL | 租户、Grant、Document、Version、Job、Outbox、activeVersion、审计 | 是 |
| S3 兼容对象存储 | 原文件、canonical JSONL、retrieval JSONL | 原文件/canonical 是可追溯事实；retrieval 是可重建派生产物 |
| RabbitMQ | 暂存并分发处理消息 | 否，只负责传递 |
| Elasticsearch | 原文关键词投影、检索卡向量投影 | 否，可重建 |
| Redis | 查询请求幂等、执行状态、短期结果复用 | 否，可丢失 |
| Chat/Embedding Model | 生成检索卡、查询扩展、受控回答和导航向量 | 否，输出必须校验 |

第一版不增加独立向量数据库。Elasticsearch 同时承载全文字段和 `dense_vector` 导航字段。

## 6. 跨组件不变量

- 可信 `tenantId`、`applicationId` 和 `knowledgeBaseId` 必须来自服务端认证与授权上下文。
- MySQL 决定业务版本和可见性；ES、Redis、RabbitMQ 都不能改变业务事实。
- 每个外部投影使用稳定 `documentVersionId` 和确定性业务标识，支持至少一次执行。
- 新版本处理失败时，旧 `activeVersionId` 继续服务。
- 只有原文件、canonical 对象、检索卡和双索引全部校验成功后，后续阶段才允许进入 `READY`。
- 检索卡只能导航，不能充当最终答案证据；最终引用必须来自标准化原文。
- 所有检索通道在召回阶段就应用租户、知识库和生效版本过滤，不能全局召回后再删越权结果。
- 文档文本是不可信输入，不执行其中的提示或工具指令。

## 7. 主要取舍

| 决策 | 得到什么 | 接受什么 |
| --- | --- | --- |
| S3 兼容端口 + SeaweedFS | 本地可运行、服务端可替换 | 仍需验证目标部署环境的运维能力 |
| RabbitMQ + Outbox | ACK、重试、DLQ 和可靠发布边界清晰 | 至少一次投递要求消费者幂等 |
| 单个 canonical JSONL | 原文、结构、位置同一校验和提交 | 消费方需要按记录类型流式读取 |
| 真实标题树 | 结构可解释，不让模型篡改目录 | 无标题长文的语义导航粒度较粗 |
| BM25 + 检索卡向量 | 同时覆盖精确词和语义表达 | 需要两路索引、融合和评测 |
| 向量只做导航 | 最终证据回到原文 | 命中后需要额外读取，延迟更高 |
| LangChain4j 底层 API | 模型适配统一且 Agent 可控 | Agent 循环、预算和审计自行实现 |
| Redis 只做请求幂等 | 不污染权限和业务事实 | Redis 异常时需要显式降级或拒绝 |

## 8. 明确不做

- 固定长度 Chunk 和 Overlap 调参作为主链路
- 对全部原文块生成向量并直接回答
- 模型生成虚拟目录或伪标题树
- OCR、图片理解、复杂版面和复杂表格恢复
- GraphRAG、RAPTOR、知识图谱和独立向量数据库
- Kafka、通用 Agent 平台、多轮聊天记忆
- Redis 权限缓存、activeVersion 缓存或文档处理锁
- 第一版拆分独立 Worker

## 9. 面试说明顺序

1. 先讲问题：简化版固定 Chunk RAG 难以保证结构和证据完整性。
2. 再讲入库：对象存储保文件，MySQL 保事实，RabbitMQ + Outbox 保可靠触发。
3. 讲解析：无模型解析产生可追溯原文和真实标题树。
4. 讲检索：原文 BM25 与检索卡向量导航并行，Java RRF 融合。
5. 讲证据：检索卡只返回地址，Answer 必须读取原文。
6. 讲权限：两路检索都带租户、知识库和 activeVersion 过滤。
7. 最后讲不足：无标题长文粒度、模型卡遗漏、双路延迟都要通过小型评测验证。

重点不是声称“没有使用 RAG”，而是说明：

> DocQuery 把语义导航、全文定位和原文举证拆成了可独立验证的工程阶段。
