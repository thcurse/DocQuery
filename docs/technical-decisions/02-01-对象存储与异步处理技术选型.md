# DocQuery 对象存储与异步处理技术选型

> 适用阶段：N2.1、N2.2  
> 状态：方案已确认、实现并经用户验收  
> 日期：2026-08-05  
> 总览：[`N2 技术选型总览`](./02-文档检索与异步处理技术选型.md)  
> 实施证据：[`N2.1 文档数据模型与上传受理`](../development/N2.1-文档数据模型与上传受理.md)、[`N2.2 对象存储与异步投递`](../development/N2.2-对象存储与异步投递.md)

## 1. 选择结果

- MySQL 保存 Document、DocumentVersion、ProcessingJob、OutboxEvent 和版本可见性，是入库业务事实源。
- 原文件保存到 S3 兼容对象存储；Java 业务层依赖 `SourceObjectStore`，不依赖具体 Server SDK。
- 默认自托管 Server 使用 SeaweedFS，首个 Java Client 使用 AWS SDK for Java 2.x。
- RabbitMQ 负责文档处理工作消息，MySQL Transactional Outbox 负责数据库事务与消息发布的可靠衔接。
- Consumer 按至少一次投递设计，使用 MySQL 任务事实做幂等和租约，不使用 Redis 去重。

## 2. 为什么采用 S3 兼容抽象

DocQuery 需要的对象操作很小：

- Put：持久保存上传文件；
- Get：解析阶段读取原文件；
- Head/Exists：校验对象存在和大小；
- Delete：精确补偿删除；
- List：有限前缀扫描孤儿对象。

业务代码只依赖 `SourceObjectStore`，对象的 Bucket、Key、大小和 SHA-256 保存到 MySQL。这样可以：

- 本地或自托管环境使用 SeaweedFS；
- 阿里云部署时用 OSS 的 S3 兼容接入或新增 OSS Adapter；
- 迁移 Server 时保持上传、版本和任务领域模型不变；
- 通过同一组契约测试验证 Put/Get/Head/Delete/List 行为。

S3 兼容不表示所有供应商行为完全一致。切换 Server 时仍需验证签名、Path Style、分页、元数据、错误码和大文件行为。

## 3. 为什么默认选择 SeaweedFS

第一版需要本地 Docker 可启动、支持多节点演进、暴露 S3 API，并避免个人项目承担 Ceph 级别的运维复杂度。SeaweedFS满足这一定位：

- 本地可使用单进程/精简模式完成开发；
- 架构上支持 Master、Volume、Filer 和 S3 Gateway 的多节点部署；
- S3 API 能覆盖 DocQuery 当前使用的对象操作；
- 业务层仍保留可替换端口，不把 SeaweedFS 类型扩散到 Parser 或领域服务。

这不代表 SeaweedFS 是所有生产环境的唯一选择。若目标环境已经采购 OSS，直接采用托管 OSS 通常比自建集群更合理。

## 4. 为什么不是直接绑定 OSS

- 当前项目首先要求本地、离线和校招演示环境可完整运行，不能依赖云账号和持续费用。
- OSS 是具体云产品，直接把其 SDK、Bucket 规则和异常类型写进业务层会扩大供应商绑定。
- S3 兼容端口允许生产部署按已有基础设施替换，并不排斥 OSS。

面试时可以表述为：

> 默认部署选 SeaweedFS 是为了本地可复现；接口按对象存储能力抽象，企业已有 OSS 时可以替换 Adapter，而不是重新设计文档领域模型。

## 5. 上传与业务事实顺序

原文件对象和 MySQL 事务无法组成真正的分布式事务，第一版使用明确的顺序与补偿：

```text
管理权限和参数校验
→ 对象存储写入随机Key并计算大小/SHA-256
→ MySQL单事务创建DocumentVersion、ProcessingJob、OutboxEvent
→ 更新Document.latestVersionId
→ 提交后返回202 Accepted
```

对应规则：

- 对象写入失败，不创建数据库事实；
- 数据库提交失败，精确删除本次随机 Key；
- 删除失败或进程崩溃，由带宽限期、逐对象引用检查的回收器兜底；
- 数据库状态未知、对象年龄不足或引用检查失败时不删除；
- 幂等重放复用既有业务 ID，并清理本次多余对象。

内容哈希用于完整性、幂等和无意义重复判断，不能替代稳定 Document/DocumentVersion ID，也不能跨租户合并资源。

## 6. MySQL 四类入库事实

- `Document`：长期逻辑文档，区分 `activeVersionId` 与 `latestVersionId`。
- `DocumentVersion`：一次具体内容，保存版本号、对象引用、大小、SHA-256 和处理状态。
- `ProcessingJob`：版本处理尝试、租约、重试和失败摘要。
- `OutboxEvent`：与版本和任务同事务提交的待发布事件。

`activeVersionId` 与 `latestVersionId` 必须分开：新版本处理期间，旧 activeVersion 继续服务；只有后续双索引投影完整后才能切换。

## 7. 为什么选择 RabbitMQ

文档解析、模型调用、Embedding 和索引通常超过普通 HTTP 请求时长，需要：

- 快速返回上传受理结果；
- 工作消息 ACK；
- 有界重试和退避；
- 死信队列；
- 消费者并发控制；
- 应用重启后继续处理。

这是耗时工作队列，不是需要长期回放并供多个下游重复消费的事件流。RabbitMQ 的 ACK、重试和 DLQ 比 Kafka 更贴合第一版，而且团队不需要额外承担 Kafka 的分区、消费组和日志保留运维。

## 8. Transactional Outbox

直接执行“MySQL 提交后发送 RabbitMQ”会出现：

- 数据库成功、消息未发送；
- 消息发送成功、数据库回滚；
- 消息到达但发布状态未更新导致重复发送。

第一版在受理事务内同时写 `OutboxEvent(PENDING)`。事务提交后，Publisher 领取租约并发送；RabbitMQ Confirm 成功后标记 `SENT`。

这提供的是至少一次投递，不是恰好一次：

- RabbitMQ 暂时不可用时，Outbox 保持 PENDING；
- Confirm 超时或进程崩溃时允许重新发布；
- Consumer 必须基于稳定 `documentVersionId` 和 ProcessingJob 状态幂等处理。

## 9. Consumer 边界

Consumer 收到的消息只包含稳定 ID 和契约版本，不相信消息携带的租户、对象地址或业务状态。处理前重新从 MySQL 加载可信事实并交叉校验。

已落地的骨架包括：

- ProcessingJob 租约和心跳；
- 重复消息识别；
- 5 秒、30 秒、300 秒三级重试；
- 最终失败与 DLQ 边界；
- RabbitMQ durable 主队列、TTL 重试队列和死信队列。

生产 Listener 在完整 Processor 能完成 N2.3—N2.5 全链路前默认关闭。不能用只解析的空实现 ACK 消息并伪装任务成功。

## 11. 安全与失败边界

- Bucket、Object Key 和 tenantId 来自服务端可信事实，不允许请求覆盖。
- 对象 Key 使用随机/稳定业务前缀，日志不输出长期地址和原文。
- RabbitMQ 消息不包含 Secret、Authorization Header、文件正文或长期 URL。
- RabbitMQ 不可用时上传事实和 PENDING Outbox 可以保留，版本继续为 PROCESSING。
- 对象存储暂时失败与确定性文件失败必须区分重试属性。
- 不执行递归或宽前缀删除；补偿只删除本次精确对象，回收器逐对象检查数据库引用。

## 12. 明确不做

- 不把 Redis 用作 RabbitMQ 消费幂等或文档处理锁；
- 不用对象存储元数据代替 MySQL 业务事实；
- 不承诺跨 MySQL、对象存储和 RabbitMQ 的分布式事务；
- 第一版不拆独立 Worker，不引入 Kafka；
- N2.2 不解析正文、不生成检索卡、不切换 READY。
