# DocQuery 身份与授权技术选型

> 文档用途：解释技术选择、权衡和演进路线，便于设计复盘与面试说明  
> 不承担：阶段进度、数据库 DDL、接口实现记录和测试结果  
> 实现依据：[`N1-身份与授权.md`](../development/N1-身份与授权.md)

## 1. 三十秒说明

DocQuery 有两类调用者，因此不能用一套登录方式混在一起：

1. 管理员通过浏览器进入管理后台。
2. 传统业务后端通过应用凭证调用服务 API。

第一版的选择是：

- 管理员：本地账号、bcrypt 密码哈希、Spring Security、服务端 `HttpSession`。
- 浏览器：只持有 `HttpOnly` 的 `JSESSIONID` Cookie，并保留 CSRF 防护。
- 业务应用：使用独立的高熵 Application Credential，不使用管理员 Session。
- 授权：角色权限、固定租户范围和应用到知识库的 Grant 共同判断。
- 首个平台管理员：部署期交互命令创建，不提供注册或公开初始化接口。
- OIDC：不属于本个人项目的实施路线，只保留已有企业身份提供方场景下的知识扩展说明。

这套方案优先保证边界清楚、立即失效和实现可解释性，不为了“看起来现代”而引入 JWT 或自建 OAuth2 服务。

## 2. 先区分认证和授权

### 2.1 认证 Authentication

认证回答：

> 你是谁？

例如：

- 管理员账号和密码是否匹配。
- 一个 Application Credential 属于哪个 Application。
- 假设存在 OIDC 接入时，外部身份是否可信。

### 2.2 授权 Authorization

授权回答：

> 已经知道你是谁以后，你能做什么？

例如：

- 平台管理员能否创建租户。
- 租户管理员能否操作路径中的这个租户。
- 某个 Application 能否读取指定 KnowledgeBase。

认证成功不代表可以访问所有资源。DocQuery 必须在每次请求中继续判断角色、租户、资源状态和 Grant。

## 3. 项目约束

技术选择基于以下现实条件：

- 第一版是传统 Spring Boot 单体，不是多服务身份平台。
- 管理后台只有少量管理员。
- 需要支持本地独立部署，不能强制依赖企业身份提供方。
- 租户、应用、知识库和授权状态变更后，新请求需要立即失败。
- 业务系统拥有自己的终端用户，DocQuery 不接管业务用户登录。
- 项目重点是多租户知识库接入与授权，不是重新实现账号中心。

因此，“行业里功能最多的方案”不等于“当前最合适的方案”。

## 4. 总体身份模型

```text
管理面

管理员
  -> 本地密码
  -> Spring Security
  -> HttpSession / JSESSIONID
  -> 角色 + 固定 tenantId
  -> 管理 API

服务面

传统业务后端
  -> Application Credential
  -> 解析 Application + tenantId
  -> 检查 KnowledgeBase 和 READ Grant
  -> 服务 API
```

两条链路必须分离：

- 管理员 Session 不能调用服务 API。
- Application Credential 不能调用管理 API。
- 业务终端用户身份不进入 DocQuery。

## 5. 管理员身份验证选型

### 5.1 第一版：本地管理员账号

管理员账号由 DocQuery 保存：

- `login_name`
- `password_hash`
- `role`
- `tenant_id`
- `status`

优点：

- 不依赖外部身份平台，项目可以独立部署和演示。
- 容易验证平台管理员、租户管理员和跨租户隔离。
- Spring Security 已提供成熟的密码验证和 Session 防护。

局限：

- DocQuery 需要承担密码策略、管理员停用和未来密码重置。
- 无法直接复用企业 MFA、统一离职和单点登录能力。

因此它不是临时占位方案，而是当前个人项目的完整管理员认证方案。

### 5.2 可选知识扩展：OIDC 企业登录

OIDC，即 OpenID Connect，是建立在 OAuth 2.0 之上的身份协议。

本个人项目没有企业身份提供方，不计划实现 OIDC、部署 Keycloak 或接入 Auth0。以下内容只用于解释：如果真实部署方已经具备统一身份系统，DocQuery 可以怎样接入，而不是项目后续开发承诺。

典型流程：

```text
管理员点击企业登录
  -> 浏览器跳转到企业身份提供方 IdP
  -> IdP 完成密码、MFA 或 Passkey 验证
  -> IdP 返回一次性 Authorization Code
  -> DocQuery 后端交换并校验 ID Token
  -> 使用 issuer + subject 识别外部用户
  -> 映射到本地管理员、角色和租户
  -> 创建 DocQuery HttpSession
```

OIDC 接入后的边界：

- 企业 IdP 负责证明用户身份。
- DocQuery 不接触企业密码。
- DocQuery 仍负责本地角色、租户范围和资源授权。
- 外部身份应使用 `(issuer, subject)` 唯一标识，不能只依赖可能变化的邮箱。
- DocQuery 是 OIDC Client，不自行实现 Authorization Server。

OIDC 和 Session 不是二选一：

- OIDC 解决首次登录时如何证明身份。
- Session 解决登录后如何在连续请求中保持身份。

### 5.3 为什么项目不实现 OIDC

OIDC 需要额外准备：

- 可用的企业 IdP
- Client ID 和 Client Secret
- HTTPS 回调地址
- 外部用户与本地角色、租户的映射规则
- 单点退出和账号停用策略

这些工作不能证明 DocQuery 的核心知识库授权能力，反而会增加虚构的环境依赖。项目只在文档中保留清晰的概念边界，不把 OIDC 列为实施阶段。

## 6. 密码存储选型

### 6.1 选择

使用 Spring Security `DelegatingPasswordEncoder`，第一版编码格式使用 bcrypt。

数据库只保存类似下面的编码结果：

```text
{bcrypt}$2a$...
```

不保存：

- 明文密码
- 可解密密码
- 普通 SHA-256 密码摘要

### 6.2 为什么不能直接 SHA-256

用户选择的密码通常熵较低。SHA-256 计算速度很快，数据库泄露后，攻击者可以高速尝试密码字典。

bcrypt 属于自适应慢哈希：

- 每次计算故意消耗一定时间。
- 内部包含随机 Salt。
- 可以通过工作因子提高破解成本。

工作因子需要在目标运行环境实测，使一次密码验证达到可接受的安全成本，不能机械照搬固定参数。

### 6.3 为什么使用 DelegatingPasswordEncoder

编码结果带有 `{bcrypt}` 等算法标识，因此未来可以：

- 新密码改用更合适的算法。
- 登录成功后逐步升级旧哈希。
- 不需要一次性重置全部管理员密码。

选择 bcrypt 不代表它永远是唯一方案。后续可以评估 Argon2，但算法迁移不应改变业务账号模型。

### 6.4 当前落地参数

N1.3a 最初只引入 `spring-security-crypto`；N1.3b 已切换为包含同一密码组件的 `spring-boot-starter-security` 并启用 Web 登录链。bcrypt 默认工作因子为 `12`，可通过 `DOCQUERY_BCRYPT_STRENGTH` 调整。

密码至少 12 个字符，并且 UTF-8 编码后最多 72 字节。72 字节是 bcrypt 的算法输入边界；创建和登录必须在进入 PasswordEncoder 前执行相同检查，不能接受更长输入后依赖 bcrypt 截断。

工作因子 `12` 是当前可运行基线，不代表所有部署环境都固定使用该值。上线前应在目标硬件实测哈希耗时，在安全成本和管理员登录延迟之间重新确认参数。

## 7. 登录状态选型

### 7.1 选择

使用 Spring Security 标准 `HttpSession`：

```text
登录成功
  -> 服务端创建 HttpSession
  -> 浏览器收到随机 JSESSIONID Cookie
  -> 后续请求自动携带 Cookie
  -> 服务端恢复 Authentication
```

第一版规则：

- Session 保存在单体 JVM 内存中。
- 连续 8 小时无请求后失效；正常请求会重新计算空闲时间。
- 不通过前端机械心跳延长 Session，不提供 Remember Me。
- 服务重启后重新登录。
- 登出立即使当前 Session 失效。
- 不增加自定义 `admin_session` 表。
- 不提供 Remember Me 或 Refresh Token。

### 7.2 REST 登录如何保存到 Session

项目不使用会重定向 HTML 页面的表单登录，而是提供 JSON REST 接口。`AuthenticationManager` 只负责验证凭证；自定义 Controller 还必须完成：

1. 执行 Session Authentication Strategy，更换 Session ID 并清除旧 CSRF Token。
2. 创建包含认证结果的 `SecurityContext`。
3. 通过 `HttpSessionSecurityContextRepository` 显式保存。
4. 在 Principal 进入 Session 前清除密码哈希。

如果只调用 `AuthenticationManager.authenticate` 而不保存 SecurityContext，本次请求虽然验证成功，下一次请求仍会是未登录状态。

### 7.3 为什么不选择自定义数据库令牌

自定义不透明令牌需要自行实现：

- Token 生成和格式
- 数据库存储
- 摘要比较
- 到期和撤销
- 清理任务
- 认证过滤器

这些能力标准 `HttpSession` 已经提供。当前只有一个单体实例和少量管理员，自建令牌系统没有带来相应收益。

### 7.4 为什么不选择 JWT

JWT 的优势主要在于多个服务可以独立验证签名，减少集中 Session 查询。

但当前管理后台是单体浏览器应用，JWT 会额外引入：

- 签名密钥管理
- Access Token 到期
- Refresh Token
- 主动登出和吊销
- 浏览器安全存储
- 账号停用后的立即失效

JWT 在签发后通常会在有效期内自行成立。如果需要立即撤销，又要增加黑名单、短有效期或额外状态查询，削弱“无状态”的收益。

因此：

- 单体浏览器后台：优先 Session。
- 多个独立资源服务、跨系统令牌传递：再评估 OAuth2 Access Token/JWT。

“使用 JWT”不等于“安全性自动更高”。

### 7.5 将来多实例怎么办

第一版内存 Session 的局限是：

- 服务重启会退出登录。
- 多实例不能天然共享 Session。

需要水平扩容时，可以引入 Spring Session 和 Redis 等共享存储。浏览器仍使用 `JSESSIONID`，登录接口和授权模型不需要推翻。即使第一版为检索请求幂等引入 Redis，管理员 Session 仍保存在当前 JVM；“项目中存在 Redis”不等于已经启用 Spring Session。

## 8. Cookie、CSRF 和常见攻击防护

### 8.1 Cookie 设置

管理员 Cookie 使用：

- `HttpOnly`：JavaScript 不能直接读取 Session Cookie。
- `Secure`：生产环境只通过 HTTPS 发送。
- `SameSite=Lax`：降低跨站请求自动携带 Cookie 的风险。
- 合理的 Path 和超时时间。

当前实际配置为连续 8 小时无请求后过期、`HttpOnly=true`、`SameSite=Lax`。本地 HTTP 的 `Secure` 默认关闭，生产必须通过 `DOCQUERY_SESSION_COOKIE_SECURE=true` 开启并全程使用 HTTPS；不设置持久化 Max-Age。

登录成功后更换 Session ID，防止 Session Fixation。

### 8.2 为什么还需要 CSRF

浏览器会自动携带 Cookie。攻击者可能诱导已登录管理员从恶意网站发起修改请求。

因此状态修改请求需要第二个攻击者无法获知的 CSRF Token：

```text
JSESSIONID Cookie
    +
X-CSRF-TOKEN Header
    =
允许修改请求
```

登录本身也会创建认证状态，因此同样要求 CSRF Token。客户端先匿名获取 Token，登录成功后由于 Session ID 和 Token 都会轮换，需要再获取一次 Token，才能登出或提交其他修改请求。

登录和 `POST`、`PUT`、`PATCH`、`DELETE` 请求都需要 CSRF 校验。`GET` 必须保持只读。

### 8.3 CSRF 和 CORS 不是一回事

- CSRF：防止浏览器带着已有身份替攻击者提交请求。
- CORS：限制浏览器脚本能否读取或调用跨域资源。

配置 CORS 不能替代 CSRF 防护。

## 9. 首个平台管理员如何产生

本地账号存在“鸡生蛋”问题：系统中还没有管理员时，没人能通过管理 API 创建管理员。

### 9.1 选择

部署人员执行一次性交互命令：

```text
java -jar docquery.jar bootstrap-admin --login-name=<name>
```

密码通过终端交互输入，不进入：

- 命令行历史
- 配置文件
- Git 仓库
- 日志

命令只在没有任何 AdminUser 时创建一个 `PLATFORM_ADMIN`，然后退出。

### 9.2 为什么不提供初始化页面或 HTTP 接口

公开初始化入口会增加：

- Bootstrap Token 管理
- 接口暴露和扫描风险
- 并发初始化控制
- 初始化完成后的关闭逻辑
- 额外页面和错误状态

它只解决一次性的部署问题，不应该变成长期产品功能。

### 9.3 为什么不通过 Flyway 写死管理员

Flyway 适合管理数据库结构和确定性基础数据，不适合保存真实管理员密码或环境秘密。将固定密码哈希写进迁移脚本会导致所有环境共享可预测凭证。

## 10. 业务应用身份选型

### 10.1 为什么业务应用不能使用管理员 Session

管理员 Session 面向浏览器中的人；Application Credential 面向传统业务后端。

二者生命周期和风险不同：

| 对比项 | 管理员 | 业务应用 |
| --- | --- | --- |
| 主体 | 人 | 后端程序 |
| 认证方式 | 本地密码 | Application Credential |
| 状态载体 | HttpSession Cookie | Authorization Header |
| 权限 | 管理操作 | 指定知识库 READ |
| 泄露处理 | 退出、停用账号 | 轮换、撤销凭证 |

### 10.2 Application Credential

建议格式：

```text
dq_app_<keyId>.<secret>
```

- `keyId` 用于定位凭证记录，不属于秘密。
- `secret` 由 `SecureRandom` 生成至少 256 位随机值。
- 数据库只保存 Secret 的 SHA-256 摘要。
- 完整凭证只在创建时返回一次。
- 同一应用最多同时保留两把有效凭证，便于无中断轮换。

### 10.3 为什么应用 Secret 可以使用 SHA-256

管理员密码由人选择，通常熵低，所以需要 bcrypt 这类慢哈希。

Application Secret 由安全随机数生成，至少 256 位，无法进行现实可行的字典枚举。因此可以使用 SHA-256 摘要配合常量时间比较。

两种“秘密”不能因为都叫密码或 Secret 就使用相同策略：

```text
低熵人类密码 -> bcrypt
高熵随机 Secret -> SHA-256 digest
```

### 10.4 为什么第一版不使用 OAuth2 Client Credentials

OAuth2 Client Credentials 适合已有统一 Authorization Server 的企业环境，但需要额外的令牌签发、校验、密钥和部署体系。

DocQuery 第一版使用自包含 Application Credential，目的是让传统系统最少改造即可接入。未来如果企业已有 IdP，可以将服务面升级为 OAuth2 Resource Server，但应用到知识库的 Grant 仍由 DocQuery 管理。

## 11. 授权模型

DocQuery 不是纯 RBAC，而是：

> RBAC + 租户范围 + 资源归属 + 关系授权

### 11.1 管理面

- `PLATFORM_ADMIN`：管理 Tenant，不自动获得租户内部资源管理权。
- `TENANT_ADMIN`：只能管理自己固定 `tenant_id` 下的资源。

请求路径中的 `tenantId` 不是可信身份来源。可信租户范围来自已认证管理员。

### 11.2 服务面

允许读取一个知识库需要同时满足：

```text
Credential ACTIVE
AND Application ACTIVE
AND Tenant ACTIVE
AND KnowledgeBase ACTIVE
AND Application 与 KnowledgeBase 属于同一 Tenant
AND READ Grant ACTIVE
```

调用方不能自行声明或覆盖 `tenantId`。租户身份必须从已验证 Credential 对应的 Application 推导。

### 11.3 为什么使用逻辑外键

DocQuery 遵循不使用数据库物理外键的工程规范。表中的 `tenant_id`、`application_id` 和 `knowledge_base_id` 都是逻辑外键，不创建 `FOREIGN KEY` 或级联操作。

数据库负责：

- 字段类型和 `NOT NULL`
- 主键
- 单表 `UNIQUE`
- 逻辑外键列索引

其中唯一索引用于解决并发竞态：两个请求可能同时通过业务层的“数据不存在”检查，数据库需要原子地保证只有一个事务成功。

数据库不使用 `CHECK` 表达状态、枚举、角色组合或其他业务语义。

Mapper 和 Service 负责：

```text
从可信身份得到 tenantId
→ 使用 (tenantId, applicationId) 查询 Application
→ 使用 (tenantId, knowledgeBaseId) 查询 KnowledgeBase
→ 在同一事务中校验状态和归属
→ 创建同一 tenantId 下的 Grant
```

跨租户 Grant 是业务授权问题，必须通过业务集成测试证明请求失败且没有数据写入。

逻辑外键带来的风险是数据库允许绕过业务代码写入不一致关系。对应控制包括：

- 生产写入只经过受控 Mapper 和 Service。
- 关联写入使用事务。
- N1 不提供物理删除。
- 数据修复和导入脚本必须复用校验规则或执行一致性检查。
- 自动化测试覆盖不存在的父记录和跨租户组合。

这个选择便于未来拆库和迁移，但也意味着不能声称数据库能够独立阻止跨租户关系。

### 11.4 为什么主键使用 BIGINT

当前 DocQuery 是单体服务和单个 MySQL，不需要多个节点脱离数据库独立生成 ID。因此六张表使用 `BIGINT AUTO_INCREMENT` 主键，Java 使用 `Long`，所有逻辑关联 ID 也使用 `BIGINT`。

相比 `CHAR(36)` UUID：

- BIGINT 只占 8 字节，主键和二级索引更紧凑。
- Java、JDBC 和 MySQL 之间不需要 UUID 字符串或二进制转换。
- 自增行为由当前唯一数据库负责，不增加雪花算法等组件。

ID 可预测不构成授权机制。接口仍必须使用可信租户上下文和资源归属校验，不能因为 UUID 难猜就省略鉴权。

如果未来出现分库、多写节点或公开标识不可枚举等明确需求，再评估雪花 ID 或独立 `public_id`；当前不提前增加。

## 12. 立即失效如何实现

每次管理请求检查：

- Session 是否有效
- AdminUser 是否启用
- Tenant 是否启用

每次服务请求检查：

- Credential、Application、Tenant 和 KnowledgeBase 状态
- ApplicationGrant 是否有效

第一版不缓存正向授权结果，因此：

- 管理员被停用后，新请求立即失败。
- 租户或应用被停用后，新请求立即失败。
- Credential 或 Grant 被撤销后，新请求立即失败。

将来引入缓存时，必须同时设计失效消息、短 TTL 或版本号，不能只增加缓存而继续声称“立即失效”。

## 13. 主要取舍

| 决策 | 得到什么 | 接受什么 |
| --- | --- | --- |
| 本地账号 | 可独立部署和演示 | 暂无企业 SSO/MFA |
| bcrypt | 抵抗密码离线枚举 | 登录验证需要可控计算时间 |
| JVM HttpSession | 实现简单、登出直接 | 重启退出登录、暂不支持多实例 |
| 不使用 JWT | 少一套令牌刷新和吊销机制 | 暂不支持跨服务无状态验证 |
| 一次性管理员命令 | 不暴露初始化接口 | 部署时多一个明确操作 |
| 自有应用凭证 | 传统系统接入简单 | 暂不复用企业 OAuth2 平台 |
| 每次查状态 | 撤销和停用立即生效 | 每次请求增加数据库读取 |
| 逻辑外键且无 CHECK | 业务规则集中在 Java，便于迁移和拆库 | 业务代码必须承担关联与状态一致性 |
| BIGINT 自增主键 | 索引紧凑、实现简单、Java Long 直接映射 | 暂不支持多节点独立生成 ID |

## 14. 演进路线

### 阶段一：当前 MVP

- 本地管理员
- bcrypt
- JVM HttpSession
- Application Credential
- RBAC + tenant scope + Grant

### 非项目阶段：已有企业身份系统时的假设扩展

以下内容不是本个人项目的路线。如果真实部署方已有企业身份平台，才可能评估：

- OIDC Authorization Code Flow
- 企业 MFA 或 Passkey
- 外部身份与本地管理员映射
- 继续使用本地 Session 和授权模型

### 阶段三：多实例部署

- Spring Session
- Redis 等共享 Session 存储
- 明确 Session 清理和故障行为

### 阶段四：统一服务身份

如果企业已有成熟 Authorization Server：

- 服务 API 作为 OAuth2 Resource Server
- 使用标准 Access Token
- 保留 DocQuery 内部 Tenant、KnowledgeBase 和 Grant 判断

演进时替换的是认证入口和状态存储，不应推翻业务授权模型。

## 15. 面试常见问题

### 15.1 为什么不用 JWT？

因为管理后台是单体浏览器应用，Session 已经满足身份保持、登出和立即失效。JWT 更适合多个服务独立验证令牌的场景；当前引入 JWT 只会增加刷新、吊销和浏览器存储问题。

### 15.2 Session 是否落后？

不是。Session 和 JWT 是不同约束下的选择。服务端 Web 应用使用安全 Cookie 加 Session 仍然是成熟方案。多实例时可以用 Spring Session 共享，客户端协议不需要改变。

### 15.3 为什么密码不用 SHA-256？

人类密码熵低，快速哈希便于攻击者高速撞库。bcrypt 是带 Salt、可调成本的慢哈希。高熵随机 Application Secret 才适合保存 SHA-256 摘要。

### 15.4 OIDC 和 OAuth2 有什么区别？

- OAuth2 主要解决一个客户端能否代表主体访问资源。
- OIDC 在 OAuth2 之上增加身份层，解决登录后“这个人是谁”。

DocQuery 当前不使用 OIDC。假设真实部署方已有身份平台，DocQuery 应作为 Client 接入，而不是自己成为 OAuth2/OIDC 身份平台。

### 15.5 接入 OIDC 后还需要 Session 吗？

在假设接入场景中仍然需要。OIDC 完成首次身份验证后，DocQuery 可以创建自己的 HttpSession，继续管理本地角色和租户范围。

### 15.6 如何保证跨租户隔离？

租户身份从已验证的管理员或应用身份推导，不信任请求传入的 tenantId；Mapper 始终使用 `tenantId + resourceId` 查询；Service 在同一事务中检查 Application、KnowledgeBase 和 Grant 的归属，并通过集成测试证明跨租户请求不会写入数据。数据库不使用物理外键。

### 15.7 停用账号后，已有 Session 为什么会立即失败？

因为每次管理请求不仅检查 Session，还读取当前 AdminUser 和 Tenant 状态。Session 只证明之前登录成功，不覆盖实时的停用状态。

### 15.8 为什么平台管理员不能直接管理所有知识库？

平台运维权限和租户内部数据权限是不同职责。默认不继承租户数据权限可以减少平台账号被攻破后的影响范围，也让授权边界更容易审计。

### 15.9 第一个管理员从哪里来？

部署人员通过一次性交互命令创建。密码不进入仓库、配置或命令参数；系统不开放注册和 `/bootstrap` 接口。

### 15.10 当前方案最大的不足是什么？

本地账号没有 MFA，JVM Session 不支持无感多实例，服务凭证也不是统一 OAuth2 Token。这些是个人项目明确接受的边界；只有真实需求出现时才评估 OIDC、Spring Session 或 Resource Server，不把它们包装成已经规划的功能。

### 15.11 为什么主键不用 UUID？

当前只有单个 MySQL，使用 BIGINT 自增主键可以获得更小的索引和更简单的 Java 映射。安全性由租户和权限校验保证，不依赖 ID 难猜。未来只有在分库、多写节点或公开 ID 不可枚举成为真实需求时，才引入分布式 ID 或独立 public_id。

### 15.12 为什么数据访问选择 MyBatis，而不是 JPA 或 MyBatis-Plus？

DocQuery 的核心查询会显式携带租户范围、资源状态和授权条件。原生 MyBatis 让 SQL 和查询条件直接可见，便于代码审查时确认有没有漏掉 `tenant_id` 或状态条件，也不会提前引入一套当前用不到的通用 CRUD 抽象。

这不是说 JPA 或 MyBatis-Plus 不好。JPA 更适合围绕对象关系和聚合进行持久化的模型；MyBatis-Plus 可以减少常规 CRUD 样板代码。当前项目的表和查询不多，并且多租户授权更重视 SQL 可见性，所以先选择原生 MyBatis。复杂动态 SQL 出现后可以增加 XML Mapper，但不改变 Service 负责业务规则的边界。

### 15.13 为什么 REST 登录后要显式保存 SecurityContext？

因为自定义 Controller 不是 Spring Security 内置登录过滤器。`AuthenticationManager` 返回成功的 Authentication 只说明凭证验证通过，不会自动保证后续请求能从 Session 恢复身份。项目显式执行 Session 策略、设置 SecurityContext，并保存到 `HttpSessionSecurityContextRepository`。

### 15.14 为什么登录接口也要求 CSRF？

登录会让浏览器进入攻击者指定账号的认证状态，也可能造成后续操作和数据关联错误，因此不能把登录简单排除在 CSRF 防护之外。客户端先获取匿名 Token，登录后再获取轮换后的 Token。

## 16. 面试回答结构

遇到身份授权问题时，可以按下面顺序回答：

1. 先讲调用者：管理员和业务应用是两类主体。
2. 再讲约束：单体、少量管理员、多租户、要求立即失效。
3. 给出选择：本地密码加 Session，应用使用独立 Credential。
4. 解释取舍：为什么当前不使用 JWT、自建 OAuth2 或强制 OIDC。
5. 讲安全措施：bcrypt、Cookie、CSRF、状态复查、逻辑外键和跨租户业务测试。
6. 最后区分实际实现与知识扩展：当前没有 OIDC、Spring Session 或 OAuth2 Resource Server，只有出现对应部署需求才评估。

重点不是声称某个技术“最好”，而是证明选择和项目约束一致，并且知道它的边界。

## 17. MyBatis 数据访问选型

### 17.1 当前选择

- 使用原生 `mybatis-spring-boot-starter:4.1.0`，与 Spring Boot `4.1.0`、Java 17 基线匹配。
- 简单 SQL 使用注解 Mapper；复杂动态 SQL 真正出现后再引入 XML。
- 不使用 MyBatis-Plus、通用 BaseMapper 或代码生成器。
- Mapper 只表达数据操作；关联存在性、状态组合和跨租户规则由 Service 在事务中校验。
- 数据库仍然不使用物理外键、`CHECK` 或级联操作，MyBatis 不改变这一决定。

### 17.2 得失

得到的是 SQL 可见、租户条件易审查、行为接近数据库实际执行；接受的是简单 CRUD 需要手写少量 SQL，字段变更时需要同步维护 Mapper。当前规模下这是可控成本。

N1.3a 只有 `AdminUserMapper` 的统计和插入两条 SQL，因此使用注解比单独创建 XML 更直接。后续若出现长 SQL、动态筛选或复杂结果映射，再把对应语句移入 XML，不提前建立空模板。

### 17.3 版本依据

MyBatis 官方 Starter 文档说明 4.0 系列面向 Spring Boot 4.0+ 和 Java 17+；官方 4.1.0 发布说明记录了对 Spring Boot 4.1.0 的更新。项目因此选择 4.1.0，而不是跨主版本使用旧 Starter。
