## 1. 选择结果

N2.3 选择“格式专属、无模型、结构感知”的解析方式：

| 格式 | 已落地组件 | 版本/来源 | 主要输出 |
| --- | --- | --- | --- |
| PDF | Apache PDFBox | 3.0.8 | 可见文本、物理页、布局属性、Outline、Tagged Structure |
| DOCX | Apache POI `poi-ooxml` | 5.5.1 | 段落、Heading/outline、列表、表格单元格 |
| Markdown | CommonMark Java | 0.28.0 | AST、标题、段落、列表、引用、代码块、源码行 |
| TXT | JDK Charset API | Java 17 | 严格 UTF-8、段落、起止行 |

第一版不引入 Apache Tika。当前只有四种明确格式，而且每种格式都需要不同的真实标题和位置规则；通用 Parser 会增加隐藏行为，不能替代格式 Adapter。

## 2. 为什么 N2.3 不使用模型切分

N2.3 保存的是可重建的文档事实，不是最终检索策略：

- 语义切分依赖 Embedding、阈值和模型版本，规则变化会改变事实输出；
- Contextual Retrieval 是给检索块增加上下文的索引增强，不是文件解析；
- RAPTOR 使用模型递归摘要生成语义树，成本、稳定性和评测工作超过第一版需要；
- 固定窗口会切断真实结构，且 Chunk Size/Overlap 只能通过后续检索评测确定。

因此本阶段先确定性地保留原文、真实结构和位置。未来新增语义段落、上下文或 RAPTOR 时，只建立可重建投影，不覆盖 canonical 事实。

## 3. EvidenceBlock 不是向量 Chunk

解析器仍会拆分文档，但边界来自源文件结构：

| 格式 | EvidenceBlock 边界 |
| --- | --- |
| PDF | 物理页内恢复出的标题、段落、列表项或文本块 |
| DOCX | 标题、段落、列表项、表格单元格、预格式段落 |
| Markdown | AST 中的标题、段落、列表、引用和代码块 |
| TXT | 空行分隔的段落 |

这些块用于：

- 保持稳定原文顺序；
- 提供页码、段落或行号；
- 建立 canonical offset；
- 供后续 BM25 和原文阅读重建输入。

它们不生成 Embedding，也不直接决定回答上下文。异常巨大的单一源元素只按自然边界做无重叠安全拆分，并用 `continuationGroupId` 表明同源关系。

## 4. 真实标题树

标题树不需要大模型总结：

1. 建立必有的文档根节点；
2. 按源文件顺序读取真实标题和级别；
3. 用标题级别栈连接最近的真实父标题；
4. 同级或更浅标题关闭之前的章节范围；
5. 级别跳跃时连接真实父节点并记录 Warning，不补造中间标题。

文档封面标题保存为 `TITLE` 原文块并归属于根节点，不自动冒充章节。没有章节标题的文档只有根节点，这不是解析失败。

## 5. PDF 标题识别边界

PDFBox 不只用于书签。N2.3 按以下优先级识别能够映射到可见原文的真实标题：

1. Tagged Structure 中可验证的 `H1`—`H6`；
2. 能定位目标页并匹配可见文本的 Outline；
3. 普通单栏文档中由字号、字重、上下留白、行长、重复样式和页面位置共同支持的高置信可见标题。

结构提示必须映射到实际可见文本，不能只因为 PDF 内部存在标签或书签就信任。样式冲突或置信不足时，保留原文并记录 Warning，不创建不可靠标题。

第一版支持普通文本型、正常阅读顺序的单栏 PDF；以下情况受控失败：

- 扫描/纯图片 PDF；
- 禁止文本提取的加密 PDF；
- 损坏 PDF；
- 明显多栏、旋转或无法确定阅读顺序的复杂版面；
- 页数或输出资源超过上限。

## 6. 为什么只生成一个 canonical JSONL

每个文档版本形成：

```text
DocumentVersion
├─ source object                 原始上传文件
└─ DocumentCanonicalArtifact    MySQL清单
   └─ canonical.jsonl object     正文、真实标题树、位置和Warning
```

不再拆成 `content.txt` 与 `structure.json` 两个对象，原因是：

- 正文、标题和位置在同一对象摘要下提交，不会出现两对象只成功一个；
- JSONL 可以逐行消费，不必把长文全部载入内存；
- Header/Footer 能表达 schema、计数、完整标记和文本摘要；
- N2.4/N2.5 可以从同一事实重建模型卡片或 ES 投影；
- 原文件仍保留，Parser 规则升级时可以重新解析。

MySQL 只保存对象地址、版本、计数和 SHA-256，不保存全文 BLOB。

## 7. 对象存储端口

派生对象使用独立业务端口 `CanonicalArtifactStore`，而不是让 Parser 直接依赖 S3 SDK 或 SeaweedFS：

- 可与 `SourceObjectStore` 共用同一 S3 Client、Bucket 配置和 Server；
- 原文件与派生对象具有不同前缀、生命周期和清理规则；
- Parser 只读写本地解析模型，不访问对象存储或数据库；
- 编排 Service 负责下载、完整性校验、上传和清单登记。

默认实现使用 AWS SDK v2 对接 SeaweedFS S3 API，但业务语义不绑定具体 Server。

## 8. 完整性与幂等

`DocumentCanonicalService.ensureCanonical(documentVersionId)` 的关键顺序是：

```text
加载MySQL可信版本和对象引用
→ 下载原文件并复核大小/SHA-256
→ 调用显式格式Adapter
→ 组装并校验CanonicalDocument
→ 写本地临时canonical JSONL
→ 上传随机Key并完整读回校验
→ 插入document_canonical_artifact
→ 返回已验证清单
```

幂等身份是 `documentVersionId`：

- 已有清单且对象大小/摘要有效时直接复用；
- 数据库唯一约束只允许一个并发胜者；
- 败者只删除自己生成的随机 Key；
- 对象上传成功但清单失败时立即精确删除；
- 删除失败或进程崩溃由有宽限期、逐对象检查引用的回收器兜底；
- 数据库状态未知时不删除。

## 9. canonical 校验

写入有效清单前同时验证：

- Schema、Header、Footer 和 `complete=true`；
- Block ordinal、稳定 ID 和 canonical range；
- 按块重建全文、UTF-16 长度和 UTF-8 SHA-256；
- 每个块的 SourcePosition；
- 标题树单根、无环、父节点存在；
- 每个非根标题映射真实标题原文块；
- 章节范围、计数、对象大小和对象 SHA-256；
- 至少一个非空证据块。

任何核心校验失败都不能保存成功清单。

## 10. 资源上限

当前默认边界：

| 项目 | 上限 |
| --- | --- |
| PDF 页数 | 2000 |
| DOCX 展开大小 | 200 MiB |
| canonical JSONL | 100 MiB |
| EvidenceBlock 数量 | 200000 |
| 单块字符数 | 65536 |

DOCX 在 POI 完整解析前检查 ZIP 结构、条目数量和展开规模，防止伪装文件与明显 ZIP 膨胀。TXT/Markdown 使用严格 UTF-8 解码，非法字节不静默替换。

## 11. 失败契约

确定性文件失败不可重试，例如：

- `DOCUMENT_FORMAT_MISMATCH`
- `DOCUMENT_CORRUPT`
- `ENCRYPTED_DOCUMENT_UNSUPPORTED`
- `PDF_NO_EXTRACTABLE_TEXT`
- `PDF_COMPLEX_LAYOUT_UNSUPPORTED`
- `TEXT_ENCODING_UNSUPPORTED`
- `DOCUMENT_PARSE_LIMIT_EXCEEDED`
- `CANONICAL_VALIDATION_FAILED`
- `SOURCE_OBJECT_INTEGRITY_MISMATCH`

对象存储或数据库暂时不可用是可重试失败，例如：

- `SOURCE_OBJECT_UNAVAILABLE`
- `CANONICAL_OBJECT_UNAVAILABLE`
- `PROCESSING_DATABASE_UNAVAILABLE`

异常消息不包含正文、Bucket、Object Key 或第三方完整堆栈。

## 12. 阶段边界

N2.3 不做：

- Chat Model、Embedding Model 或语义切分；
- DocumentProfile、RetrievalNode、摘要、主题和别名；
- Elasticsearch、BM25、向量或 Redis；
- 查询、Agent、回答和外部引用接口；
- OCR、图片理解、公式识别和复杂版面模型；
- `READY`、`activeVersionId` 切换或 ProcessingJob 成功；
- 在完整 Processor 存在前开启生产 RabbitMQ Listener。
