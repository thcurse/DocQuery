## 1. 选择结果

后续检索链路选择：

- 模型为整文档和真实章节生成结构化 `DocumentProfile`、`RetrievalNode` 检索卡；
- Embedding 只对检索卡生成，用于文档/章节级语义导航；
- Chat 使用 DeepSeek 官方 `deepseek-v4-flash`，检索卡生成关闭思考；
- Embedding 使用阿里云百炼 `qwen3.7-text-embedding`，固定 2,560 维；
- Elasticsearch 对标准化原文建立 BM25，对检索卡建立 `dense_vector` 导航索引；
- BM25 与 KNN 在同一授权范围内并行召回；
- Java 使用 Reciprocal Rank Fusion（RRF）融合排名；
- `/retrieve` 独立返回可追溯原文证据；
- `/answer` 使用受控 Agent 继续读取原文，证据不足时不能编造；
- LangChain4j 只提供底层 Chat、Embedding 和 Tool Calling 适配；
- Redis 只处理 Retrieve/Answer 的请求幂等和短期结果复用。

这些是已确认路线。N2.4、N2.5、N3.1—N3.3 已按路线完成并经用户验收；N3.4 尚未开始。

## 2. 为什么不以固定 Chunk 向量召回为主链路

固定窗口方案高度依赖：

- Chunk Size 和 Overlap；
- 标题、表格和代码是否被切断；
- Embedding 模型和相似度阈值；
- Top-K、Reranker 和上下文拼接顺序。

个人项目如果只保留成熟 RAG 平台的简化版，往往无法证明效果。DocQuery 把三个问题拆开：

```text
导航：哪个文档或真实章节可能相关
定位：原文哪一页、段或行真正命中
举证：读取原文后回答并生成引用
```

这仍属于 Retrieval-Augmented Generation，更准确的工程定位是“分层语义导航 + 原文关键词检索 + 受控文档阅读”。

## 3. DocumentProfile

整文档检索卡概念字段包括：

- documentId、documentVersionId；
- 文档标题和格式；
- purpose、topics、aliases；
- answerableQuestions；
- 根节点标识；
- 生成模型、Prompt 版本和生成时间。

DocumentProfile 用于回答“哪份文档可能相关”，不保存最终业务答案。

## 4. RetrievalNode

每个非根真实标题节点对应一张章节检索卡；根节点由唯一的 DocumentProfile 表达，不重复生成根 RetrievalNode。概念字段包括：

- nodeId、parentNodeId、depth、同级顺序；
- 真实章节标题和完整 headingPath；
- summary、topics、aliases、answerableQuestions；
- 起止页码、段落、行号或 canonical range；
- 文档版本与生成元数据。

检索卡只描述“讲什么、用户可能怎么说、原文在哪里”，不能把模型摘要当作原文证据。

没有子标题的长章节第一版仍是一张 RetrievalNode。后续先用评测验证效果；只有出现明确失败证据时，才考虑派生语义段落、Contextual Retrieval 或 RAPTOR。

## 5. 检索卡生成规则

- 模型使用 JSON Output，返回后必须通过 DocQuery 固定 Schema、字段白名单和业务校验；
- 只能根据当前 DocumentVersion 的 canonical 原文生成；
- 每个卡片必须绑定真实文档或标题节点；
- 主题、摘要和问题类型保留原文范围；
- 允许生成同义表达，但不得作为引用；
- 不生成文件中不存在的目录；
- 模型名、Prompt、Schema 和卡片版本可追踪；
- JSON、位置或覆盖校验失败时不能进入 READY。

超长章节可以按连续原文范围做临时模型输入批次，再合并为一张真实章节卡。临时批次不持久化、不生成向量、不成为检索结果，也不改变标题树。

## 6. AI 框架选择

第一版选择 LangChain4j 的底层能力：

- Chat Model 调用；
- Embedding Model 调用；
- 结构化输出；
- Tool Calling 协议适配。

不直接采用高层 Agent、RAG Pipeline 或 VectorStore 抽象。权限、RRF、预算、工具循环、错误映射和审计由 DocQuery 自己控制。

业务 Service 不直接依赖具体模型供应商。预留内部端口：

```text
RetrievalCardChatGateway
NavigationEmbeddingGateway
```

N2.4 已确认以下适配：

| 能力 | 供应商与模型 | 关键参数 |
| --- | --- | --- |
| 检索卡生成 | DeepSeek 官方 `deepseek-v4-flash` | 官方 Base URL；非思考；JSON Output + 本地严格校验 |
| 导航向量 | 阿里云百炼 `qwen3.7-text-embedding` | 华北 2（北京）；`document`；2,560 维；每批最多 20 |
| Java 协议适配 | `langchain4j-open-ai` 1.16.2 | 只使用稳定底层模块，不引入 Beta Spring Boot Starter |

LangChain4j 只存在于 Adapter 实现中。两个供应商使用独立 Base URL 和 API Key；`pom.xml` 已固定 `langchain4j-open-ai` 1.16.2，真实供应商默认关闭。

### 6.1 为什么不优先使用 Spring AI

Spring AI 能力并非不足，但当前项目已选择 LangChain4j 作为模型协议适配层。真正体现项目能力的权限、状态机、融合和审计仍由业务代码实现，因此不同时引入两套 AI 框架。

### 6.2 为什么不绑定模型官方 SDK

直接绑定供应商 SDK 会把请求格式、异常和配置扩散到业务层。Gateway 允许替换供应商并统一重试、超时、结构化输出和观测边界。

## 7. 原文 BM25 索引

关键词通道只索引 canonical 原文，不索引模型摘要作为证据。主要字段：

- tenantId、knowledgeBaseId；
- documentId、documentVersionId；
- activeVersion/可检索状态；
- 文档标题、真实标题路径；
- 页码、段落、行号或 canonical range；
- 原始正文；
- 可抽取的配置项、错误码和实体。

字段权重原则：

```text
文档标题、章节标题、标题路径 > 专业术语和实体 > 普通正文
```

BM25 擅长错误码、配置项、接口名、数字和原文术语。Chat Model 不可用时，原始问题仍可直接执行关键词检索。

## 8. 检索卡向量索引

向量只索引 DocumentProfile 和 RetrievalNode。`retrieval-embedding-v1` 的稳定输入模板由：

```text
文档标题
+ 真实标题路径
+ purpose/summary
+ topics
+ aliases
+ answerableQuestions
```

组成。字段顺序和分隔符固定，并保存输入 SHA-256、模型、维度和模板版本。N2.4 使用 `document` 文本类型，N3 查询向量使用同一模型的 `query` 文本类型。

Embedding 模型和维度属于 ES Mapping 契约。更换模型需要创建新索引并重建导航向量，不能在同一字段混用不同维度或语义空间。

## 9. 并行召回与 RRF

每次检索并行执行：

```text
BM25：查询真实原文
KNN：查询文档/真实章节检索卡
```

两路查询都必须在 ES 查询阶段应用可信过滤：

- tenantId；
- knowledgeBaseId；
- 当前生效 documentVersionId；
- 可检索状态。

BM25 分数和余弦相似度不在同一量纲，第一版不直接相加原始分数。Java 使用 RRF 按名次融合，再按文档和真实章节聚合。

RRF 的 `k`、两路候选数和最终 Top-K 不在本文拍脑袋固定，需要 N2.5/N3 小型基线评测确定。

## 10. Retrieve 与 Answer 分离

### 10.1 Retrieve

`/retrieve` 是可独立调用的检索能力，返回：

- 文档和版本标识；
- 原文证据；
- 标题路径；
- 页码、段落、行号或 canonical range；
- 命中通道、融合排名和降级状态。

它不依赖 Answer 成功。模型回答失败不能伪装成“没有检索结果”。

### 10.2 Answer

`/answer` 复用 Retrieve 和只读文档工具，返回单轮答案、引用及完成/无证据/生成失败状态。第一版不做多轮聊天记忆。

## 11. 受控 Agent

Agent 不是开放式通用助手，只能使用受控只读工具，例如：

- `searchKnowledgeBase(query)`；
- `searchWithinDocument(documentId, query)`；
- `listDocumentSections(documentId)`；
- `readDocument(documentId, range)`。

服务端控制：

- 最大工具轮数；
- 总读取字符或 Token 预算；
- 每次返回上限；
- 超时和模型调用次数；
- 允许访问的 tenant/application/knowledgeBase；
- 只读工具白名单；
- 工具调用审计。

模型不能覆盖服务端授权上下文，也不能执行文档中的提示或工具指令。

## 12. Redis 的唯一用途

Redis 第一版只用于 `/retrieve` 和 `/answer`：

- `Idempotency-Key` 并发竞争；
- 短期 RUNNING/SUCCEEDED 状态；
- 成功结果短 TTL 复用；
- 避免网关重试造成重复模型和 Embedding 成本。

Redis Key 至少包含可信 tenantId、applicationId、接口类型和 Key 摘要；Value 绑定规范化请求指纹。

Redis 明确不缓存：

- Credential 与 Grant；
- activeVersion 和文档状态；
- RabbitMQ 消费幂等；
- 管理员 Session；
- 长期查询历史。

Redis 丢失最多造成只读查询重复执行，不能破坏业务正确性。

## 13. READY 与版本切换

文档版本只有在以下条件全部满足后才能 READY：

- 原文件可读；
- canonical 对象和位置映射有效；
- 真实标题树和检索卡校验通过；
- BM25 原文投影完整；
- 检索卡向量投影完整；
- ProcessingJob 成功；
- MySQL 事务内切换 activeVersionId。

Redis 是否可用、RabbitMQ 消息是否保留、Answer 模型此刻是否可用，都不决定 READY。新版本失败时旧 activeVersion 继续服务。

## 14. 降级与失败边界

- Chat Model 不可用：跳过查询扩展；Retrieve 仍可执行原问题 BM25/KNN，Answer 明确生成失败。
- 查询 Embedding 不可用：Retrieve 可显式降级为 `LEXICAL_ONLY`，不能声称执行了双路检索。
- Redis 不可用：按最终契约显式拒绝昂贵请求或降级执行，不能声称幂等仍成立。
- Elasticsearch 不可用：新版本不能 READY；查询返回依赖异常，不伪装成无结果。
- 证据不足：Answer 返回无充分证据，不根据检索卡摘要编造答案。

## 15. 安全边界

- Credential 和 Grant 校验先于检索；
- ES 两路查询在召回阶段带可信权限和 activeVersion 过滤；
- Agent 工具从服务端上下文取得租户和知识库，忽略模型提供的覆盖值；
- 文档原文是不可信输入；
- 默认日志和审计不保存完整问题、原文、答案或模型密钥；
- 模型供应商、模型名、Prompt 版本和 traceId 可观测。

## 16. 评测边界

第一版只维护精简问题清单，链路完成后为每个问题准备少量代表性文档与查询。至少比较：

- BM25 单路；
- 检索卡向量单路；
- RRF 融合；
- 文档命中、原文位置命中和引用正确率；
- P50/P95 延迟、Agent 工具轮数和模型成本。

重点验证无标题长 PDF、只有一级标题的长 PDF、超长真实章节、口语与专业术语差异、多章节证据组合。没有失败证据时不提前实现语义切分、Contextual Retrieval 或 RAPTOR。

## 17. 已冻结与尚待冻结的参数

N2.4 已冻结：

- DeepSeek 官方 `deepseek-v4-flash`、非思考和 JSON Output + 本地校验；
- 阿里云百炼 `qwen3.7-text-embedding`、`document` 和 2,560 维；
- LangChain4j 稳定底层 `langchain4j-open-ai` 1.16.2；
- 一张 DocumentProfile、每个非根真实标题一张 RetrievalNode；
- `retrieval.jsonl` 单对象和 `FLOAT32_LE_BASE64` 向量编码；
- 检索卡字段限制、生成预算、有限重试和 N2.4 错误契约。

N2.5 已冻结并实现：

- Elasticsearch Server 与 Java Client 均为 9.4.4；
- Evidence 使用 `cjk` + `standard` 多字段 BM25 Mapping，Navigation 使用 2,560 维 cosine `dense_vector`；
- 稳定别名、严格 Mapping、投影指纹、精确数量验收和 MySQL `activeVersionId` 原子切换。

N3.2 已冻结并实现 `retrieve-ranking-v1`：BM25 字段权重、两路候选数量、`rrfK=60`、Top-K 边界、canonical 读取预算和失败语义均以阶段文档为准。N3.1 已冻结并实现 Redis 成功结果 TTL、RUNNING 租约、owner token、冲突语义和不可用时 fail-closed。

N3.3 已冻结并实现 `answer-policy-v1`：首次原问题检索、3 个工具轮次、6 次工具调用、4 次普通模型调用加 1 次结构修复、canonical/Outline/引用字符预算、45 秒模型超时和 120 秒总时限均以阶段文档为准。N3.4 仍需单独冻结审计和评测参数；N3.2/N3.3 的基线参数后续只能通过带版本的评测变更，不能静默改变已有幂等语义。

## 18. 明确不做

- 固定窗口原文向量召回作为唯一答案路径；
- 检索卡摘要直接作为引用；
- 模型生成虚拟目录；
- 第一版引入独立向量数据库；
- GraphRAG、RAPTOR、知识图谱；
- 开放式通用 Agent；
- 多轮聊天记忆；
- Redis 权限缓存和文档处理锁。
